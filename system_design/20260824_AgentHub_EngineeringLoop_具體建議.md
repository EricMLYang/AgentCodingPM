## 1. 核心觀念：一個控制迴路，量四種落差

骨架仍是一句話：

> **定義目標 → 量測現況 → 算出落差（目標−現況）→ 改變 input → 執行 → 再量測**，直到落差歸零。

但「目標」不只一種。程式「功能對了」只是其中一項；一個系統可以功能全對、卻越改越慢、架構越改越歪、畫面越改越醜。所以 loop 要同時量**四種落差**，各有各的目標定義方式與量測器：

| 落差 | 目標怎麼定 | 落差怎麼量 | 最終誰判 |
|---|---|---|---|
| **① 功能性** | 需求卡三句驗收 → 翻成測試 | 單元＋整合測試（含 MCP 鐵律、寫入閉環） | 測試紅綠，全自動 |
| **② 非功能性** | 把形容詞寫成**數字預算**（載入 < 2 秒、無障礙零重大違規、未授權寫入 100% 被拒） | 效能／無障礙／資安的自動化檢查，進 CI | 預算超標即紅，全自動 |
| **③ 期望架構** | ARCHITECTURE.md 寫下模組邊界與依賴規則 | 兩層：架構體檢測試（可機器判的規則）＋ code review（機器判不了的意圖偏離） | 體檢測試自動；review 由 AI 初審、人終審 |
| **④ UI/UX** | 設計基準截圖＋體驗檢查表 | Agent E2E 三件套：腳本斷言＋畫面比對＋Agent 走一遍打檢查表 | Agent 交證據與初評，**Eric 終判** |

兩個原則貫穿四種落差：

1. **寫不下來的目標，量不出落差。** 非功能性需求停在「要快」、期望架構停在腦中、「好看」停在感覺——都等於沒有目標訊號。動工前先把四種目標各自「寫成可比對的東西」（數字預算、ARCHITECTURE.md、基準截圖、檢查表），這比先寫功能程式碼更優先。
2. **「改變 input」有兩層。** 內圈改**程式碼**（量測器紅了→修 code）；外圈改**工作環境**（Agent 重複犯同類錯→修文件、測試、規則）。2026 年業界把後者叫 **harness engineering**（harness＝Agent 的工作鷹架：回饋迴路＋安全邊界＋驗證系統的總稱），並有一條經驗法則：**同一種錯出現第二次，就該去修鷹架，而不是再修一次 code**。

## 2. 本版吸收的外部概念（2026 主流，白話版）

研究了 harness engineering（Martin Fowler 等）、架構 fitness functions、Playwright MCP 生態、LLM 評審（LLM-as-judge）後，挑出四個對本案直接有用的概念：

1. **事前引導與事後感測並用**（feedforward / feedback）：給 Agent 的規則文件、需求卡是「事前引導」；測試、review 是「事後感測」。兩者都要投資——只堆事後測試而文件爛，Agent 每次都先犯錯再被抓，loop 空轉。
2. **快慢兩種感測器**（computational / inferential）：一種是**機器判**——測試、lint、型別檢查、架構體檢，毫秒到秒級、答案確定；一種是**模型判**——AI code review、UX 評審，慢且不完全穩定，但能看懂「意圖」。分工原則：**能寫成機器判的規則絕不留給模型判；模型判專門負責機器判不了的東西**（過度設計、誤解需求、偏離架構意圖）。
3. **AI 加速架構飄移，所以架構規則要可執行**：業界實測發現 coding agent 產出快、弄歪架構也快（有研究統計 agent 平均每個 patch 弄壞 6.5 個既有測試）。對策是「架構體檢測試」（architecture fitness functions）：把模組邊界寫成會跑的測試（JS/TS 生態常用 dependency-cruiser 這類工具），違規直接擋合併——Google、Shopify、Netflix 都採「違規即擋」策略。
4. **一張需求卡＝一份 loop 規格**：2026 年對「交給 agent 的任務」的共識格式是五要素——**觸發（何時啟動）、目標、驗證方式、停止規則、記錄**。我們的三句驗收已覆蓋中間兩項，補上停止規則與記錄欄位就齊了（§6 的需求卡模板照此補）。

## 3. Loop 的形狀:三層迴路

```text
外圈（版本級・修鷹架）        每輪開發結束跑一次
┌──────────────────────────────────────────────┐
│  同一種錯出現第二次？→ 修文件／測試／規則           │
│  → 記進 casebook                               │
│                                                │
│  中圈（任務級）              每張需求卡跑一次       │
│  ┌──────────────────────────────────────────┐  │
│  │ 需求卡（loop 規格五要素）→ 判 R0–R3          │  │
│  │ → 先寫測試（紅）→ 開發                      │  │
│  │ → 四種落差量測（§5）→ AI 初審＋自我 review    │  │
│  │ → R2/R3 停下等人 → 合併 → 閉環確認           │  │
│  │                                          │  │
│  │  內圈（秒級・Agent 自主）    改一次跑一次      │  │
│  │  ┌────────────────────────────────────┐  │  │
│  │  │ 改 code → verify:fast → 紅了修       │  │  │
│  │  │ → 綠了才前進（修 3 次不過 → 停）        │  │  │
│  │  └────────────────────────────────────┘  │  │
│  └──────────────────────────────────────────┘  │
└──────────────────────────────────────────────┘
```

- **內圈**只放機器判的快感測器（lint、型別、單元測試、架構體檢的靜態部分），目標 10 秒內，Agent 全速自主。
- **中圈**在合併前把四種落差量齊；模型判的慢感測器（AI review、UX 評審）放這裡，不放內圈。
- **外圈**修的是鷹架不是 code——這正是「網站用 agent loop 持續精進」的字面意義：不只網站在進步，開發網站的環境本身也在進步。

## 4. 中圈逐步定義

每一步定義「做什麼、產出什麼證據、憑什麼往下走」，沒有證據不前進：

| # | 步驟 | Agent 做什麼 | 產出證據 | 前進條件 |
|---|------|-------------|---------|---------|
| 1 | 需求卡 | 讀卡；卡含五要素（觸發／目標／驗證／停止規則／記錄），目標與驗證即三句驗收（`00_context/04`） | 無（人寫卡） | 三句答得出來 |
| 2 | 判風險 | 對照風險熱點表（檢討缺口 3）自評 R0–R3 | 等級與理由寫進任務記錄 | R2/R3 → 先向人確認 checkpoint 再動工 |
| 3 | 先寫測試 | 把驗收翻成**會失敗的測試**；翻不成的明標人工項 | 新測試＋跑一次證明是紅的 | 紅得「對」（因功能沒做而紅） |
| 4 | 開發 | 寫功能，每次修改跑 `verify:fast`（內圈） | 修改記錄 | `verify:fast` 全綠 |
| 5 | 四落差量測 | 跑 `verify:full`＋`verify:e2e`＋`verify:arch`；UI 任務跑畫面比對＋體驗檢查表（§5.4） | 測試報告、截圖、檢查表 | ①②③自動項全綠；④證據齊 |
| 6 | Review | 先 AI code review 對照 ARCHITECTURE.md 與需求卡（§5.3）；再自查 diff 範圍，動到卡外→停下來問 | review 意見＋diff 摘要 | 範圍內、無弱化測試、無架構偏離未解釋 |
| 7 | 合併 | 照 R 等級走對應 Gate 與人審深度（`00_context/05`） | PR／合併記錄 | 過門檻 |
| 8 | 閉環確認 | 生效後實際讀回：內容改動→MCP 查回比對；頁面改動→瀏覽器實開（檢討缺口 7） | 讀回結果 | 讀回一致才回報完成 |

## 5. 四種落差的量測器具體佈局

統一入口先定「介面」，實際命令隨技術規格選型代入：

| 入口 | 量哪種落差 | 速度 | 何時跑 |
|---|---|---|---|
| `verify:fast` | ①功能（單元）＋③架構（靜態規則） | < 10 秒 | 內圈每次修改 |
| `verify:full` | ①功能（整合：MCP server 真的起來打） | 分鐘級 | 合併前；CI |
| `verify:arch` | ③架構體檢全套 | 秒級 | 合併前；CI（快的部分併入 fast） |
| `verify:e2e` | ②非功能＋④UI/UX 的自動部分 | 分鐘級 | 合併前；CI |
| （人工） | ④主觀體驗終判＋③架構意圖抽查 | — | Eric |

### 5.1 功能性落差（沿用 v1，不變）

- 單元測試：內容資料驗證規則、MCP 工具純邏輯、出處欄位組裝。
- 整合測試四組核心案例（§8.2 鐵律的測試化，檢討缺口 4／7）：
  1. **帶出處**：固定題庫（10–20 條真實查詢＋預期來源），斷言回覆含來源欄位且指向系統內真實條目。
  2. **查不到就說查不到**：必無題庫（5–10 條系統內確定沒有的主題），斷言回「查無」且不含模型生成的一般知識。
  3. **寫入管制**：未授權來源呼叫寫入工具，斷言被拒＋有記錄。
  4. **寫入閉環**：寫入→立即讀回逐欄比對→確認修改記錄多一筆→清理；任一段失敗即紅。

### 5.2 非功能性落差：把形容詞變成預算

原則：每條非功能性需求都寫成**一個數字＋一個自動檢查**，數字化不了的就明定人工。第一版預算表：

| 需求裡的形容詞 | 預算（待實測校正） | 量測器 |
|---|---|---|
| 「快」 | 首頁載入 < 2 秒；主要頁面 < 3 秒 | E2E 腳本計時；技術規格若選 Lighthouse CI 可直接掛效能預算 |
| 「手機能看」 | 375px 寬無橫向捲軸、可讀可點 | E2E 三寬度腳本（375/768/1280px） |
| 可及性（新增建議） | axe-core 這類無障礙掃描：嚴重（critical）違規＝0 | 掃描工具進 `verify:e2e` |
| 「寫入嚴格管制」 | 未授權寫入 100% 被拒、100% 留記錄 | §5.1 案例 3 |
| MCP 攻擊面（Gate B） | 工具清單與權限宣告有快照測試：任何變動必是紅的、必經人審 | 快照比對進 `verify:fast` |
| 可回滾（R0/R1 全速區的前提） | 每次部署可一鍵回上一版 | 部署腳本自帶回滾命令＋演練一次 |

### 5.3 期望架構落差：先寫下期望，再兩層量測

**前提：ARCHITECTURE.md。** 沒寫下來的期望架構量不出落差。動工前先寫一頁（就一頁）：模組怎麼切、依賴方向、哪些規則不可違反。team-agent-hub 第一版至少寫這五條：

1. **部門識別只能來自設定檔**——程式碼與模板內不得寫死站名、團隊名、色系（v0.2 §3.5 通用產品定位的落地）。
2. **唯讀與寫入分離**——MCP 唯讀工具模組不得 import 寫入模組；寫入必經認證層。
3. **資料存取集中**——頁面與 MCP 工具不得直接下 SQL，一律經資料層。
4. **出處是型別強制**——查詢回覆的介面型別把來源欄位設為必填，漏帶出處在編譯期就紅。
5. **新依賴是紅燈**——lockfile 出現新第三方套件即紅，走 Gate A 供應鏈檢查後人工放行。

**量測層 1（機器判）：架構體檢測試（fitness functions）。** 上面五條全部可自動化：規則 1 用 lint/掃描（掃寫死字串）；規則 2、3 用 dependency-cruiser 這類依賴規則工具（宣告「A 模組不得依賴 B」，違規即紅）；規則 4 是型別檢查天然覆蓋；規則 5 是 lockfile 差異偵測。全部進 `verify:arch`，違規擋合併——**這是防「AI 加速架構飄移」最便宜的一道閘**。

**量測層 2（模型判）：code review 抓機器判不了的偏離。** AI review 在步驟 6 對照兩份文件問三個問題：

1. 這個 diff 有沒有**偏離 ARCHITECTURE.md 的意圖**（規則沒違反、但精神歪了，例如在設定檔外另開一條後門式設定）？
2. 有沒有**過度設計**（需求卡沒要的抽象層、預留的「以後可能用到」）？
3. 有沒有**誤解需求**（做出來的和三句驗收第一句對不上）？

這三項正是 2026 年 harness 研究公認「自動感測器最抓不到」的三種錯，所以明定為 review 的必問清單，且 R2/R3 必有人終審（照 `00_context/05` 的 Code Review L1–L3 分級）。

### 5.4 UI/UX 落差：Agent E2E 三件套

「期望的畫面體驗」要先變成可比對的目標，才有落差可言。三件套各管一段：

**件套 1：腳本化 E2E——功能與非功能的斷言（可重複、進 CI）。** 用 Playwright 之類寫固定腳本，紅綠明確。第一版清單：

1. 首頁完整載入＋計時（對 §5.2 預算）
2. 全程 console 零錯誤
3. 三寬度（375/768/1280px）各開一次：無橫向捲軸、導覽可點
4. 資源列表頁：每筆資源渲染出「為什麼推薦」欄位（差異化核心，值得一條斷言）
5. skill 卡頁：安裝指令複製鈕存在且內容非空
6. 全站站內連結無 404
7. MCP 場景端對端：腳本模擬 client 跑完「查詢→帶出處回覆→取得安裝指令」（判準 2 的自動預演）

**件套 2：畫面比對（visual regression）——「長得跟定稿一樣嗎」。** 設計定稿後，把關鍵頁在三寬度的截圖存成**基準圖**進 repo；之後每次改動自動重截、逐像素比對，差異超過門檻即紅。這把「期望的樣子」變成機器可比對的目標——Agent 改樣式不小心弄壞別頁的排版，這道閘會抓到腳本斷言漏掉的破版。基準圖的更新本身視為一次「改目標」，必經 Eric 確認（不然 Agent 可以用「更新基準」自我過關）。

**件套 3：Agent 當合成使用者——體驗檢查表走一遍。** Agent 用瀏覽器控制工具（Playwright MCP、Claude Code 的 Chrome 整合）**實際操作**自己剛改的站，照固定檢查表逐項評「通過／不通過／不確定」，每項附截圖證據＋一句理由。檢查表從需求 1 與差異化論述（v0.2 §8.1）翻成可操作的問題，第一版：

1. 打開首頁 3 秒內，說得出這站是做什麼的嗎？
2. 隨機抽三筆資源，都看得到「為什麼推薦／什麼情境用」嗎？
3. 抽一張 skill 卡，安裝指令一鍵複製成功嗎？
4. 手機寬度下，不橫向捲動能完成上面三件事嗎？
5. 開一個不存在的網址，有合理的「找不到」頁嗎？
6. 從任一頁，三次點擊內回得到首頁嗎？

2026 年的研究支持這種做法（模型評審與人類評審一致率約 85%，且「實際操作＋觀察狀態變化」比只看截圖可靠），但也明確警告模型評審的偏誤（自我美化、把「流暢」誤當「好」）。所以界線維持 v1 的鐵律並升級表述：

> **件套 3 的產出是「證據＋初評」，不是判決。**「不通過」與「不確定」項連同截圖一律交 Eric；連「全部通過」也只代表「初篩沒抓到問題」，主觀終判（舒服、一眼 get、繁中閱讀節奏）永遠是 Eric 的人工項。Agent 不得以任何檢查結果自我宣告「體驗通過」。

## 6. AGENTS.md 驗證區塊草稿（未來 team-agent-hub repo 用）

```markdown
## 驗證命令
- 每次修改後：`npm run verify:fast`（lint＋型別＋單元＋架構靜態規則；全綠＝通過，目標 10 秒內）
- 合併前：`npm run verify:full`＋`npm run verify:arch`＋`npm run verify:e2e`
- UI 有變動：畫面比對須綠（基準圖更新必經 Eric 確認）＋跑體驗檢查表附截圖進任務記錄

## 停止規則
1. 同一測試連修 3 次仍紅 → 停止，輸出「試了什麼／為何失敗／卡在哪」交還給人
2. 禁止為過關而弱化驗證：刪測試、放寬斷言、跳過案例、擅自更新畫面基準圖都算違規
3. 碰到以下部位 → 暫停等人確認：MCP 工具介面與權限（R3）／寫入 API 與認證（R3）／
   DB schema（R2 起跳）／部署與 IaC（R3）／ARCHITECTURE.md 本身
4. 要動需求卡範圍外的東西（新依賴、別的模組、既有介面）→ 先停下來問
5. 主觀體驗與架構意圖不自我宣告通過：只交證據、初評與「不確定」清單給人判

## 需求卡模板（loop 規格五要素）
- 觸發：這張卡因何而開（誤差來源：哪個量測器紅了／誰提的需求）
- 目標：成功長什麼樣（三句驗收第一句）
- 驗證：怎麼驗證（第二句→對應哪些測試／檢查表項）
- 停止規則：本卡特有的煞車（預設沿用上面五條）
- 記錄：改了什麼、跑了什麼、結果如何，寫進任務記錄
```

---

## 7. 外圈：修鷹架，不是修 code

每完成一輪開發（幾張需求卡合併後），花 30 分鐘結構化檢討，材料就是 loop 自己留下的記錄：

1. **收集**：停止規則觸發幾次、各哪條？哪個量測器紅最多？AI review 三問各抓到（或漏掉）什麼？Agent 哪裡誤解需求卡？
2. **歸因**：code 的問題（內圈已修）還是**鷹架的問題**？判斷口訣：**同一種錯出現第二次＝鷹架問題**。
3. **修鷹架**：對症下藥——文件不清→補 AGENTS.md 一句話；量測有洞→加一條測試或檢查表項；規則太緊／太鬆→調重試預算或門檻；架構規則缺角→補 ARCHITECTURE.md 一條＋對應體檢測試。
4. **沉澱**：過程記進 casebook（v0.2 判準 4）；重複出現的做法抽成部門 repo 的 skill。
