# 外部案例研究 — 原始整理（2026-07-28）

> 支撐 `20260728_AgentHub_系統構想_v0.1.md` §7 的完整研究記錄。
> 研究方式：網路搜尋＋抽查驗證（實際開啟確認的連結標註「已抽查」：anthropics/skills、gitmcp.io、Anthropic 內部使用報告、MCP Registry 官方公告）。

## 類別 1：Internal Developer Portal

**Spotify Backstage**｜https://backstage.io ｜CNCF 開源的內部開發者入口框架，3,400+ 組織採用。
- 關鍵機制：(a) Software Catalog——以 `catalog-info.yaml` 放在各 repo 內宣告實體（服務/API/文件），portal 聚合成單一目錄；(b) TechDocs——docs-as-code，Markdown 跟著程式碼走，portal 內用 MkDocs 渲染集中呈現；(c) Scaffolder 樣板——表單式自助建立新專案；(d) 插件架構（200+ 社群插件），不 fork 核心即可擴充。
- 借鏡：「metadata 跟著 repo 走、portal 只做聚合」可直接套用到 skills/案例的登錄；TechDocs 證明文件與程式同源可規模化。
- 侷限：React/Node 重型應用，需專職平台團隊維運；核心資料模型是「服務目錄」不是「知識/技能資產」；對 60 人部門明顯過重。
- 延伸：[TechDocs Architecture](https://backstage.io/docs/features/techdocs/architecture/)、[Roadie Backstage Guide](https://roadie.io/backstage-spotify/)

**Port**｜https://www.port.io ｜SaaS 型 IDP，主打彈性資料模型（blueprints）與自助操作。
- 關鍵機制：blueprint 可自訂任意實體 schema（不限於服務）；self-service actions 可接 API 觸發；scorecards 檢核合規。
- 借鏡：blueprint 思路適合建模非典型資產——「skill」「R0–R3」「Gate 狀態」都可以是一種實體型別。
- 侷限：商用 SaaS、企業定價；資料要餵進它的平台，與「repo 即真相」路線相斥。

**Cortex**｜https://www.cortex.io ｜SaaS 型 IDP，主打 scorecard 驅動的工程卓越管理。
- 關鍵機制：目錄+scorecards+workflows 一體；開箱即用的成熟度/合規追蹤；面向工程主管的儀表視角。
- 借鏡：用 scorecard 把治理規範變成「可視化狀態」而非文件牆——正對應 Gate A–E / L0–L4 的呈現方式。
- 侷限：以服務目錄為中心；self-service 彈性弱於 Port；SaaS 依賴。
- 比較文：[Port vs Cortex](https://www.port.io/compare/cortex-vs-port)、[Cortex vs Port](https://www.cortex.io/compare/cortex-vs-port)

## 類別 2：Agent Skills / Prompt 資產註冊表

**anthropics/skills（官方 Skills repo）**｜https://github.com/anthropics/skills ｜Anthropic 官方 Agent Skills 公開庫（已抽查）。
- 關鍵機制：(a) 每個 skill 是自包含資料夾 + `SKILL.md`（YAML frontmatter：name/description）；(b) repo 本身就是 Claude Code plugin marketplace——`/plugin marketplace add anthropics/skills` 後 `/plugin install document-skills@anthropic-agent-skills` 一鍵拉取；(c) 附 `spec/`（Agent Skills 開放規範）、`template/` 與 skill-creator skill；(d) 授權分層：多數 Apache 2.0，production 文件技能為 source-available。
- 借鏡：**最直接的可抄機制**——部門 repo 加 `.claude-plugin` 設定即可讓成員用 `/plugin install` 拉 skills，不必自建分發系統；spec + template + creator-skill 三件套降低投稿門檻。
- 侷限：純通用示範，無風險/治理 metadata、無使用追蹤、無審核流程。

**Agent Skills 開放規範（agentskills.io）**｜https://github.com/agentskills/agentskills ｜由 Anthropic 制定後開放的 skills 格式標準，已被多家 agent 產品採納。
- 關鍵機制：統一的 SKILL.md 格式規範，跨 Claude Code / Copilot / Codex CLI / Gemini CLI 等 20+ 平台可用。
- 借鏡：部門 skills 依此標準寫，未來不被單一工具綁死（部門同時有 Copilot 使用者時尤其重要）。
- 侷限：只是格式規範，不含分發、品質、治理。

**awesome-agent-skills 等收集庫**｜https://github.com/VoltAgent/awesome-agent-skills 、https://github.com/travisvn/awesome-claude-skills ｜社群策展清單，前者號稱 1000+ skills。
- 關鍵機制：分類目錄 + 連結；量大、更新快、零門檻收錄。
- 借鏡：分類法（文件處理/開發工具/資安等）可參考；更重要的是**反面教材**——證明「通用大雜燴」的問題，是差異化論述的現成對照組。
- 侷限：無品質把關、無情境貼合、無 tested 標記——正是部門 repo 要區隔的對象。

**Smithery.ai / mcp.so / PulseMCP（目錄型市集）**｜https://smithery.ai 、https://mcp.so 、https://www.pulsemcp.com ｜MCP server 的人類可瀏覽目錄/託管平台。
- 關鍵機制：每個 server 一頁，附各 client 的安裝設定片段；一鍵安裝 UX；部分提供託管。
- 借鏡：「資產詳情頁 + 複製即用的安裝指令」是好的呈現單位設計。
- 侷限：面向公網、以量取勝；彼此分散需重複發布（registry 碎片化問題）。

## 類別 3：MCP server 作為知識入口

**Context7（Upstash）**｜https://github.com/upstash/context7 ｜把最新版本文件變成 LLM 可查的 MCP server。
- 關鍵機制：(a) 兩段式工具設計：`resolve-library-id`（名稱→ID）→ `get-library-docs`（取文件）；(b) 支援 topic 聚焦與 token 上限控制；(c) 文件預先索引成 agent 易消化的片段。
- 借鏡：**「部門知識 MCP server」的工具介面範本**——先 resolve 再 fetch（帶 token 預算），比丟整份文件給 agent 有效。
- 侷限：服務公開函式庫文件；索引在其 SaaS 端，內部知識需自建同等 pipeline。

**GitMCP**｜https://gitmcp.io ｜https://github.com/idosal/git-mcp ｜零設定把任一 GitHub repo 變成遠端 MCP server（已抽查）。
- 關鍵機制：(a) URL 換域名即用（`github.com/u/r` → `gitmcp.io/u/r`）；(b) 優先讀 `llms.txt`，退回 README/docs；(c) 提供文件搜尋 + 原始碼搜尋工具；(d) 開源、可自架到內網。
- 借鏡：部門 repo 只要維護好 `llms.txt`＋結構化 docs，自架一套就能讓所有成員的 agent 直接查部門知識——成本最低的「docs-as-MCP」路徑。
- 侷限：託管版僅限公開 repo（內部要自架）；查詢品質完全取決於文件結構好壞。

**官方 MCP Registry**｜https://registry.modelcontextprotocol.io ｜https://blog.modelcontextprotocol.io/posts/2025-09-08-mcp-registry-preview/ ｜MCP server 的官方開放目錄與 API 標準（已抽查），由 Anthropic/GitHub/Microsoft/PulseMCP 等共同支持。
- 關鍵機制：(a) 機器可讀的 OpenAPI 規格；(b) **私有子 registry 模式**——企業沿用公共 API schema 建自己的核准清單，工具鏈通用；(c) 下游聚合器（Smithery 等）從中央 registry 拉取再加工。
- 借鏡：部門若要做「核准的 MCP server 清單」，直接採官方 schema 建私有子 registry，相容性最好。
- 侷限：仍屬 preview 成熟度；管 metadata 不管內容品質。

**langchain-ai/mcpdoc**｜https://github.com/langchain-ai/mcpdoc ｜極簡方案：把 llms.txt 清單餵給 IDE 的 MCP server。
- 借鏡：驗證概念用的最小可行版本，一個下午可跑起來。
- 侷限：功能陽春，無搜尋排序。

## 類別 4：Docs-as-code / 知識平台

**GitLab Handbook**｜https://handbook.gitlab.com ｜handbook-first 文化的標竿：2,000+ 頁公開手冊，公司運作的單一真相源。
- 關鍵機制：(a) Hugo + GitLab Pages 靜態產出；(b) 所有修改走 MR——改制度與改程式同一條貢獻流；(c) 「先寫進 handbook 再執行」的文化規範。
- 借鏡：**貢獻流設計**是精髓——部門規範用 PR 修訂，agent 也能發 PR 投稿案例；「handbook-first」是對抗知識散落聊天室的解法。
- 侷限：規模養護成本高（有專職團隊）；純靜態、原生無 agent 互通。
- 延伸：[Handbook Development](https://handbook.gitlab.com/docs/development/)

**Docusaurus / Astro Starlight / MkDocs Material（SSG 選型）**｜https://docusaurus.io ｜https://starlight.astro.build ｜https://squidfunk.github.io/mkdocs-material/
- 關鍵機制：Docusaurus——React/MDX 可嵌互動元件（例如「R0–R3 風險判定決策樹」小工具）、版本化；Starlight——Astro 底、輕量快速，已有企業拿來做帶登入的內部手冊；MkDocs Material——純 Markdown 最低摩擦，且是 Backstage TechDocs 的底層（留了未來升級 Backstage 的相容路徑）。
- 借鏡：60 人規模首選輕量 SSG＋內網部署；MkDocs Material 的「未來可被 TechDocs 吃掉」是隱藏優勢。
- 侷限：皆為「給人看」的單介面，agent 互通要另外補（llms.txt / MCP）。

**incident.io「The practical guide to incident management」**｜https://incident.io/guide ｜廠商出品但高品質的公開 playbook。
- 關鍵機制：有立場的方法論敘事（原則→實務→案例），不是資源連結堆；免費公開反哺品牌。
- 借鏡：**playbook 的寫法範本**——「任務交辦與驗收」「Gate A–E」適合這種敘事結構，而非條列規章。
- 侷限：單一領域；行銷動機使某些主張偏產品。

**Monzo 工程平台（含 Stripe 對照）**｜https://monzo.com/blog/topic/technology ｜https://newsletter.pragmaticengineer.com/p/stripe-part-2 ｜「有主見的鋪好路」(paved road) 內部平台的公開敘事。
- 關鍵機制：Monzo——高度統一的技術棧＋內部工具（如 Shipper 自動化受監理環境的變更管理）、DevEx 團隊叫 Developer Velocity；Stripe——大量自研內部工具（Sail、Trailhead、Compass 等）與 API review 文化。
- 借鏡：平台價值來自「限縮選擇＋把正確路徑做到最順」，不是提供所有選項。
- 侷限：只能透過部落格/報導窺見，無法直接取用其實作。

## 類別 5：企業內部 AI Coding Enablement

**How Anthropic teams use Claude Code**｜https://claude.com/blog/how-anthropic-teams-use-claude-code ｜Anthropic 十個內部團隊的第一手用法報告（已抽查）。
- 關鍵機制：(a) **各團隊維護共享 skills registry**，新人直接繼承最佳實踐；(b) 資安團隊讓 Claude 把多來源文件整併成 markdown runbook；(c) 知識透過 MCP + CLAUDE.md 變成「人人可及的格式」；(d) 新人 onboarding 直接用 Claude Code 讀 CLAUDE.md 導覽 codebase。
- 借鏡：與本構想幾乎同構——「team skills registry + CLAUDE.md + MCP 知識入口」就是 Anthropic 自己的內部做法，可直接引用作為說服素材。
- 侷限：廠商第一方敘事，無失敗案例與治理細節（風險分層、審核付之闕如）。

**Claude Code Best Practices（官方）**｜https://code.claude.com/docs/en/best-practices ｜官方最佳實踐文件，涵蓋 CLAUDE.md / Hooks / Skills / Plugins / Managed Agents 的擴充模式。
- 借鏡：平台的「工作流章節」可對映此結構撰寫，降低與官方語彙的落差。
- 侷限：通用層次，不含企業治理。

**Rakuten 案例**｜https://claude.com/customers/rakuten ｜https://rakuten.today/blog/rakuten-accelerates-development-with-claude-code%EF%BF%BC.html ｜日本大型企業全公司「AI-nization」推動案例。
- 關鍵機制：高層戰略定調→工程先行→擴散到各業務職能；公開量化指標（新功能上市時間 24 天→5 天、7 小時自主重構）。
- 借鏡：用可量測指標說服組織的敘事方式；「先在工程部門做出實績再外擴」與「一人彙整→分享」的節奏同構。
- 侷限：數字經行銷過濾；未公開內部平台/治理細節。TELUS 亦有公開採用數據（號稱省 50 萬小時）可作補充引用。

**claude-code-ultimate-guide（社群）**｜https://github.com/FlorianBruniaux/claude-code-ultimate-guide ｜社群彙整的超大型 Claude Code 指南（430K+ 行）。
- 借鏡：目錄結構與「production-ready template」的打包方式可參考；同時是「大而全≠有用」的另一個對照組。
- 侷限：無情境、無把關，維護靠個人熱情。

## 跨案例的共同模式

1. **Repo 即真相，網站只是視圖**：Backstage 的 catalog-info.yaml、anthropics/skills 的 marketplace、GitLab handbook 全都把 git repo 當單一真相源，網站/portal 是渲染層。
2. **標準格式是互通的前提**：SKILL.md（agentskills 規範）、`llms.txt`、MCP registry OpenAPI schema——採用開放標準就免費獲得整個工具鏈生態，自創格式等於自建孤島。
3. **雙介面（人＋agent）正在成為標配**：同一份內容同時供人瀏覽（靜態站）與供 agent 查詢（MCP / llms.txt）。Context7 與 GitMCP 證明後者可以極低成本自動化。
4. **分發用既有機制，不自建**：`/plugin marketplace add <部門repo>` 就能讓成員拉 skills；私有 MCP 子 registry 沿用官方 schema。成功案例都搭便車於工具原生機制。
5. **治理呈現為 metadata 與 scorecard，不是文件牆**：把「這個 skill 是 R2、過了 Gate C、tested by 某人」做成可過濾的結構化欄位，比長篇規章有效。
6. **有立場的 playbook 才能與 awesome list 區隔**：incident.io、Monzo、GitLab 的共同點是「取捨明確的敘事＋真實案例」；通用收集庫反而示範了無策展的天花板。
7. **貢獻流與程式碼同一條路**：GitLab 的 MR-first、Backstage 的 docs 隨 repo——投稿案例/修訂規範都走 PR，agent 也能代發 PR。
8. **輕重分層、由小做起**：靜態站＋部門 git repo＋一個自架 GitMCP 級 MCP server ≈ 覆蓋 80% 需求，一人可維護；Backstage/Port/Cortex 級平台需專職團隊，列為「被驗證後才升級」的遠期選項。
