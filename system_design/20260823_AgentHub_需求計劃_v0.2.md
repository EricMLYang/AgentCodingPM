# 部門 Agent Hub — 需求計劃 v0.2

> **文件狀態**：需求定案版（2026-08-23，取代 2026-07-28 的系統構想 v0.1）
> **文件範圍**：只談「要做什麼、為誰、做到什麼程度」，不談技術實作。技術規格與開發計劃是需求定稿後的下一步。
> **v0.1 去哪了**：v0.1 走「純靜態網站＋唯讀 MCP、沒有資料庫」路線，方向已修訂，原檔刪除（git 歷史可回溯）；仍然成立的內容已整併進本文件 §8。

---

## 1. 一句話定位

一個放**部門獨特資訊**的網站：我們自己策展的文章、skills、外部專案等資源——
人可以舒服地看、同事的 coding agent 可以直接查；
Eric 用自己的 coding agent 維護內容；
系統本身也全程用 agent 開發、持續精進。

---

## 2. 四大需求（2026-08-23 討論定案）

### 需求 1：觀看體驗很好的部門資訊站

- 內容：建議的新聞／文章、收藏的 skills、外部 repo 與專案、流程資訊、技術分享。
- 重點不是「多」，是**帶部門觀點的策展**：每筆資源都講清楚「我們為什麼推薦、什麼情境用」，讓同事一眼 get 到我們要的東西——這是與外部 awesome list 的根本區隔。
- 觀看體驗是第一優先：乾淨、快、繁中閱讀舒服、手機也能看。

### 需求 2：Eric 用自己的 coding agent 維護內容

- 新增、修改、下架內容，都是 Eric 對自己的 agent 講一句話就完成，不用開網頁後台慢慢填表單。
- 每筆修改留下記錄（誰、何時、改了什麼），可回溯。

### 需求 3：同事的地端 agent 能取得高共識資源

同事把自己的 coding agent（Claude Code 等）接上部門的 MCP 之後：

- 問「部門有沒有處理 X 的建議做法／skill」→ agent 直接拿到**帶出處**的答案；
- 想用某個 skill（含外部專案的 skills）→ agent 拿到安裝指令，**輕易就裝進自己的工具**；
- 查不到的就明說查不到，不拿一般知識充數——回答代表「部門共識」，不是模型自由發揮。

### 需求 4：網站本身用 agent loop 持續精進

- 這個系統的開發與後續改版，全程用 agent coding 進行，照部門自己的風險分層（R0–R3）與品質門檻（Gate A–E）走——做系統的過程就是部門建議流程的親身示範，成果進 casebook。
- 系統要為「未來每次都由 agent 迭代」而設計：文件、測試、驗證方式齊備，任何一次 agent session 都能安全接手改進。

---

## 3. 方向決定（討論過程已拍板的四條）

1. **系統自己保存內容**：文章與資源目錄存在系統的資料庫裡，透過 MCP 編輯即時生效。這是對 v0.1「內容 git repo 是唯一真相」原則的**正式修訂**。
2. **skills 檔案本體不進系統**：skill 的實際檔案留在原本的 git repo（部門 repo 或外部專案），安裝走 Claude Code 原生機制（plugin marketplace）；系統只保存「目錄卡」——介紹、部門觀點、狀態、安裝指令。理由：發佈通道搭原生便車零成本，也避免「系統直接餵可執行內容給大家的 agent」的資安疑慮。
3. **寫入權第一版只有 Eric**：同事全部唯讀；多管理者等部門正式採用再開。
4. **先本機／內網跑通**：AWS VM 部署做好準備（打包與部署文件），實際部署另開任務、照部門 R3 紀律走。
5. **通用產品定位，定名 `team-agent-hub`**（2026-08-23 定案）：這不是只給我們部門的專案，而是**任何團隊都能架一套的產品**——部門識別（網站標題、團隊名、色系）一律做成設定檔，不寫死在程式裡；別的部門 clone 之後改幾行設定、放自己的內容，就是「他們的站」。我們部門跑的這套只是第一個實例。Repo 簡介（tagline）：*Self-hosted info hub for your team — humans browse it, coding agents query and edit it via MCP.*

## 4. 角色與使用場景

| 角色 | 能做什麼 |
|------|---------|
| Eric（維護者） | 透過自己的 agent 新增／修改／下架內容；查看修改記錄 |
| 部門同事（瀏覽者） | 逛網站看文章與資源；複製安裝指令拿走 skill |
| 部門同事的 agent | 接 MCP 查詢部門共識資源；引導使用者安裝 skill |
| 未來的開發 agent | 依系統內建的文件與驗證方式，安全地迭代系統本身 |

代表場景三則：

1. Eric 看到一篇好文章 → 跟 agent 說「加進 Hub，分類新聞，備註為什麼值得看」→ 幾秒後網站上線。
2. 同事的 agent 被問到「跨服務 schema 要怎麼改」→ 查部門 MCP → 回覆部門建議做法＋相關 skill 安裝指令＋出處。
3. 想改進網站某頁 → 開一個 agent session → 讀系統自帶說明 → 改完跑驗證 → 過了才合併。

---

## 5. 第一版成功判準

1. 同事拿到連結後，**30 分鐘內看懂這站有什麼、並拿走至少一個資源**（裝起一個 skill 或收下一篇文章）。
2. **MCP 場景跑通**：至少一位同事的 agent 接上後，完成「查詢 → 拿到帶出處的答案 → 安裝一個 skill」全程。
3. Eric 日常維護**全程不開後台**：用 agent 講話就能上架與修改，且有修改記錄。
4. 開發過程整理出至少一則 casebook 案例（情境／做法／結果／學到什麼）。

---

## 6. 第一版明確不做

- 帳密登入、多角色權限（靠內網＋唯讀為主先擋）
- 留言、按讚、瀏覽統計等互動功能
- A×R 授權矩陣互動頁（等內容與制度成熟再加，見 §8.3 未來想像）
- 同事投稿流程（先單一維護者）
- 實際部署 AWS（準備好但另開任務）
- 與部門內容 repo 的自動同步（需要的內容用手動匯入）

## 7. 與既有計劃的關係

- 本 repo（AgentCodingPM）仍是 PM 工作室；系統程式碼先在此孵化，未來與 `system_design/` 一起移出成獨立 repo，名稱定為 **`team-agent-hub`**（見 §3.5 通用產品定位）。
- 主線「一人彙整部門 repo」不變：本系統是分享的放大器，開發過程直接生產 casebook 案例，是對主線的貢獻而非偏離。
- 開發紀律沿用部門自己的 R0–R3 與 Gate 門檻（`00_context/05`），對外就說「這個站就是照我們建議的流程做出來的」。

## 8. 從 v0.1 保留的資產（整併，資訊不遺失）

### 8.1 差異化論述：為什麼外部資源站取代不了它

| # | 差異化 | 外部資源站 | 部門 Agent Hub |
|---|--------|-----------|----------------|
| 1 | 情境貼合 | 通用內容，不知道你的技術棧與風險邊界 | 資源可掛部門座標（能力 A0–A4、風險 R0–R3），給「在我們部門該怎麼做」的答案 |
| 2 | 先審後收 | 上千個 skill 良莠不齊，品質自負 | 每筆資產有 owner、`draft / tested / shared / deprecated` 生命週期、最後驗證日；標 `tested` 就代表真的被用過 |
| 3 | 真實案例＋結果 | 多是 demo 與教學，少有「後來怎麼了」 | casebook 記錄真實任務的情境、做法、**結果**，失敗也照寫 |
| 4 | 拿了就能用 | 看完文章還要自己搬 | 每個 skill 附一鍵複製的安裝指令，30 秒進自己的工具 |
| 5 | 接進工作流 | 網站是網站、工作是工作 | MCP 讓 agent 在寫 code 當下就查得到部門共識 |

### 8.2 MCP 鐵律（沿用不變）

- 回答必須引用系統內版本化的內容並帶出處；查不到就說查不到。
- 唯讀開放、寫入嚴格管制（v1 僅 Eric）。
- MCP server 本身視為攻擊面：最小權限、不碰 secret、內網部署，比照部門 Gate B 把自己當第三方依賴審。

### 8.3 未來想像（都不在第一版）

- 週報 bot：偵測內容變更，自動摘要「本週新增／更新了什麼」推到部門頻道。
- A×R 授權矩陣互動頁：選「我的能力」＋「任務風險」→ 給出 AI 可放手程度與該守的門檻。
- Defective AI PR 練習場：評鑑素材掛上網站，點了直接開練習環境（等部門採用評鑑制度）。
- 使用回饋迴路：skill 安裝數、MCP 查詢熱點，回頭指引維護優先序。
- 跨工具 adapter：同一份資產自動輸出成 Claude Code / Codex / Copilot 各自的格式。
