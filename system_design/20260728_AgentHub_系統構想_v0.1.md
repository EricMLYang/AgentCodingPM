# 部門 Agent Hub — 系統構想 v0.1

> **文件狀態**：Concept Draft v0.1（2026-07-28）
> **系統暫名**：部門 Agent Hub（工作代號 `agent-hub`，正式名稱待定）
> **與現有計劃的關係**：見 §1.2，先把話說清楚
> **本文件用途**：系統設計規格的第一份構想，供後續拆解成正式規格與開發任務

---

## 1. 一句話定位

> 把部門 Agent Engineering 參考 repo（內容資產）做成一個**看得到、拿得走、接得上**的系統：
> 網站呈現我們認為重要的資訊、skills、流程；同事的 coding agent 可以透過 MCP 直接查詢與取用；
> 而這個系統本身就用 agent coding 開發，開發過程照我們自己的 R0–R3 / Gate 紀律走，做完就是 casebook 的下一個真實案例。

三個關鍵詞：

- **看得到**：不是又一個 awesome list，是「在我們部門、你這個角色、這個風險等級下，該怎麼做」的答案。
- **拿得走**：每個 skill 附一行安裝指令，30 秒進到自己的 Claude Code / Codex。
- **接得上**：提供 MCP server，讓每個人的 agent 在工作當下就能查部門的矩陣、規範、案例，不用切出來翻文件。

### 1.2 跟現有計劃的關係（先把衝突攤開）

`new_plan/20260711_Repo彙整執行計劃.md` §7 明確寫了「❌ 網站 / Dashboard / Matrix 呈現層」暫不做。本構想**不推翻**那個判斷，而是這樣接：

1. **彙整清單仍是主線**：models / casebook / assets / content 的彙整優先，內容不夠好，系統做出來也是空殼（構想檔 §13.5 的「Renderer 先行、內容空洞」風險）。
2. **本系統是「分享」那一步的放大器**：執行計劃 §6 說夠好之後「有人問就給連結」——給的連結如果是一個 30 分鐘能逛完、能直接拿走 skill 的網站，說服力遠大於一個 raw repo。
3. **開發本身就是主線的素材**：這個系統用 agent coding 開發，全程照部門自己的紀律走，做完就是 casebook 第二、三案。做系統不是偏離彙整，是**用做系統來生產案例**。
4. **設計先行、開發挑時機**：本文件先把設計規格做扎實；動工時間點建議在彙整清單第 1–4 項（skeleton / models / casebook 第一案 / assets 第一批）完成之後，或以極小步並行。

一句話：**內容 repo 是唯一真相，系統只是它的呈現與互通層**——這是構想檔原則 3.4（資料與呈現解耦）的直接延伸，不是新立場。

## 2. 為什麼要做，以及跟外部資源站的區隔

外部已經有一大堆 awesome-claude-code、skills 收集庫、MCP registry、教學網站。我們再做一個的理由，必須建立在它們**做不到**的事情上：

| # | 差異化 | 外部資源站 | 部門 Agent Hub |
|---|--------|-----------|----------------|
| 1 | **情境貼合** | 通用內容，不知道你的技術棧與風險邊界 | 每個資源都掛在 A0–A4 × R0–R3 座標上：「你是 A2、這任務 R1，可以交辦到 PR、人工 merge」 |
| 2 | **先審後收** | 上千個 skill 良莠不齊，品質自負 | 每筆資產有 owner、`draft / tested / shared / deprecated` 生命週期、`last_verified` 日期；標 `tested` 就代表真的被用過 |
| 3 | **真實案例＋結果** | 多是 demo 與教學，少有「後來怎麼了」 | casebook 記錄真實任務的情境、做法、**結果**（對方採納沒、修了沒），失敗也照寫 |
| 4 | **拿了就能用** | 看完文章還要自己搬 | 每個 skill 一行指令裝進自己的 agent；流程附 checklist 與範本 |
| 5 | **接進工作流** | 網站是網站、工作是工作 | MCP server 讓 agent 在寫 code 當下就查得到部門規範，規範從「牆上的告示」變成「工具箱裡的工具」 |

核心論點沿用構想檔 §14 的結論：外部沒有任何單一專案完整解決「**個人能力 × 專業領域 × 任務風險 × 驗證能力 → 自動化授權建議**」這個交集。這個交集就是我們系統的靈魂功能，也是所有頁面與 API 的中心。

## 3. 系統全貌：三層架構

沿用構想檔 §6 的「資料與呈現解耦」，具體化成三層：

```text
┌─ 第一層：內容 Repo（唯一真相）────────────────────┐
│  department-agent-engineering（獨立 git repo）      │
│  models/（A0–A4、R0–R3、A×R 矩陣）                  │
│  content/（知識內容，自 00_context 遷入）            │
│  assets/（skills，相容 anthropics/skills 格式）      │
│  registry.yaml（資產清單與狀態）                     │
│  casebook/（真實案例）                              │
└────────────────┬───────────────────────────────┘
                 │ git push 觸發
┌─ 第二層：建置管線（CI）───────────────────────────┐
│  1. Schema 驗證：registry.yaml 欄位齊不齊、          │
│     連結會不會斷、`tested` 有沒有對應驗證記錄        │
│  2. 產靜態網站（Markdown → 頁面）                    │
│  3. 產機器可讀索引（JSON：資產目錄、矩陣、案例索引） │
└────────────────┬───────────────────────────────┘
                 │ 同一份資料，餵給不同消費端
┌─ 第三層：消費端（可以各自演進、各自替換）──────────┐
│  A. Web Portal    — 靜態網站，人看的                 │
│  B. MCP Server    — agent 查的（讀 JSON 索引）        │
│  C. 安裝通道      — skill 一行指令拉進本機            │
│  D.（未來）Dashboard / IDE extension / Bot           │
└────────────────────────────────────────────────┘
```

設計鐵律：

1. **網站與 MCP 永遠不自己養內容**——所有內容改動走內容 repo 的 PR，系統只負責呈現。
2. **同一個 ID 貫穿全部**——資產 id（如 `ai-security-review`）在網頁 URL、MCP 回覆、安裝指令中一致，引用時可以指到特定版本。
3. **每個消費端都可以整個換掉**而不動內容——今天用靜態網站，明天換框架，內容零成本遷移。

## 4. 功能構想（人用的部分：Web Portal）

第一版只做五個頁面，每一頁都對應「同事 30 分鐘看懂並拿走一個 skill」這個既有判準：

### 4.1 首頁：30 分鐘導覽

執行計劃 §4 設計的 README 動線直接搬上網：**看懂分級 → 在矩陣找到自己 → 拿走一個 skill → 讀完一個案例**。首頁就是這四步的流程圖，各連到對應頁面。

### 4.2 A×R 授權矩陣（互動版，靈魂頁面）

- 5×4 的格子（A0–A4 × R0–R3），點任一格顯示：這一格的白話說明、適用的 Gate 要求、推薦 skills、相關案例。
- 附兩個下拉選單的「自我定位」：選「我的能力大概是…」＋「這個任務是…」→ 直接給出「AI 可以放手到什麼程度」與該遵守的門檻。
- 這頁是外部任何資源站都沒有的東西，也是 demo 給部門看的第一畫面。

### 4.3 資產目錄（skills / flows / templates）

每筆資產一張卡片，欄位直接來自 `registry.yaml`：用途、owner、狀態、版本、適用風險（allowed_risk）、最低能力（min_level）、禁止行為、最後驗證日、已知限制。卡片上有**一鍵複製的安裝指令**。可依角色、風險、狀態篩選。

### 4.4 Casebook（真實案例）

每案固定格式：情境 → 做法 → 結果 → 學到什麼。第一案就是 AI 資安 Review V1→V2。案例會反向連結它用到的 skills 與對應的矩陣格子。

### 4.5 知識庫（content/）

`00_context` 七檔遷入後的呈現，附全文搜尋。不做花俏功能，重點是每篇的 TL;DR 與 status / last_review 標頭要顯眼——過期內容自動標示，呼應「資產有生命週期」原則。

> 明確不做（第一版）：登入與個人化、留言、按讚排行、學習進度追蹤、能力評鑑。凡是「對人的制度」都等部門正式採用再說（沿用執行計劃 §7 的邊界）。

## 5. 互通與協作（agent 用的部分：MCP 與安裝通道）

這是「讓大家方便做很多有趣的事」的核心。MCP（Model Context Protocol）是 Anthropic 提出的開放標準，讓任何 AI agent 能以統一方式呼叫外部工具與資料——同事不管用 Claude Code、Codex 還是別的，接上我們的 MCP server 後，agent 就能直接查部門的知識。

### 5.1 MCP Server v1：唯讀查詢（四個工具就夠）

| 工具 | 輸入 | 回覆 |
|------|------|------|
| `lookup_authorization` | 我的能力等級＋任務描述 | 建議風險分級、AI 可放手程度、該過的 Gate、引用矩陣版本 |
| `search_assets` | 關鍵字／角色／風險 | 符合的 skills 清單＋狀態＋安裝指令 |
| `search_knowledge` | 問題 | 相關內容段落＋出處連結（含版本） |
| `find_cases` | 情境描述 | 相似的 casebook 案例摘要＋連結 |

介面設計參考 Context7 的兩段式模式：先「找到是哪份資源」再「帶 token 預算取內容」，避免一次把整份文件塞進 agent 的脈絡。另外有一條**第 0 版捷徑**：在內容 repo 維護 `llms.txt`（給 AI 讀的網站地圖），自架一套 GitMCP 就能先讓 agent 做泛用查詢——一個下午可跑起來，用它驗證「agent 查部門知識」的價值，再決定投入自製上表的四個工具（自製的價值在 `lookup_authorization` 這種矩陣邏輯，泛用工具做不到）。

鐵律（來自 `00_context/05` Gate B 與構想檔 §8.6）：

- **回答必須引用 repo 內版本化的內容**，不能只憑模型的一般知識回答；查不到就說查不到。
- **v1 全部唯讀**，沒有任何寫入工具。寫入（投稿案例、提報 skill）走 git PR，不走 MCP。
- MCP server 本身視為攻擊面：最小權限、不碰 secret、部署在內網。我們自己的 Gate B 明文寫著「MCP server 需納入供應鏈治理」——自己做的也一樣照辦。

### 5.2 有趣的使用場景（賣點示範）

```text
同事在自己的 Claude Code 裡：
「我要改一個跨服務的 event schema，幫我看部門規範怎麼說」
 → agent 呼叫 lookup_authorization
 → 「這屬於 R2（跨服務契約），依 Gate C 必須有契約測試證據，
    禁止 AI 產碼+AI review 直接 merge。相關 skill：contract-test-design（tested），
    安裝指令如下… 類似案例：casebook/xxx」
```

規範不再是「進 repo 前要先讀完的文件」，而是 agent 在動手當下主動撞到的護欄。

### 5.3 安裝通道：skill 一行指令拿走

- 資產維持 anthropics/skills 相容格式（`SKILL.md` + scripts），本來就能被 Claude Code 直接吃。
- **首選：plugin marketplace（搭原生便車，幾乎零開發）**——內容 repo 加上 `.claude-plugin` 設定後，它本身就是一個 marketplace：同事 `/plugin marketplace add <部門repo>` 一次，之後 `/plugin install <skill名>` 逐個拉取。anthropics/skills 官方 repo 就是這樣運作的，我們照抄機制、補上自己的治理欄位。
- 次選（跨工具時再做）：一支小安裝腳本，把 skill 資料夾拉到 Codex / Copilot 等其他工具的對應位置。
- 網站資產卡片上的「安裝指令」直接顯示上述指令，一鍵複製。

### 5.4 協作回路：投稿與回饋

- **投稿走 PR**：casebook 與 skill 的貢獻範本放在內容 repo 的 PR template，網站上「我要投稿」按鈕就是連到開 PR 的頁面。單一維護者時期由 Eric 審；未來部門採用，再啟用構想檔 §9 的 owner 制。
- **回饋極簡起步**：每頁腳放「這頁有用／有問題」連到 issue。不做留言系統。

## 6. 用 Agent Coding 開發本身（吃自己的狗糧）

這個系統的開發過程，本身就是部門紀律的示範場：

| 開發任務 | 風險自評 | 依循的紀律 |
|---------|---------|-----------|
| 靜態網站頁面、樣式、內容渲染 | R0–R1 | AI CR + CI lint/unit + 本人簽核即可，放手讓 agent 做 |
| 建置管線（CI）、schema 驗證 | R2（CI/CD 屬工具鏈） | 依 `00_context/05` 禁止事項：pipeline 設定不能 AI 產完直接上，人工逐段確認 |
| MCP server | R2（agent 工具面） | Gate B 全套：最小權限、白名單、不碰 secret、上線前做一次 prompt injection 自測 |
| 部署 | R3（IaC/部署從嚴） | 四重保護裡至少做到 dry-run＋具名簽核；用最簡單的靜態託管壓低這一項的面積 |

開發全程記錄：每完成一個里程碑，整理成 casebook 一案（情境／做法／結果／學到什麼）。**系統上線那天，casebook 至少多兩案**——這是本計劃對主線彙整工作的直接貢獻。

也用這個專案實測 `00_context/08` 的 Skill 工程方法：把「網站頁面開發」「MCP 工具開發」各做成一個 skill（六節結構＋Anti-Rationalization Table），邊做邊驗證，成熟後就是 assets/ 的新資產。

## 7. 類似目的的專案與案例（2026-07-28 研究，連結經抽查）

> 程式碼類專案的參考清單構想檔 §14 已有，本節聚焦「**系統／平台**」層面的同類案例。
> 五個類別各挑最有參考價值者；完整研究記錄可再展開成獨立檔。

### 7.1 內部開發者入口（Internal Developer Portal）

| 專案 | 定位 | 可借鏡 | 不適用處 |
|------|------|--------|---------|
| [Backstage](https://backstage.io)（Spotify／CNCF） | 開源內部開發者入口框架，3,400+ 組織採用 | **「metadata 跟著 repo 走、portal 只做聚合」**：各 repo 放一個 yaml 宣告自己，入口網站自動聚合成目錄——正是我們 registry.yaml 的放大版；TechDocs 證明「文件與程式同源」可規模化 | React/Node 重型應用，需專職團隊維運；核心模型是「服務目錄」不是「知識資產」；60 人部門明顯過重 |
| [Port](https://www.port.io)／[Cortex](https://www.cortex.io) | 商用 SaaS 型入口 | Port 的自訂實體模型（skill、風險等級都可以是一種實體）；Cortex 的 **scorecard**——把治理規範變成可視化狀態而非文件牆，正對應 Gate A–E 的呈現方式 | 商用定價；資料要餵進對方平台，與「repo 即真相」路線相斥 |

### 7.2 Skills 資產的格式與分發

| 專案 | 定位 | 可借鏡 | 不適用處 |
|------|------|--------|---------|
| [anthropics/skills](https://github.com/anthropics/skills) | Anthropic 官方 skills 庫 | **最直接可抄的分發機制**：repo 本身就是 plugin marketplace——`/plugin marketplace add <repo>` 之後 `/plugin install <skill>` 一鍵拉取，不必自建分發系統；spec + template + skill-creator 三件套降低投稿門檻 | 純通用示範：無風險／治理欄位、無審核流程——那正是我們要補的 |
| [Agent Skills 開放規範](https://github.com/agentskills/agentskills) | SKILL.md 格式標準，20+ 平台採納 | 照標準寫，同一份 skill 跨 Claude Code / Copilot / Codex 可用，不被單一工具綁死 | 只管格式，不管品質與分發 |
| [awesome-agent-skills](https://github.com/VoltAgent/awesome-agent-skills) 等收集庫 | 社群策展清單（1000+ skills） | 分類法可參考；更重要是**現成的反面對照組**——demo 時拿它對比「通用大雜燴 vs 部門情境貼合」 | 無把關、無 tested 標記——正是我們要區隔的對象 |

### 7.3 「文件變 MCP」的先例（§5 設計的直接依據）

| 專案 | 定位 | 可借鏡 | 不適用處 |
|------|------|--------|---------|
| [Context7](https://github.com/upstash/context7)（Upstash） | 把函式庫文件變成 agent 可查的 MCP server | **兩段式工具介面**：先 resolve（找到是哪份資源）→ 再 fetch（帶 token 預算取內容），比一次丟整份文件有效——我們的 `search_*` 工具照這個模式設計 | 索引在其雲端；內部知識要自建同等管線 |
| [GitMCP](https://gitmcp.io)（[開源](https://github.com/idosal/git-mcp)） | 零設定把任一 GitHub repo 變成 MCP server，可自架 | **成本最低的起步路徑**：內容 repo 維護好 `llms.txt`＋結構化文件，自架一套就能讓 agent 查部門知識——可當 §9 階段 4 之前的「第 0 版 MCP」 | 查詢品質完全取決於文件結構；沒有我們的授權矩陣邏輯 |
| [官方 MCP Registry](https://registry.modelcontextprotocol.io) | MCP server 的官方目錄與 API 標準 | 未來若要管「部門核准的 MCP server 清單」，直接沿用官方 schema 建**私有子 registry**，工具鏈相容性最好 | 尚屬早期；只管清單不管內容品質 |

### 7.4 Docs-as-code 知識平台的標竿

| 案例 | 定位 | 可借鏡 | 不適用處 |
|------|------|--------|---------|
| [GitLab Handbook](https://handbook.gitlab.com) | 2,000+ 頁公開手冊，公司運作的單一真相源 | **貢獻流設計**：改制度與改程式走同一條 PR 流；「先寫進 handbook 再執行」的文化——我們的投稿流程（§5.4）就是這個模式的縮小版 | 養護成本高（有專職團隊）；原生無 agent 互通 |
| [incident.io Guide](https://incident.io/guide) | 廠商出品的高品質公開 playbook | **有立場的寫法範本**：原則→實務→案例的敘事，不是資源連結堆——Gate A–E、任務交辦與驗收適合這樣寫 | 單一領域；帶行銷動機 |
| Monzo／Stripe 內部平台（公開報導） | 「有主見的鋪好路」內部平台 | 平台價值來自**限縮選擇＋把正確路徑做到最順**，不是提供所有選項——與好策略的取捨觀一致 | 只能從部落格窺見，無法直接取用 |

### 7.5 企業內部 AI Coding 推廣的平台化做法

| 案例 | 定位 | 可借鏡 | 不適用處 |
|------|------|--------|---------|
| [How Anthropic teams use Claude Code](https://claude.com/blog/how-anthropic-teams-use-claude-code) | Anthropic 十個內部團隊的第一手用法 | **與本構想幾乎同構**：各團隊維護共享 skills registry、知識用 MCP + CLAUDE.md 變成人人可及的格式、新人用 Claude Code 讀 CLAUDE.md 導覽——demo 時可直接引用「Anthropic 自己就是這樣做的」 | 第一方敘事；無失敗案例與治理細節 |
| [Rakuten 案例](https://claude.com/customers/rakuten) | 大型企業全公司推動 | 用可量測指標說服組織（上市時間 24 天→5 天）；「工程先做出實績再外擴」與我們「一人彙整→分享」節奏同構 | 數字經行銷過濾 |

### 7.6 跨案例共同模式（直接吸收進本設計）

1. **Repo 即真相，網站只是視圖**——Backstage、anthropics/skills、GitLab Handbook 全都如此。已是本設計鐵律（§3）。
2. **採用開放標準就免費獲得工具鏈生態**——SKILL.md 規範、llms.txt、MCP registry schema；自創格式等於自建孤島。
3. **雙介面（人＋agent）正在成為標配**——同一份內容同時供人瀏覽與供 agent 查詢，而且後者可以極低成本自動化。
4. **分發搭工具原生機制的便車，不自建**——plugin marketplace 一行設定勝過自寫 CLI（已據此修改 §5.3）。
5. **治理呈現為 metadata 與 scorecard，不是文件牆**——「這個 skill 是 R1、tested、誰驗的」做成可篩選欄位。
6. **有立場的 playbook 才能與 awesome list 區隔**——取捨明確的敘事＋真實案例是護城河；無策展的千件收集庫是天花板的示範。
7. **貢獻流與程式碼同一條路**——都走 PR，agent 也能代發 PR，天然支援「用 agent coding 開發平台本身」。
8. **輕重分層**——靜態站＋git repo＋一個輕量 MCP ≈ 覆蓋八成需求且一人可維護；Backstage 級平台列為「被驗證後才升級」的遠期選項。

## 8. 技術選型建議（第一版從最輕的做起）

| 項目 | 建議 | 理由 |
|------|------|------|
| 網站 | **Astro Starlight**（靜態文件網站框架） | 原生吃 Markdown、內建搜尋與側欄、輸出純靜態檔好部署好搬家；不用寫後端。備選 MkDocs Material：更樸素，但它是 Backstage TechDocs 的底層——若部門未來上 Backstage 級平台，內容可被直接收編（升級保險） |
| 全文搜尋 | Starlight 內建（Pagefind） | 零後端、零維運；語意搜尋等有真需求再加 |
| 機器索引 | CI 產 `registry.json` / `matrix.json` / `cases.json` | 網站與 MCP 共用同一份，避免兩套真相 |
| MCP server | TypeScript 官方 SDK，先 stdio 本機版 → 再內網 HTTP 版 | 先讓自己與少數人接上驗證價值，再考慮常駐服務 |
| 部署 | 內網靜態託管（或 GitHub Pages private）擇最簡單者 | 壓低 R3 部署面積；沒有資料庫、沒有使用者資料 |
| 身分驗證 | 第一版不自建，靠內網/私有 repo 隔離 | 沿用構想檔 §15：SSO 不在 v0.1 自建 |

原則：**每一項都選「可以被丟掉重來」的**。內容在 repo，網站與 MCP 都是消費端，選錯框架的代價被架構刻意壓到最低。

## 9. 分階段做法（比照執行計劃：清單制，做完一項算一項）

| # | 項目 | 內容 | 完成判準 | 預估 |
|---|------|------|---------|------|
| 0 | 前置 | 內容 repo 彙整清單 1–4 完成（skeleton / models / 案例一 / assets 一批） | 有東西可渲染 | （主線工作） |
| 1 | 網站 v0.1 | Starlight 起站：首頁導覽＋矩陣頁（先靜態）＋資產目錄＋casebook＋知識庫＋搜尋 | 同事給連結後 30 分鐘走完四步動線 | 2–3 天 |
| 2 | 機器索引 | CI 驗證 registry.yaml＋產 JSON 索引 | schema 錯誤會擋 build | 1 天 |
| 3 | 安裝通道 | skill 拉取腳本＋每張資產卡附指令 | 自己在乾淨環境 30 秒裝起一個 skill | 1 天 |
| 4 | MCP v1 | 四個唯讀工具，stdio 版 | 自己的 Claude Code 接上，§5.2 場景跑通且回答帶出處 | 2–3 天 |
| 5 | 矩陣互動化 | A×R 自我定位選單＋格子詳情 | demo 時 3 分鐘講完一個完整故事 | 1–2 天 |
| 6 | Casebook 補案 | 把 1–5 的開發過程整理成 1–2 個案例 | 案例有結果、不灌水 | 半天 |
| 7 | 小規模分享 | 給 2–3 位同事連結＋MCP 接法，收回饋 | 至少一人真的裝走一個 skill | — |

到第 7 項為止都是一人可完成、不需任何批准的桌面＋內網工作。之後（內網常駐 MCP、投稿流程、Dashboard）視回饋再開。

## 10. 風險與對策

| 風險 | 對策 |
|------|------|
| 網站先行、內容空洞（構想檔 §13.5） | 階段 0 是硬前置；網站只渲染已存在的內容，不為網站趕寫內容 |
| MCP 亂答、拿一般知識充數 | 工具設計上強制帶出處與版本；查不到就回「repo 沒有這條」；上線前用刁鑽問題自測 |
| MCP / 安裝腳本本身成為攻擊面 | 全唯讀起步、內網部署、不碰 secret；比照 Gate B 把自己當第三方依賴審 |
| 又變成沒人用的內部網站 | 判準綁死在「有人真的裝走 skill」與「agent 場景跑通」，不是頁面數；每次分享從真實案例開場 |
| 一人維運壓力 | 全靜態＋零資料庫的架構讓維運趨近於零；內容過期靠 last_verified 自動標示，不靠人記 |
| 與內容 repo 的邊界模糊 | 鐵律：系統 repo 裡不准出現任何知識內容；發現就搬回內容 repo |
