## 1. 一句話定位

> 我自己先彙整一個高品質的 Agent Engineering 參考 repo——
> **共同語言（能力與風險分級）＋ 可執行資產（skills）＋ 真實案例** 三層齊備——
> 做好之後分享給部門，讓內容品質自己說話。

## 2. 為什麼用這個角度執行

- 組織推動（選種子成員、培訓、評鑑、跨部協調）需要處長與另一部配合，時程不由我控制；彙整 repo 一個人就能做完。
- 分享的說服力來自「拿得出手的內容 + 真實案例」，不是推動計劃書。
- 構想最有原創價值的部分——**「個人能力 × 任務風險 → AI 可以放手到什麼程度」**——本來就是桌面工作可以直接寫出來的。

構想檔內容完整，本檔刻意只取三分之一：

| 構想檔中暫不啟用 | 本檔改用的輕量做法 |
|---|---|
| 12 個月 Phase 時間表、一圈圈推廣 | 彙整清單（§5），做完一項算一項，沒有時程壓力 |
| 對「人」的制度：評鑑、等級認定、委員會 | 對「內容」的治理：每筆資產標明誰寫的、驗證過沒、何時過期 |
| 網站 / Dashboard / Matrix 呈現層 | repo 本身就是介面，Coding Agent 直接讀 Markdown 回答問題 |

## 3. 共同語言：A0–A4 × R0–R3（repo 的核心資產）

> 權威定義：A0–A4 在構想檔 §4.3、R0–R3 在 `00_context/05`。本節是執行用的對照摘要，外加一張構想檔提到但尚未畫出的 A×R 授權矩陣草案。

### 3.1 個人 Agent 能力五級（A0–A4）摘要

| 等級 | 白話 | 一般自動化範圍 |
|---|---|---|
| A0 | 問 AI | 查詢、解釋、摘要、用草稿；唯讀 |
| A1 | 和 AI 一起做 | 小批次修改，逐步確認，理解每個改動 |
| A2 | 把明確任務交給 AI | 任務交辦到 PR，人工 merge / release |
| A3 | 設計 AI 做事的方法與閉環 | 受控的長時間執行、可重複的工作流 |
| A4 | 管理整套 Agent 工程制度 | 治理資產、政策與風險，不等於無限部署權 |

### 3.2 任務風險四級（R0–R3）摘要

| 風險 | 說明 | 例子 |
|---|---|---|
| R0 | 低風險、可逆、容易驗證 | 文件、格式、測試草稿、Prototype |
| R1 | 一般 Production 變更 | UI、一般 API、可逆 Refactor |
| R2 | 高影響或高權限變更 | Auth、Schema Migration、Production IaC、敏感資料 |
| R3 | 安全、法規或不可逆變更 | Safety Firmware、Signing Key、Production Delete |

### 3.3 A × R 授權矩陣（草案，先自己用）

「這個人能力到哪、這個任務風險多高」交叉出「AI 可以放手到什麼程度」：

| | R0 低風險可逆 | R1 一般變更 | R2 高影響 | R3 不可逆／安全 |
|---|---|---|---|---|
| **A0 問 AI** | 自由使用 | 只當參考 | 只當參考 | 不碰 |
| **A1 一起做** | 放手做 | 小步改、逐步確認 | 只當參考 | 不碰 |
| **A2 交辦任務** | 放手做 | 交辦到 PR，人工 merge | 小步改、逐步確認 | 只當參考 |
| **A3 設計流程** | 可自動化 | 受控流程，人工 merge | 人工審 + 獨立驗證 | 只當參考 |
| **A4 管理制度** | 可自動化 | 驗證充分者可評估 auto-merge | 人工審 + 獨立驗證 | 正式批准，永遠有具名負責人 |

原則不變：**能力高只代表能設計更複雜的自動化，不代表拿到高風險授權**；風險等級永遠可以壓住自動化程度。


```yaml
  type: skill
  owner: eric

  prohibited: [auto-fix, production-write]
```

## 5. 彙整清單（不是階段，做完一項算一項）

| # | 項目 | 內容 | 預估 |
|---|---|---|---|
| 1 | Repo skeleton | 建 repo、README、AGENTS.md、資料夾 | 半天 |
| 2 | models/ | A0–A4、R0–R3、A×R 矩陣、glossary（大半從 `00_context/03、05` 搬） | 1 天 |
| 3 | casebook 第一案 | 資安 Review V1→V2 整理成標準格式：情境／做法／結果／學到什麼 | 半天 |
| 4 | assets 第一批 | 資安 Review 流程 skill 化 + 自己日常在用且穩定的 2–3 個 skill | 1–2 天 |
| 5 | content/ | `00_context` 七檔分批遷入（2026-07-11 已先精簡去噪，可用零碎時間，每檔 ≤ 半天） | 陸續 |
| 6 | 案例持續補 | 之後每做完一件真實任務就補一筆 casebook | 持續 |

> **第 3 項的加分動作**：回頭問 4 月受測團隊，Critical 項目（無密碼登入、Token 可預測）修了沒。案例有「結果」才完整、分享時才有力；但這是加分項，**不擋**其他項目進度。

## 6. 什麼叫「夠好可以分享」

自我判準（全部做到才算）：

1. 一位沒接觸過的同事，**30 分鐘內**能：看懂分級、在 A×R 矩陣找到自己的位置、抓走一個能直接用的 skill、讀完一個真實案例。
2. 每個標 `tested` 的資產都真的被我用過；沒用過就誠實標 `draft`，不灌水。
3. 至少 2–3 個案例有**結果**（發生了什麼、對方採納沒），不是只有過程記錄。

分享方式，由輕到重：

1. 有人問就給連結，不辦發表會。
2. 部內找機會 demo 一次，用 casebook 的真實案例開場。
3. 反應好 → 才談「部門共同維護」，屆時再啟用構想檔的組織設計（Owner 制、生命週期、評鑑）。

## 9. 不變的核心原則（與構想檔一致）

1. **能力 ≠ 授權**：A×R 矩陣說了算，高能力不解鎖高風險。
2. **資料與呈現解耦**：Markdown / YAML 是唯一真相，任何介面都只是消費端。
3. **資產有生命週期**：`draft → tested → shared`，過期標 `deprecated`；沒有「上傳後永久有效」。
4. **外部內容先審再收**：來源、License、權限、行為都看過才進 repo。
5. **誠實邊界**：不確定的就標明不確定，案例失敗也照寫進 casebook。
