# 定位與判斷權

## TL;DR

- **AI 拿走產出的苦力，留下判斷的重量。** 角色存在的理由不是會什麼技能，而是一類判斷做錯代價很高、必須有人為結果負責。
- **五個判斷權**：PM 的目的判斷、架構師的結構判斷、開發的實作判斷、QE 的可信度判斷、維運的風險判斷。
- **AI 24/7 的最小可行控制集只有 3 個**：QE 的品質門檻、架構師的最小權限隔離、PM 的可執行需求定義 —— 其餘 7 個建立在這三個之上才有意義。
- **底層共通習慣**：「AI 產出的東西，你敢不敢用你的名字簽核上線？」如果無法解釋這段程式碼為什麼是對的，它就不該被合併。

## 為什麼這篇是基礎

後面所有原則（風險分層、品質門檻、流程設計、量測指標）都是這篇推論出來的。如果不接受「角色按判斷權劃分」這個核心命題，下面那些原則會看起來像「為了流程而流程」。

---

## 一、核心命題：判斷權 vs 技能

Kent Beck：「AI 讓我 90% 的技能價值歸零，但剩下 10% 的槓桿放大了 1000 倍。」

用限制理論（TOC）翻譯：當 AI 把 90% 的工作優化到極致，剩下那 10% 的部分就是新的瓶頸。主動讓自己成為那個瓶頸，意味著把時間集中在真正影響目標的核心問題上。

那 10% 是什麼？不是技能，是判斷權。AI 能：
- 給你十個方案，但不能替你決定賭哪一個
- 生成看起來正確的程式碼，但不能判斷它三個月後還維護得動
- 偵測異常，但不能決定「現在要不要叫醒整個團隊」

所以 AI 時代每個角色存在的理由 = 有一類判斷 AI 做不了、做錯代價很高、需要有人為結果負責。

## 二、五個判斷權

| 角色 | 判斷權 | 一句話 | AI 改變了什麼 | 人的新瓶頸 |
|------|--------|--------|--------------|-----------|
| **PM** | 目的判斷 | 這件事值不值得做、衝突時砍什麼留什麼 | AI 能源源不絕生成方案 | 取捨的勇氣、對顧客的直覺判斷 |
| **架構師** | 結構判斷 | 邊界在哪、什麼能妥協什麼不行、壞了影響多大 | AI 能生成 schema/spec/架構圖 | 看到 AI 看不到的失敗模式與跨系統副作用 |
| **開發團隊** | 實作判斷 | AI 產出能不能上線、技術債現在處理還是延後 | AI 能在幾分鐘生成過去要幾天的 code | 品味與審查力（writing → reviewing） |
| **QE** | 可信度判斷 | 這個數字能不能對外講、變更有沒有破壞已有正確性 | AI 能生成測試案例、自動偵測異常 | 定義「可信」的標準（懷疑的直覺，不是測試的手速） |
| **維運** | 風險判斷 | 異常要不要現在處理、回補策略是什麼、能不能安全發布 | AI 能自動偵測異常、建議根因 | 從「被動救火」轉向「主動設計韌性」 |

## 三、PM 的判斷權細化

### 必須回答的四個風險（Marty Cagan / SVPG）
- **價值風險**：顧客會買單或決定使用嗎？
- **易用性風險**：用戶搞得懂怎麼用嗎？
- **實行性風險**：工程師做得出來嗎？
- **商業可行性風險**：對公司財務、法務、銷售行得通嗎？

### 必須帶來的四項貢獻
1. 深入了解顧客（質化訪談 + 量化數據）
2. 深入了解資料（每天第一件事查看數據）
3. 深入了解事業（產品如何幫公司獲利）
4. 深入了解市場與產業（競品 / 趨勢 / 顧客行為變化）

### 收斂與交付（給工程的四件事）
- 定義要贏什麼（Outcome）
- 定義真正要解的問題（Problem Framing）
- 做取捨並形成可交付的賭注（Bet / Slice）
- 把成功條件交給工程（Acceptance / Guardrails）

### 優先序的本質（Reinertsen）
不是看利潤或重要性，是看「延遲會讓價值怎麼變化」（Cost of Delay）。

### 驗證與前型（Pretotyping）
- 句型：「至少 X% 的 Y 會 Z」（X = 目標市場百分比；Y = 市場明確描述；Z = 期望接受情況）
- 三原則：讓目標客群付出某種代價以產生自我數據、迅速執行、成本低廉

## 四、架構師的判斷權細化

核心工作 = **把不確定性轉換成確定性**，讓商業需求變成開發團隊能執行的規格。

### 四件事
1. **不確定性的規格化**：SPEC 不只是畫面流程行為，還包括設計決策、跨系統介面（API）、非功能性需求（效能/安全/成本）、失敗模式
2. **用 Prototype 驗證結構判斷**：Vibe Coding Prototype 不只收斂需求，更是驗證結構判斷的工具
3. **判斷「足夠確定」的標準**：開發團隊拿到這份 spec 後，能不能在 80% 工作不需回頭問的情況下完成？
4. **確定性之後從設計者轉為守護者**：確保實作沒偏離結構意圖

### Prototype 的價值
- 敘述行為（可以直接 RUN）
- 定義設計（有實際 API spec 與 database schema）
- 驗證整合（多個專案透過呼叫 API，確保單一規格能滿足多需求）

## 五、開發團隊的判斷權細化

核心轉變：**從 writing 轉向 reviewing**。

四個品質屬性的判斷仍是人的責任（速度不是目標，可部署性才是）：
- **可維護**：三個月後換人接手能不能看懂
- **可測試**：能不能寫出有意義的自動化測試
- **可觀測**：出事時能不能快速定位問題
- **可回滾**：上線發現不對能不能安全退回

### 為什麼品味重要（Andrew Ng 的例子）
他用 MidJourney 時無法精準描述想要的結果。但他一位有藝術史背景的合作夥伴，因為熟悉不同藝術流派，產出遠比 AI 專家更好。同理，工程師要掌握程式生成 AI，就要培養對程式設計的品味（歷史脈絡、各種範式、設計模式、撰寫風格）。

## 六、QE 的判斷權細化

QE 的交付不是「測試報告」，而是**「一套可重複執行的信心機制」**。

### 四個重點
- **測試策略**：根據風險分佈決定深度與廣度，不是追求覆蓋率數字
- **自動化品質門檻**：每次變更必須通過的最低標準（功能正確性 + 效能基準 + 安全掃描）
- **回歸評估**：版本變更前後關鍵行為與指標的差異
- **驗收評估（Evals）**：端到端驗證從輸入到輸出是否符合 PM 定義的 Acceptance Criteria

## 七、維運的判斷權細化

目標不是「零事故」（不現實），而是**「出事時能快速復原，且每次事件都讓系統變得更強韌」**。

### 五個重點
- **可控發布**：漸進部署 + feature flag + canary
- **可觀測性**：出事時能在 5 分鐘內定位根因
- **事件處理**：告警分級 + 影響評估 + 回補 SOP + 事後覆盤
- **容量與成本**：資源使用趨勢 + 成本異常偵測
- **資安與依賴治理**：權限最小化 + secret 管理 + 第三方依賴風險評估

## 八、瓶頸收斂順序（TOC）

不是同時解五個問題，是每個階段只打一個。在 Coding Agent 把 delivery 速度拉高之後，瓶頸更常依以下順序浮現：

| 順序 | 瓶頸 | 打穿的標誌 |
|------|------|----------|
| 第 1 | PM 的問題定義與取捨（做對事） | 開發團隊不再問「這個功能到底要幹嘛」 |
| 第 2 | 架構師的風險規格化（把不確定性壓縮成可交棒） | 開發拿到 spec 後，80% 工作不需回頭確認 |
| 第 3 | QE + 維運的品質與風險門檻（讓變更安全地快） | 團隊能自信說「這版可以上」，且上了真的沒事 |

每打穿一個瓶頸，它就不再是瓶頸，約束會移動到下一個。這不是一次性規劃，是持續節奏：觀察、聚焦、突破、再觀察。

## 九、AI 24/7 的最小可行控制集（前三名）

> 「要讓 AI 24/7 有效 → 需要完美 Spec + 自動驗證 → 需要成熟工程文化 → 通常不缺人力，不需要 AI 24/7」
>
> 這個悖論的解法不是「先做到完美再開始」，而是**選出最少的控制點，讓 AI 在有限範圍內安全地 24/7 運作，再逐步擴大**。

從 TOC 視角，最小可行控制集是 **3 個**：

### 🥇 第一：品質門檻（Quality Gates）—— QE 的判斷
**為什麼第一**：唯一一個「沒有它就絕對不能讓 AI 自主運作」的控制點。其他做不好最多是效率低，這個做不好 AI 會把壞東西推上 production。

**最小實作**：CI pipeline 中的自動化測試 + linter + 安全掃描 + secrets scanning，全過才能 merge。

### 🥈 第二：最小權限與隔離（Sandbox）—— 架構師的判斷
**為什麼第二**：品質門檻擋的是「品質不好的產出」，但若 AI 執行環境本身沒隔離，它可能繞過 gate 直接造成損害（寫錯分支、碰不該碰的資料、洩漏 secret）。

**最小實作**：獨立 bot 帳戶 + 只能推 PR 到特定分支 + 沙盒執行環境 + 不碰 production 資料庫。

### 🥉 第三：可執行需求定義 —— PM 的判斷
**為什麼第三**：前兩個保證 AI 不會搞破壞，但若需求定義模糊，AI 會 24 小時高效地做錯事，產出一堆通過 gate 但沒人要的功能。

**最小實作**：維護一份「AI 可自主執行任務清單」，每項都有明確驗收條件與錯誤成本評估。

### 為什麼其他 7 個不在前三
不是不重要，是**沒有前三個其他做了也沒意義**：
- 沒有 Gate（②），雙重審查（⑤）和監控（⑦）只是在看垃圾進 production 的速度
- 沒有隔離（③），版本控制（④）和回滾策略救不了被直接污染的環境
- 沒有需求定義（①），成本管理（⑧）只是在計算做錯事花了多少錢

## 十、10 個控制點對應的角色歸屬與調整方向

| # | 控制點 | 主要判斷權歸屬 | 調整方向 |
|---|--------|---------------|---------|
| ① | 可執行的需求定義 | PM | 從「寫好 ticket」升級為「決定什麼任務以什麼優先序交給 AI 自主執行」 |
| ② | 嚴格品質門檻 | QE | 已成熟，唯一要補的是「誰判斷 gate 的標準夠不夠嚴」 |
| ③ | 最小權限與隔離 | 架構師 | 是結構決策，不是維運的事後配置 |
| ④ | 版本控制與可回滾 | 開發團隊 | 不需大改，「這個 AI commit 要不要 merge / revert」是實作判斷 |
| ⑤ | 雙重審查 | 開發團隊 | 補審查標準：結構性審查 + 品味審查 + 風險直覺 |
| ⑥ | 工程師技能與心態培養 | 開發團隊 | 從 writing → reviewing 的能力轉型 |
| ⑦ | 衡量與監控 | QE | 補閾值：什麼數字出現要踩煞車 |
| ⑧ | 成本與資源管理 | 維運 | 判斷的不是「要不要省錢」，是「成本趨勢可不可持續、何時該介入」 |
| ⑨ | 變更管理與責任 | 跨角色（維運主導） | 責任按判斷權拆開（事故根因是需求不清→PM；架構遺漏→架構師；審查疏忽→開發；gate 不夠嚴→QE） |
| ⑩ | 護欄示例化 | 架構師 | 提前到架構階段，作為「AI 協作的系統約束」而非「持續優化的流程文件」 |

## 十一、各角色的 AI 時代必備能力（每角色取 3 項最高槓桿）

### 共通底層習慣
> **「AI 產出的東西，你敢不敢用你的名字簽核上線？」** 無法解釋這段程式碼為什麼是對的，它就不該被合併。GitClear 211M 行追蹤：團隊 review 深度已下降 30%，copy/paste 首次超越 refactoring，技術債正在無聲累積。

### 前端工程師
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| 辨識「外觀正確」陷阱 | AI 生成 UI 格式完美但隱藏 XSS、不安全 DOM、外洩 state；前端是直接攻擊面 | review 時手動檢查：sanitize、敏感資料、第三方 CDN |
| 依賴審計直覺 | 前端依賴樹深，AI 最容易推薦幻覺套件 | 對每個 AI 建議的 npm package：查 npmjs.com、看 weekly downloads、檢查最後更新日 |
| 無障礙與效能的系統判斷 | AI 不會主動考慮 a11y、bundle size、render performance | Lighthouse / Core Web Vitals 基線；a11y 檢查列入 CI |

### 後端工程師
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| 故障場景想像力 | AI 寫 happy path 完美但不會主動破壞自己的程式碼來測試韌性 | 每個變更自問「下游掛了會發生什麼」，確認 circuit breaker / fallback / timeout 沒被誤刪 |
| 授權與安全邊界意識 | 跨服務 JWT/header/claims 變更是 AI CR 最難抓的（靜默授權回退）；45% AI code 含安全漏洞 | 涉及 auth 變更不信 AI CR，親自寫 contract test 驗證 |
| 資料操作的不可逆意識 | DELETE/TRUNCATE/MERGE 在 AI 看來只是一行（Replit 事件教訓） | 看到資料寫入/刪除 → 自問：dry-run？備份？rollback？沒有就不過 |

### 架構師 / Tech Lead
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| 跨服務影響的全局視野 | AI 只看單一 PR，看不到漣漪效應 | R2/R3 PR 畫出影響的服務鏈：schema 向後相容、event contract 消費者、shared state 一致性 |
| 技術債的主動治理 | 沒人主動排程 refactoring 就沒人會做 | 每迭代保留 15-20% 容量給 refactoring；定期 review duplication；拒絕「AI 生成所以先這樣」的藉口 |
| AI 工具鏈的風險治理 | 團隊用什麼 AI tool / 有什麼權限 / 連接什麼外部服務 是架構師責任 | 維護 AI tool allowlist、定義 agent 權限邊界、MCP server / IDE extension 納入安全審計 |

### 數據工程師 / 分析師
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| 效能直覺與成本意識 | AI 寫 Spark/SQL 在小樣本完美但生產可能 data skew / shuffle explosion | AI 生成 query 必須附 explain plan 或 Spark UI 截圖；問「join 基數？partition 策略？」 |
| 資料品質的懷疑本能 | AI 可能產出「格式正確但語義錯誤」的資料 | 用已知答案樣本做 sanity check；對聚合結果建立 data quality assertion |
| Incremental processing 的邊界條件 | AI 寫 watermark/CDC/merge 最容易忽略：late-arriving、exactly-once、重播冪等性 | 改動 incremental 邏輯必附 replay test 結果 |

### DevOps / SRE
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| CI/CD pipeline 即攻擊面 | AWS CodeBuild webhook 漏洞（CodeBreach）證明 pipeline 配置本身是供應鏈攻擊入口 | 定期審計 token scope / webhook filter / build trigger；agent credential 最小權限 + 定期輪換 |
| 可觀測性設計 | AI 產碼幾乎不會主動加 structured logging / metrics / alerting | 「有 metrics/alert 更新」列入 R2/R3 合併必要條件 |
| Rollback 肌肉記憶 | AI 不會幫你設計 rollback；agent 多步驟部署出問題時，幾分鐘內回滾是 SRE 獨有價值 | 每個部署附具體回滾命令；定期演練；agentic deployment 必須支援原子性回滾 |

### QA / 測試工程師
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| 「AI 沒測到什麼」的逆向思維 | AI 生成 test 覆蓋率好看但只測 happy path | 系統性補：邊界值、null/empty、併發、故障注入、跨時區、權限不足 |
| Contract testing 實作能力 | 跨服務靜默回退是 AI 時代最隱蔽 bug；只做 UI E2E 抓不到 header/schema 不一致 | 推動 Pact 或類似 consumer-driven contract testing |
| 對「AI 說通過」的健康懷疑 | AI CR 與 AI test generation 都有確認偏誤 | 至少一輪測試由人類從需求出發設計（不是從 AI 程式碼出發），打破迴圈 |

## 一頁速查：各角色的一句話提醒

| 角色 | 你最不可被 AI 取代的價值 |
|------|------------------------|
| 前端 | 你能看穿「畫面正常」背後的安全與效能問題 |
| 後端 | 你能想像「如果這個掛了」的故障場景 |
| 架構師 | 你能看到單一 PR 看不到的系統漣漪 |
| 數據工程 | 你能質疑「數字對嗎」而不是只看「能跑嗎」 |
| DevOps/SRE | 你能在出事的前 5 分鐘把系統救回來 |
| QA | 你能想到 AI 想不到的壞掉方式 |

## 結語

AI 時代的角色分工，本質上是一個關於「判斷權」的問題。AI 拿走了產出的苦力，留下了判斷的重量。每個角色之所以存在，不是因為 AI 還沒學會那項技能，而是因為有一類判斷做錯了代價很高、需要有人承擔後果——必須由人來做。

PM 判斷值不值得做，架構師判斷能不能做對，開發判斷做出來的東西能不能上線，QE 判斷結果可不可信，維運判斷風險可不可控。這五個判斷，就是 AI 時代人的價值所在。
