# 判斷權與量測指標

## TL;DR

- **角色按判斷權劃分，不按技能**：每個角色存在的理由，是有一類判斷做錯代價高、必須有人具名負責。這是 A×R 授權矩陣的理論根據。
- **五個判斷權**：PM 目的、架構師結構、開發實作、QE 可信度、維運風險。
- **瓶頸不是被消除，是被搬家**：從「寫 code」搬到需求定義 → review → 驗證 → 架構整合 → 治理。
- **量測主指標**：「需求到驗證通過」的 lead time；搭配護欄指標，防止「為了快而放水」。
- **底層共通習慣**：「AI 產出的東西，你敢不敢用你的名字簽核上線？」無法解釋這段程式碼為什麼是對的，它就不該被合併。

---

## 一、核心命題：判斷權 vs 技能

Kent Beck：「AI 讓我 90% 的技能價值歸零，但剩下 10% 的槓桿放大了 1000 倍。」那 10% 不是技能，是判斷權。AI 能給你十個方案，但不能替你決定賭哪一個；能生成看起來正確的 code，但不能判斷它三個月後還維護不維護得動。

| 角色 | 判斷權 | 一句話 | 人的新瓶頸 |
|------|--------|--------|-----------|
| **PM** | 目的判斷 | 這件事值不值得做、衝突時砍什麼留什麼 | 取捨的勇氣、對顧客的直覺判斷 |
| **架構師** | 結構判斷 | 邊界在哪、什麼能妥協什麼不行、壞了影響多大 | 看到 AI 看不到的失敗模式與跨系統副作用 |
| **開發團隊** | 實作判斷 | AI 產出能不能上線、技術債現在處理還是延後 | 品味與審查力（writing → reviewing） |
| **QE** | 可信度判斷 | 這個數字能不能對外講、變更有沒有破壞已有正確性 | 定義「可信」的標準（懷疑的直覺，不是測試的手速） |
| **維運** | 風險判斷 | 異常要不要現在處理、能不能安全發布 | 從「被動救火」轉向「主動設計韌性」 |

## 二、AI 自主運作的最小可行控制集（3 個）

不是「先做到完美再開始」，而是選出最少的控制點，讓 AI 在有限範圍內安全運作，再逐步擴大：

1. 🥇 **品質門檻（QE 的判斷）**——唯一「沒有它就絕對不能讓 AI 自主運作」的控制點。最小實作：CI 的自動化測試 + linter + 安全掃描 + secrets scanning，全過才能 merge。
2. 🥈 **最小權限與隔離（架構師的判斷）**——沒隔離，AI 可能繞過 gate 直接造成損害。最小實作：獨立 bot 帳戶 + 只能推 PR 到特定分支 + 沙盒環境 + 不碰 production 資料庫。
3. 🥉 **可執行需求定義（PM 的判斷）**——前兩個保證 AI 不搞破壞，但需求模糊時 AI 會 24 小時高效地做錯事。最小實作：「AI 可自主執行任務清單」，每項有明確驗收條件與錯誤成本評估。

其他控制點（雙重審查、監控、成本管理…）都建立在這三個之上才有意義。

## 三、瓶頸遷移：產出變快之後會撞上的五面牆

> **Coding Agent 消除的不是瓶頸，而是把瓶頸從「寫 code」推到「定義、review、驗證、整合、治理」。**

| 牆 | 現象 | 本質 |
|---|------|------|
| 需求定義 | task 很多但真正 merge 的少；PR 多但需求重開也多 | 不是寫太慢，是「做錯得更快」 |
| Review | 待 review PR 堆積、合併變慢 | 有判斷權的人太少，Agent 不能替代具名負責 |
| 驗證 / CI | 等待與修錯循環變長 | 驗證系統取代 implementation 成為新的控制介面 |
| 架構整合 | 改 A 破 B、boundary 越來越模糊 | Agent 對局部最優很強、對系統整體意圖很弱 |
| 信任與治理 | 一次事故就全面踩煞車 | 穩態是「可分級的護欄」，不是全面放行或全面封鎖 |

**最危險的是延遲**：缺陷兩週後才爆（誤以為流程變好）、架構三個月後才腐化、信任在第 21 次事故才崩潰、只看 LoC/PR 數的指標錯覺。

## 四、量測：主指標 + 護欄指標

### 主指標：需求到驗證通過的 lead time

只量「需求到程式碼」會讓團隊高效做錯事。該量的是從需求明確化，到變更通過該風險等級門檻、進入可接受狀態的時間。可切兩段看瓶頸在生成還是驗證：

- 需求 → first acceptable candidate
- candidate → gate pass

### 護欄指標（防主指標失真）

| 指標 | 抓什麼 |
|------|--------|
| Change Fail Rate | 變更失敗率 |
| Rollback Rate | 回滾率 |
| Escaped Defects | 逃逸到 production 的缺陷 |
| Security Findings Severity | 資安發現嚴重度 |
| MTTR | 平均復原時間 |
| Cost per Accepted Change | 每個通過變更的成本 |
| Review Rework Rate | review 後返工率 |

## 五、各角色的 AI 時代必備能力（每角色 3 項最高槓桿）

### 前端工程師
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| 辨識「外觀正確」陷阱 | AI 生成 UI 格式完美但可能藏 XSS、不安全 DOM | review 時手動檢查 sanitize、敏感資料、第三方 CDN |
| 依賴審計直覺 | 前端依賴樹深，AI 最容易推薦幻覺套件 | AI 建議的 npm package：查 registry、看下載量與更新日 |
| 無障礙與效能的系統判斷 | AI 不會主動考慮 a11y、bundle size | Lighthouse / Core Web Vitals 基線；a11y 列入 CI |

### 後端工程師
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| 故障場景想像力 | AI 寫 happy path 完美但不會主動破壞自己的程式碼 | 每個變更自問「下游掛了會怎樣」，確認 fallback/timeout 沒被誤刪 |
| 授權與安全邊界意識 | 跨服務 JWT/header/claims 變更是 AI CR 最難抓的 | 涉及 auth 變更不信 AI CR，親自寫 contract test |
| 資料操作的不可逆意識 | DELETE/TRUNCATE/MERGE 在 AI 看來只是一行 | 看到資料寫入/刪除 → 自問 dry-run？備份？rollback？沒有就不過 |

### 架構師 / Tech Lead
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| 跨服務影響的全局視野 | AI 只看單一 PR，看不到漣漪效應 | R2/R3 PR 畫出影響的服務鏈與相容性 |
| 技術債的主動治理 | 沒人主動排程 refactoring 就沒人做 | 每迭代保留 15-20% 容量給 refactoring |
| AI 工具鏈的風險治理 | 團隊用什麼 tool、什麼權限是架構師責任 | 維護 allowlist、定義 agent 權限邊界、MCP/extension 納入審計 |

### 數據工程師 / 分析師
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| 效能直覺與成本意識 | AI 寫 Spark/SQL 小樣本完美但生產可能 skew | AI 生成 query 必附 explain plan；問 join 基數、partition 策略 |
| 資料品質的懷疑本能 | AI 可能產出「格式正確但語義錯誤」的資料 | 已知答案樣本 sanity check；聚合結果建 assertion |
| Incremental processing 邊界 | watermark/CDC 最容易漏 late-arriving、冪等性 | 改 incremental 邏輯必附 replay test 結果 |

### DevOps / SRE
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| CI/CD pipeline 即攻擊面 | pipeline 配置本身是供應鏈攻擊入口 | 定期審計 token scope；agent credential 最小權限 + 輪換 |
| 可觀測性設計 | AI 產碼幾乎不會主動加 logging/metrics | 「有 metrics/alert 更新」列入 R2/R3 合併必要條件 |
| Rollback 肌肉記憶 | AI 不會幫你設計 rollback | 每個部署附回滾命令；agentic deployment 必須支援原子性回滾 |

### QA / 測試工程師
| 能力 | 為什麼是你 | 具體行動 |
|------|-----------|---------|
| 「AI 沒測到什麼」的逆向思維 | AI 生成 test 覆蓋率好看但只測 happy path | 系統性補邊界值、null、併發、故障注入、權限不足 |
| Contract testing 實作 | 跨服務靜默回退是 AI 時代最隱蔽 bug | 推動 consumer-driven contract testing |
| 對「AI 說通過」的健康懷疑 | AI CR 與 AI test 都有確認偏誤 | 至少一輪測試由人從需求出發設計，打破迴圈 |

### 一頁速查

| 角色 | 你最不可被 AI 取代的價值 |
|------|------------------------|
| 前端 | 看穿「畫面正常」背後的安全與效能問題 |
| 後端 | 想像「如果這個掛了」的故障場景 |
| 架構師 | 看到單一 PR 看不到的系統漣漪 |
| 數據工程 | 質疑「數字對嗎」而不是只看「能跑嗎」 |
| DevOps/SRE | 在出事的前 5 分鐘把系統救回來 |
| QA | 想到 AI 想不到的壞掉方式 |

## 六、給上層的判斷句

> Agent 越強，越不該問「能不能寫更多 code」，而要問：
> - 我們定義問題的速度跟得上嗎？
> - 有判斷權的人 review 得過來嗎？
> - 驗證系統撐得住嗎？
> - 架構邊界會不會被局部最優侵蝕？
> - 放權的護欄是否足夠細，不會一刀切？
