## 六、AI 編程工具的上下文管理（重要演講）

### YouTube：AI 編程工具的上下文管理
**連結**：https://www.youtube.com/watch?v=rmvDxxNubIg

### 核心觀點：不要把思考外包給 LLM

**Dumb Zone 概念**：當上下文視窗填滿約 **40%**，AI 回應品質就開始下降。塞太多資訊，就會產生「AI Slop」。

### 解決方案：持續壓縮和審查
- 研究系統運作，找出相關檔案
- 規劃具體步驟，包含程式碼片段
- 實作時保持上下文精簡

### 實際工作流程：刻意壓縮
- 用 Claude Code 時，把進度壓縮成 markdown 檔
- `research.md` 放研究結果
- `plan.md` 放實作步驟（含程式碼和行號）
- 新的上下文視窗能立即接手，不用重新理解整個程式庫

### 關鍵洞察
> **子代理不是用來模仿團隊角色的。它們是用來控制上下文。**
> 讓子代理去探索程式庫，完成後回傳精簡摘要給父代理。父代理保持輕量專注。

### 對應 AgentCodingPM 的意涵
- 這是 Pattern C「單 Agent + Skill > 多 Agent」的延伸：多 Agent 的價值不是「角色扮演」，是 context 控制
- 跟 [`08-Skill與Harness工程.md`](./08-Skill與Harness工程.md) 的 Progressive Disclosure 同源

## 七、Configuration 檔案：Copilot vs Claude vs 其他

### 兩者本質
都是「告訴 AI 如何協助這個專案」的設定檔。

| 功能 | GitHub Copilot | Claude Code | Codex / Gemini |
|------|---------------|-------------|---------------|
| 檔案位置 | `.github/copilot-instructions.md` | `CLAUDE.md` 或 `.claude/claude.md` | `AGENTS.md` / `GEMINI.md` |
| 讀取方式 | 自動讀為 workspace context | 自動讀為 project context | 自動讀為 project context |

### 應該包含什麼
- **角色定義**：AI 在這個專案的職責
- **產出格式**：需要什麼結構（Input / Output / Acceptance）
- **禁止事項**：避免空泛、大而化之、buzzword
- **工作流程**：與 prompts / skills 的整合方式

### 為什麼需要
1. 一次設定，持續生效
2. 團隊共享
3. 專案特定客製化
4. 品質一致

### 延伸閱讀
- [GitHub Copilot Instructions 文件](https://docs.github.com/en/copilot/customizing-copilot/adding-custom-instructions-for-github-copilot)
- [Claude Projects 文件](https://support.anthropic.com/en/articles/9517075-what-are-projects)

### 對 AgentCodingPM 的做法
我們用 `AGENTS.md` 為核心指令源：
- Claude Code / Codex CLI 直接讀取
- GitHub Copilot 透過 `.github/copilot-instructions.md` 橋接
- Gemini CLI 透過 `GEMINI.md` 讀取
- AGENTS.md 變更後用 `copilot-sync` skill 維持橋接一致
