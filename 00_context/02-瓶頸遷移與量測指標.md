# 瓶頸遷移與量測指標

## TL;DR

- **核心命題**：當 Coding Agent 讓「產生變更」的邊際成本快速下降，系統的主瓶頸不再是實作能力，而依序轉移到需求定義、判斷權、驗證 throughput、架構整合、治理能力。
- **量錯就引導錯**：只量「需求到程式碼」的速度，會讓團隊高效做錯事。該量的是「**需求到驗證通過**」的 lead time。
- **單一 KPI 必失真**：主指標 + 護欄指標，兩層綁在一起，不然會被「為了快而放水」打敗。
- **DORA 2025 結論**：AI 是放大器，會放大組織既有的強項與弱點 —— 成功導入是「系統問題」，不是單一工具問題。

## 為什麼這篇是基礎

這是 AgentCodingPM 存在的論證。如果不接受「瓶頸搬走了」這個前提，那團隊投入「需求定義 / 驗證 / 治理」的力氣會被質疑。這篇給你說服上層與同事的邏輯與證據。

---

## 一、系統的存量與流量（系統動力學視角）

### 主要存量
- 待定義需求存量
- 待 review 的 PR / change 存量
- 待驗證的變更存量
- 架構複雜度 / 技術債存量
- 團隊對 Agent 的信任存量
- 生產環境風險暴露存量

### 主要流量
- 需求被切成 task 的速度
- Agent 產生 code / PR 的速度
- 人類 review 與決策的速度
- CI / security / test 驗證的速度
- merge / release 的速度
- incident / defect 被發現與回流的速度

當 Agent 持續變強時，**上游流量暴增**，但下游流量不一定同步增加。所以瓶頸自然往後移。

---

## 二、增強迴路 R1：Agent 加速產出

```
[ Coding Agent 變強 ]
        ↓
[ 產出 code/PR 速度 ]
        ↓
[ 團隊更願意交給 Agent 的任務量 ]
        ↓
[ Agent 使用量 ]
        └────────→ 回到 [ Coding Agent 變強 ]
```

意思：**越好用 → 越多人用 → 越多任務交給它 → 產出更多。**

GitHub Copilot coding agent、Codex cloud、Gemini CLI 都已明確支援背景執行、PR 工作流或 loop 式任務完成 —— 這個加速環是現實，不是想像。

## 三、五個會撞上的平衡迴路（B1-B5）

### B1 — 需求定義變瓶頸

```
[產出 code/PR 速度變快]
   ↓
[模糊需求也更快被做出來]
   ↓
[做錯 / 返工]
   ↓
[PM/Tech Lead 重定義需求的負擔]
   ↓
[可清楚交辦的任務量下降]  → 抵消產出速度
```

**現象**：task 很多但真正 merge 的少；Agent 很忙但 roadmap 感覺更亂；PR 很多但需求重開也很多。

**本質**：不是寫太慢，是「做錯得更快」。

### B2 — Review 變瓶頸

```
[產出速度變快] → [待 review PR 變多] → [Reviewer 負荷] → [Review 時間] → [Merge 速度下降]
```

**本質**：不是「少幾個 reviewer」而已，是**有判斷權的人太少**：
- PM 對價值有判斷權
- Tech Lead 對邊界有判斷權
- QE 對可信度有判斷權
- Owner 對能不能 merge 有判斷權

Agent 可以大量產出，但不能替代具名負責的判斷。

### B3 — 驗證 / CI / 資安變瓶頸

```
[產出速度變快] → [待測試/掃描/驗證的變更變多] → [CI/test/security 負荷] → [等待時間/修錯循環] → [合併釋出速度下降]
```

**關鍵轉移**：以前 bottleneck 是「工程師沒時間寫 test」，現在更可能變成：test 本身不夠可靠 / CI 太慢 / security scan 太吵 / 沒明確 fail-fast / Agent 修錯速度比驗證速度快。

**結論**：驗證系統會取代 implementation，成為新的控制介面。

### B4 — 架構整合變瓶頸

```
[Agent 更快做局部功能] → [局部最優改動變多] → [系統耦合/邊界破壞/技術債] → [後續任務更難理解/測試/review] → [整體開發速度下降]
```

**現象**：短期看起來快，中期開始出現「改 A 破 B / schema 變更多但治理更弱 / service boundary 越來越模糊 / reviewer 越來越難判斷」—— 典型的架構債存量累積。

### B5 — 信任與治理變瓶頸

```
[Agent 產出更多變更] → [事故/不確定感/風險感受] → [組織加強人工簽核] → [Agent 可自主範圍縮小]
```

**兩個極端都不是穩態**：
- 太信任 Agent → 被 incident 教訓
- 怕風險把每步都鎖死 → Agent 只剩高級 autocomplete

**穩態**：把治理做成可分級的護欄，不是全面放行或全面封鎖。

## 四、最危險的四種延遲

系統動力學最怕的不是單點問題，是**延遲讓人誤判因果**：

| 延遲類型 | 危險點 |
|---------|-------|
| 缺陷發現延遲 | 今天快速 merge 的問題，兩週後才在整合測試或線上爆出。團隊誤以為「速度提升 = 流程變好」 |
| 架構腐化延遲 | 局部 PR 看起來都合理，三個月後才發現整體邊界被侵蝕 |
| 信任崩潰延遲 | 前面 20 次都還好，第 21 次 R2/R3 事故才讓組織全面踩煞車 |
| 指標錯覺延遲 | 只看 LoC / PR 數 / 任務完成數會以為進步很大；GitHub 把 adoption / engagement / acceptance rate / PR lifecycle 都列為正式量測項，是因為**整體流動效率與接受品質**才是重點 |

## 五、未來 12-24 個月最可能的瓶頸排序

| 排名 | 瓶頸 | 為什麼 |
|------|------|-------|
| 1 | 需求定義 / 任務切分 / 驗收標準 | 決定 Agent 是高效做對還是高效做錯（DORA 2025 明確說明 AI 回報來自底層系統） |
| 2 | Review bandwidth 與判斷權擁塞 | 工具都在把變更更快送到 PR/review 節點 |
| 3 | 可執行驗證與 CI/security throughput | 沒這層，自治越高事故越快 |
| 4 | 架構整合與跨模組一致性 | Agent 對局部最優很強，對系統整體意圖很弱 |
| 5 | 上下文資產化 | 把 tacit knowledge 變成 CLAUDE.md / AGENTS.md / templates / hooks / skills / review checklists 這類**可執行知識** |

## 六、「需求到驗證通過」的速度（新主指標）

### 核心命題

> 在 Agent Coding 時代，真正該量的，逐漸不是「需求到程式碼」的速度，而是「**需求到被驗證可接受結果**」的速度。

「可接受」不是完美，而是依專案風險，跨過一組門檻值就能往下走。這組門檻通常包含 review、測試、資安、可維運性、成本、回滾能力與觀測性。

### 流程拆解

```
Idea / Requirement
        ↓
Implemented Change
        ↓
Verified Acceptable Outcome
```

重點是中間那段不再只是 coding，而是整個驗證回路。

對應 Martin Fowler / Kief Morris 的論點：人類角色不是逐行盯 code、也不是完全放手，而是 **build and manage the working loop**。

---

## 七、雙層指標設計（防失真）

### 第一層：主指標 = Requirement-to-Accepted-Outcome Lead Time

從需求明確化，到變更通過該風險等級所需門檻、進入可接受狀態的時間。

可以再切成兩段：
- **需求 → first acceptable candidate**
- **candidate → gate pass**

這樣能看出瓶頸到底在生成還是在驗證。

### 第二層：護欄指標（防止主指標失真）

| 指標 | 抓什麼 |
|------|--------|
| Change Fail Rate | 變更失敗率 |
| Rollback Rate | 回滾率 |
| Escaped Defects | 逃逸到 production 的缺陷 |
| Security Findings Severity | 資安發現嚴重度 |
| On-call / Incident Load | 維運負擔 |
| MTTR | Mean Time To Recovery |
| Cost per Accepted Change | 每個通過變更的成本 |
| Review Rework Rate | review 後返工率 |

對應 DORA 與 SPACE 的核心訴求：不能只看速度，要同時看穩定性、效率、協作、滿意度。

---

## 八、Risk-Based Gates（不同風險走不同門檻）

| 專案類型 | 範例 | 必通過門檻 |
|---------|------|-----------|
| **低風險** | 內部工具、一次性分析、小型 PoC | 基本測試可跑、無高危漏洞、可回滾、成本沒明顯失控 |
| **中風險** | 對外功能、內部核心流程、自動化決策輔助 | code review、關鍵路徑測試、觀測性、權限/密鑰掃描、成本預估 |
| **高風險** | 金流、個資、法規、車輛控制、醫療、關鍵營運 | 嚴格測試覆蓋、threat modeling、provenance/supply-chain 控制、canary/staged rollout、runbook、SLO、rollback policy |

對應的成熟框架：
- **NIST SSDF**：在 SDLC 關鍵點驗證是否符合安全要求
- **SLSA**：分級的安全保證模型，不同 level 對應不同完整性要求
- **Google SRE Error Budget**：系統若在 SLO 內可照常發版；error budget 打爆就停止一般變更，只留必要修復

---

## 九、給上層的判斷句

> Agent 越強，越不該問「能不能寫更多 code」，而要問：
> - 我們定義問題的速度跟得上嗎？
> - 有判斷權的人 review 得過來嗎？
> - 驗證系統撐得住嗎？
> - 架構邊界會不會被局部最優侵蝕？
> - 我們的團隊知識有沒有被資產化？
> - 放權的護欄是否足夠細，不會一刀切？

## 十、最後濃縮

> **Coding Agent 消除的不是瓶頸，而是把瓶頸從「寫 code」推到「定義、review、驗證、整合、治理」。**

所以團隊的競爭力，不是讓 agent 寫得更快，而是讓系統更快地判定「什麼時候已經夠好可以往前走」。

## 簡化的瓶頸圖

```
       (R1 增強)
[Agent 變強] → [產出 code/PR 更快] → [更多任務交給 Agent]
      ↑______________________________________________|

                  但會撞上 5 個平衡迴路

[產出更快]
   ↓
   ├─→ (B1) [需求定義不足]    → [返工增加]
   ├─→ (B2) [Review 壓力上升]  → [合併變慢]
   ├─→ (B3) [CI/驗證壓力上升]  → [等待變慢]
   ├─→ (B4) [架構整合壓力上升] → [技術債增加]
   └─→ (B5) [風險與不信任上升] → [治理變重]

最後結果：
[真正交付速度] 不一定跟著 [產出速度] 一起上升
```
