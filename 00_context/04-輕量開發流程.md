# 輕量開發流程（小團隊版）

## TL;DR

- **三個核心原則**：角色按判斷權劃分（不按產出），流程按風險分流（不一條路走到底），文件只保留最少必要集。
- **核心流程**：`Inbox → Outcomes → OPP+Experiments → Backlog → User Stories → PRD → 工程實作 → 知識回流`
- **整個團隊在做一件事**：逐步降低不確定性。每個角色降低不同類型的不確定性。
- **AI 加速產出，但不負責收斂風險**。每一個角色仍負責收斂不同類型的不確定性。
- **文件不是目的**，是讓需求逐步收斂成「可設計、可開發、可驗證」的系統。

---

## 一、三個核心原則

### 原則 1：角色按「判斷權」劃分，不按產出劃分
AI 可以幫忙產出，但不能替人類承擔錯誤決策的責任。這是貫穿整個流程的軸。詳見 [`01-定位與判斷權.md`](./01-定位與判斷權.md)。

### 原則 2：流程按風險分流，不是一條路走到底
低風險任務走短流程，高風險任務才補更多控制點。詳見 [`05-風險分層與五大品質門檻.md`](./05-風險分層與五大品質門檻.md)。

### 原則 3：文件只保留最少必要集
只保留能讓 Agent 執行、也能讓人類 review 的最小文件。

---

## 二、整體流程地圖

```text
(知識庫 / 歷史脈絡 / 數據輸入) ──┐
                                  ▼
Inbox → Outcomes → OPP+Experiments → Backlog → User Stories → PRD
                                                                 ↓
                              [技術高不確定性] → 架構師 → Architecture/Prototype
                              [體驗/介面需求]  → 設計師 → Wireframe/UX Prototype
                              [系統流程/資料]  → SA    → Flow/Data/API/規則
                                                                 ↓
                                              定稿 PRD + 架構 + UX + 系統規格
                                                                 ↓
                              資深工程師/SA → 技術規格展開 (API/Data Model/系統設計)
                              QA/Agent     → 測試案例生成 / 驗收條件
                                                                 ↓
                                                          工程實作與上線
                                                                 ↓
                                                            Data Outcomes
                                                                 ↓
                                                           Retrospective
                                                                 ↓
                                                  知識庫更新 / Agent 規則更新
                                                                 ↓
                                                              回流 Step 1
```

## 三、各階段角色分工

### 階段 1：核心探索與規格化（PM 主導，設計師 / 架構師 / SA 早期參與）

#### PM 的核心責任 —— 回答三個問題

1️⃣ **這是不是值得解的問題**
- 使用者痛點
- 商業價值
- 優先順序

2️⃣ **成功長什麼樣**
- Outcomes
- 成功指標
- 使用情境

3️⃣ **範圍在哪裡**
- 做什麼
- 不做什麼

#### AI 在這一段的角色
- 整理 RAG 歷史案例
- 生成初版 PRD
- 找需求矛盾、找漏掉的場景

但 **AI 不負責決策優先順序**。

#### PM 的最小產物：需求卡

至少包含：
- 背景 / 問題描述
- 目標結果
- 範圍 / 不做什麼
- 驗收標準
- 反例 / 邊界情境
- 風險等級（L0 / L1 / L2，見 `05-`）

#### 設計流程不一定每次都要

由 PM 根據需求價值與任務性質決定是否引入。**適合引入**的情況：
- 牽涉主要使用者流程
- 介面互動改動較大
- 對轉換率、操作效率、理解成本有明顯影響
- 需求本身還不夠具體，需要用畫面幫助收斂

最小產物視任務大小選一種：線框稿 / 簡單 flow 圖 / 高保真畫面 / 可執行 prototype。

### 階段 2：專業領域驗證（架構師 / 設計師 / SA）

#### 架構師的核心責任：技術可行性與系統邊界
- 系統架構、技術選型、scalability、reliability
- AI 可以幫忙生成架構草稿，但**架構師負責判斷 trade-off**

#### 設計師的核心責任：體驗是否成立
- 使用流程、UX 邏輯、介面原型
- AI 可以生成 UI，但**不能替代使用者理解**

#### SA 的核心責任：需求 → 系統 的翻譯者
- 系統流程、商業規則、資料結構、API、整合、例外情境、權限/workflow
- 工作本質：**讓需求變成可以被工程實作的系統描述**

#### 架構師的最小產物（依風險決定）
- L0：不一定需要獨立文件
- L1：1 頁設計約束
- L2：簡版 ADR / 架構決策記錄

內容至少涵蓋：影響模組、介面/schema 變更、不可破壞的 invariant、權限/資料隔離、非功能需求（效能/安全/穩定性）、L2 必須明確 rollout/rollback 策略。

### 階段 3：實作與知識回饋（工程團隊 / QA / SA）

#### 資深工程師
AI 可以寫很多 code，但資深工程師負責：
- 系統品質、技術決策、code review、風險控制

#### QA
AI 可以生成測試案例，但 QA 負責：
- 測試策略、風險優先順序、系統驗收

#### Agent 在這段
可以幫忙：生成測試案例、Code review、安全掃描、規格一致性檢查
但**最終驗收仍是人負責**。

## 四、L0 / L1 / L2 風險骨架

> 詳細風險定義請見 [`05-風險分層與五大品質門檻.md`](./05-風險分層與五大品質門檻.md)

### L0：低風險任務骨架
```text
需求卡 → 驗證 → Agent → Review
```
適用：UI 文案、單點 CRUD、log/註解、純樣板、低風險重構、測試補齊

### L1：中風險任務骨架
```text
需求卡 → 設計約束（簡版） → 驗證 → Agent → Review
```
適用：單服務功能開發、一般報表邏輯、既有 API 增修、小範圍 schema/flow 調整、中度業務邏輯變更

### L2：高風險任務骨架
```text
需求卡 → 架構/ADR → 驗證+rollout/backout → 受監督 Agent → 多人簽核 → 分段釋出
```
適用：跨服務協定變更、schema migration、權限模型、敏感資料、效能敏感、對外 API/workflow/infra、不可逆操作

特點：
- 不能只靠 Agent 自跑
- 必須有人持續監督
- 必須明確規劃 rollback / backout
- 合併與上線是兩個獨立判斷點

## 五、彈性合併原則（哪些可省、哪些不能省）

### 可合併一：需求定義 + PRD/Spec
對 70% 任務，不需要兩份文件。需求卡若已包含目標、範圍、驗收、反例、風險級別，就足夠讓 Agent 開始工作。

### 可合併二：架構 Review + Spec
對小團隊，很多時候架構 review 本質上只是 review 一份 1 頁設計約束，不需要再另外一份長篇 spec。

### 不能省的東西（不管任務大小）
- 明確的需求目標
- 最基本的設計邊界
- 驗證標準
- 人類 review
- 高風險任務的 rollout / rollback 思考

## 六、共同驗收標準（三層）

### 6.1 PM 的業務驗證
回答：功能是否符合需求卡定義 / 成功條件是否真的滿足 / 邊界情境是否被處理 / 是否符合優先序與範圍控制。

例子：
- 報表查詢時間從 5 秒降到 2 秒內
- 使用者能在 3 步內完成提交
- 新流程不影響既有關鍵任務完成率

### 6.2 架構的驗證
回答：介面是否一致 / API/schema 是否符合設計約束 / 權限與資料隔離是否安全 / perf baseline 是否明顯退化 / security checks 是否通過。

例子：
- API contract 不變或有版本策略
- schema migration 可回滾
- 不增加跨模組耦合
- P95 latency 不超過 baseline 的 10%

### 6.3 程式的驗證
回答：程式是否穩定可執行 / 關鍵邏輯是否有測試保護 / Agent 改壞時能不能被自動發現。

例子：
- 單元測試通過
- integration test 通過
- lint / type check 通過
- secrets scanning / security check 通過

### 驗證標準的最低要求

對每張可交給 Agent 的任務，至少要回答這三句：
1. **成功長什麼樣？**
2. **怎麼驗證成功？**
3. **失敗最可能發生在哪裡？**

如果這三句答不出來，**就不該交給 Agent 自主跑**。

## 七、可執行需求定義（Executable Requirements）

> 把任務交給 AI 前，先確保需求拆解明確、具體、可驗證。

### 不要寫
> 「提升性能」

### 要寫
> 「將報表生成時間從 5 秒降到 2 秒，Acceptance：在 10000 筆資料測試下達成」

### 5 個必練技能

1. **把需求翻譯成可觀測結果** —— 不是「改善效能」，而是「P95 從 5s → 2s」或「CPU < 60%」
2. **定義 DoD（Definition of Done）** —— 功能完成 ≠ 可上線；DoD 至少包含測試、文件、監控、回滾/feature flag（視風險）
3. **邊界條件與反例（Negative cases）** —— 你能寫出 3 個「會失敗的情境」，代表你真的懂需求
4. **切割成可獨立交付的最小單元** —— 一個 PR 一個主題、可回滾、可測試；把大需求拆成 3-7 張小卡，每張都有驗收
5. **規格寫作能力（清楚、無歧義、可追溯）** —— 用固定模板寫 20 次，會越寫越快（AI 也會跑越順）

### 個人訓練法（1 個月內很有感）
每週挑 1 個需求，自己先寫一張「交給 AI 的規格卡」（含 acceptance + test hints），再看 PR 被退回的原因，把退回原因分類：缺範圍？缺驗收？缺邊界？缺相依？缺非功能？兩週後就知道你真正薄弱的點。

## 八、Repo as Knowledge：Knowledge-as-Code + Template-Driven Agent

### Repo 結構建議

```
product-requirements-repo/
├── /context/                  # 上下文知識庫
│   ├── business/              # 業務邏輯、商業模式
│   ├── product/               # 產品願景、roadmap、策略
│   ├── users/                 # User personas, feedback, interview
│   ├── stakeholders/          # 利害關係人需求、constraints
│   ├── tech-constraints/      # 技術限制、ADR
│   └── design-system/         # UI/UX guidelines
├── /templates/                # 需求文件模板
├── /requirements/
│   ├── /drafts/               # Agent 生成的草稿
│   └── /reviewed/             # PM review 後的版本
├── /prompts/                  # Agent 的 system prompts
└── .github/copilot-instructions.md or AGENTS.md or CLAUDE.md
```

### 三個關鍵成功要素
1. **Context 品質 > Agent 能力**（垃圾進垃圾出）
2. **模板要有 opinionated structure**（不要只是空白文件）
3. **PM 要當 "Editor"，不是 "Writer"**（心態轉換）

### 實務上的三個坑

| 坑 | 解法 |
|----|------|
| Agent 產出太發散 | Template 要有明確 `Acceptance Criteria` section；prompt 加 `Maximum length: 500 words for each section`；用 Structured Output（YAML/JSON frontmatter） |
| 上下文太多 Agent 反而混亂 | Prompt 指定明確的 context files；超過 100 個文件考慮 RAG |
| PM 還是要 heavy review | AI 不取代 PM judgment，是「思考夥伴 + 初稿機」；設計 20% rule（期望 Agent 節省 20-30% 時間，不是 80%） |

## 九、AI 在流程中的定位

### Agent 主導、人類審核（適合）
- 需求卡初稿整理
- 規格初稿整理
- UI 草稿 / prototype
- 測試骨架生成
- 一般程式實作
- 重構 / 樣板 / CRUD
- PR 說明整理
- 第一輪自審

### 人類主導、Agent 輔助（適合）
- 價值判斷
- 需求優先序
- 架構邊界
- 驗證標準定義
- 高風險改動
- rollout / rollback 決策
- 最終 merge / release 判斷

## 十、AI 時代軟體團隊能力金字塔

```text
                ▲
                │
        產品與系統定義能力     ← AI 最難取代
        (Problem & System Definition)
        PM / Architect / Senior SA
                │
        ────────────────────────────────
                │
        系統設計與架構能力
        (System Architecture)
        Architect / Senior Engineer / SA
                │
        ────────────────────────────────
                │
        技術實作與工程能力
        (Engineering Implementation)
        Software Engineer
                │
        ────────────────────────────────
                │
        程式生成與輔助能力     ← AI 高度自動化
        (AI Coding / Code Generation)
        AI Agents / Coding Assistants
                ▼
```

**AI 主要衝擊底層能力，不是頂層能力**。

各層在 AI 時代的變化：
- **最底層（程式生成）**：高度自動化，Junior engineer 的價值會下降
- **技術實作層**：AI 加速 3-10 倍，但仍需技術理解、debugging、系統思維（人數需求可能下降）
- **系統設計層**：AI 可幫生成草稿、找 trade-off，但很難取代系統責任人
- **產品與系統定義層**：AI 最難取代，本質是**決策與責任**

### SA 的位置：產品與系統之間的橋樑

```text
產品世界 (PM)
    │
需求轉換 (SA)
    │
系統世界 (Architect / Engineer)
```

SA 核心能力是**結構化思考**：workflow、business rule、data flow、exception case、integration。AI 可幫忙生成文件，但很難完全理解企業流程與系統邏輯。SA 未來可能演化為 **System Designer / Product System Architect**。

---

## 十一、AI 時代最稀缺的能力

> AI 讓「做事的人」變多，但「定義事情的人」仍然稀缺。

未來最有價值的能力：
1. **問題定義能力**
2. **系統設計能力**
3. **跨領域整合能力**

而不是單純 coding。

## 十二、團隊角色降低不確定性對照表

```text
PM       → 降低「產品價值」的不確定性
架構師   → 降低「技術可行性」的不確定性
設計師   → 降低「使用體驗」的不確定性
SA       → 降低「系統邏輯」的不確定性
工程師   → 降低「實作品質」的不確定性
QA       → 降低「系統風險」的不確定性
```

AI 的作用：**加速產出，但不負責收斂風險。**

---

## 一句話濃縮

> 這不是一套重文件流程，而是一套「**以判斷權為核心、按風險分流、用最少文件讓 Agent 安全高效工作**」的 AI Coding 輕量流程。
> PM 負責價值，架構師負責邊界，QE 負責驗證標準，開發負責可維護性與合併判斷；L0 走短流程，L2 才補強控制點。

## 給團隊對齊的一句話

> 我們的開發流程不是為了寫更多文件，而是讓需求逐步收斂成「可設計、可開發、可驗證」的系統。AI 可以加速產出，但每一個角色仍負責收斂不同類型的不確定性。
