# 輕量開發流程：任務交辦與驗收

## TL;DR

- **三個核心原則**：角色按判斷權劃分（不按產出）、流程按風險分流（不一條路走到底）、文件只保留最少必要集。
- **三句驗收**：任何要交給 Agent 的任務，答不出「成功長什麼樣／怎麼驗證／失敗最可能在哪」，就不該交給 Agent 自主跑。
- **AI 加速產出，但不負責收斂風險**——每個角色仍負責收斂自己那類不確定性。

---

## 一、需求卡（交辦的最小單位）

至少包含：

- 背景 / 問題描述
- 目標結果
- 範圍 / 不做什麼
- 驗收標準
- 反例 / 邊界情境
- 風險等級（R0–R3，判準見 [`05-風險分層與五大品質門檻.md`](./05-風險分層與五大品質門檻.md)）

## 二、按風險分流的任務骨架

```text
R0/R1（低風險）：需求卡 → Agent → Review
R2（高影響）  ：需求卡 → 1 頁設計約束 → Agent → Review + 契約/整合測試證據
R3（不可逆）  ：需求卡 → 簡版 ADR + rollout/rollback → 受監督 Agent → 雙人簽核 → 分段釋出
```

- R2 的設計約束至少涵蓋：影響模組、介面/schema 變更、不可破壞的 invariant、權限與資料隔離。
- R3 特點：不能只靠 Agent 自跑、必須有人持續監督、合併與上線是兩個獨立判斷點。

## 三、三句驗收 + 三層驗收標準

對每張可交給 Agent 的任務，至少回答：

1. **成功長什麼樣？**
2. **怎麼驗證成功？**
3. **失敗最可能發生在哪裡？**

驗收分三層：

| 層 | 回答的問題 | 例子 |
|---|-----------|------|
| PM 業務驗證 | 是否符合需求卡定義、成功條件是否真的滿足、邊界情境是否處理 | 報表查詢 5 秒降到 2 秒內；3 步內完成提交 |
| 架構驗證 | 介面一致、schema 符合約束、權限隔離安全、效能無明顯退化 | API contract 不變或有版本策略；migration 可回滾；P95 不超 baseline 10% |
| 程式驗證 | 穩定可執行、關鍵邏輯有測試保護、Agent 改壞能被自動發現 | unit/integration test、lint/type check、secrets scanning 通過 |

## 四、可執行需求定義（5 個必練技能）

不要寫「提升性能」；要寫「報表生成 5 秒降到 2 秒，Acceptance：10000 筆資料下達成」。

1. **把需求翻譯成可觀測結果**——不是「改善效能」，是「P95 從 5s → 2s」
2. **定義 DoD**——功能完成 ≠ 可上線；至少含測試、文件、監控、回滾（視風險）
3. **邊界條件與反例**——能寫出 3 個「會失敗的情境」才代表真的懂需求
4. **切割成可獨立交付的最小單元**——一個 PR 一個主題、可回滾、可測試；大需求拆 3-7 張小卡
5. **規格寫作能力**——用固定模板寫 20 次，會越寫越快，AI 也跑越順

**個人訓練法**：每週挑 1 個需求，先寫「交給 AI 的規格卡」，再把 PR 被退回的原因分類（缺範圍？缺驗收？缺邊界？缺非功能？），兩週後就知道自己薄弱在哪。

## 五、不能省的東西（不管任務大小）

- 明確的需求目標
- 最基本的設計邊界
- 驗證標準
- 人類 review
- 高風險任務的 rollout / rollback 思考

其餘文件能合則合：70% 任務的需求卡即是 spec；小團隊的架構 review 通常就是 review 一頁設計約束。

## 六、AI 在流程中的定位

**Agent 主導、人類審核**：需求卡初稿、規格初稿、prototype、測試骨架、一般實作、重構/樣板/CRUD、PR 說明、第一輪自審。

**人類主導、Agent 輔助**：價值判斷、需求優先序、架構邊界、驗證標準定義、高風險改動、rollout/rollback 決策、最終 merge/release。

---

## 一句話濃縮

> 以判斷權為核心、按風險分流、用最少文件讓 Agent 安全高效工作。R0/R1 走短流程，R2/R3 才補控制點。
