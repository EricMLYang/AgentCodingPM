# 工具地圖與防線設計

## TL;DR

- **核心命題**：到 2026-03，AI 不只是寫 code，已被正式放進 PR review、CI 驗測、資安 triage、品質 gate。**真正有價值的不是單一神奇 agent，是把多層防線組起來**。
- **Coding Agent 四大架構**：CLI-First（Claude Code / Aider / Codex CLI）/ IDE-Native（Cursor / Windsurf / Cline / Roo Code）/ 編排平台（Codegen / Devin）/ 開源 IDE（Cline / Roo Code）
- **AI Code Review 6 層防線**：PR Reviewer → 確定性 SAST Gate → 上下文型安全 agent → 測試生成與真實執行 → 測試經濟學 → 維護性 Gate
- **小團隊組合**：Copilot/CodeRabbit + CodeQL/Semgrep + Playwright + SonarQube
- **趨勢**：少抓多但準（提升 signal-to-noise）；context-aware 比 diff comment 強；不再執著「是不是 AI 寫的」，而是把新 code 一律放進更嚴格 gate
- **最小有效脈絡（ETH 研究）**：過度詳盡的 AGENTS.md 讓任務成功率**降 3%**、推理成本**升 20%+**；應省略自動生成冗長文件，只留高階商業意圖與專案特定指令

## 為什麼這篇是工具參考

當你要決定「我們團隊買哪個 AI Code Review？」、「Claude Code vs Cursor 該推哪個？」、「Anti-Slopsquatting 用什麼工具？」時，先看這篇。

## 一、Coding Agent 四大架構

| 架構 | 代表 | 特性 | 適用 |
|------|------|------|------|
| **CLI-First** | Claude Code、Aider、Codex CLI | 命令列環境、深度權限（讀 repo / 跑 shell / 改檔 / 跑測試）、與 Git 工作流無縫接軌 | 複雜問題解決、跨檔案重構、不熟悉的龐大程式碼庫 |
| **IDE-Native** | Cursor、Windsurf、VS Code 的 Roo Code / Cline | 嵌入編輯器、即時視覺化回饋 | 日常功能開發、視覺化重構 |
| **企業編排平台** | Codegen、Devin | 完全隔離沙盒、合規認證、深度治理 | 企業生產環境、合規要求高 |
| **開源 IDE 擴充** | Cline、Roo Code | VS Code 擴充、MCP 原生、零加價 API | 注重隱私、本地控制、零加價 |

### 主要工具速查表

| 工具 | 類別 | 關鍵特性 | 定價 |
|------|------|---------|------|
| **Claude Code** | CLI 商業 | 深度推理、跨檔案重構、平行處理優異 | 20-200 USD/月（依 API 量）|
| **Cursor** | IDE 商業 | 並行 agent、極速重構 | 16 USD/月起（點數）|
| **Codex CLI** | CLI 商業 | OpenAI 出品、有 plan mode、雲端平行 | API 量計 |
| **Aider** | CLI 開源 | Git 原子提交、100+ 語言 | 免費（API 費）|
| **Codegen** | 企業編排商業 | ClickUp 整合、SOC2 | 企業報價 |
| **Devin** | 雲端自主商業 | PR 提交、67% 合併率 | 20 USD/月 + 運算單元 |
| **Cline** | 開源 IDE | 計畫/執行分離、零加價 | 免費（API 費）|
| **Roo Code** | 開源 IDE | 多人格、自訂模式市集 | 免費（API 費）|

### Cline vs Roo Code 的兩種哲學
- **Cline** = 零加價（Zero Markup）+ 嚴格「計畫與執行分離」+ 手動批准 →  注重隱私與絕對控制權
- **Roo Code** = Cline 分支 + 多人格 + 高自主性 + 多代理協作 → 追求極致迭代速度

## 二、最小有效脈絡（Minimal Effective Context）—— ETH Zurich 研究

### 顛覆性結論
過度詳盡、由 LLM 自動生成的 `AGENTS.md` / `CLAUDE.md` **對代理表現有負面影響**：
- 任務成功率**下降約 3%**
- 因引入不必要需求與冗餘資訊，代理需要更多推理步驟，**推理成本大幅增加 20% 以上**

### 為什麼？
AI 代理的行為陷阱是「**過於服從**」。當 context 包含詳盡但不必要的 codebase 概述時，代理嚴格遵守這些多餘指示，反而把簡單任務複雜化。

現代強大基礎模型已具備足夠參數化知識，理解常見函式庫與架構模式，過多外部提示反而成為干擾性噪音。

### 最佳實務

**省略**：自動生成的冗長目錄列表、架構概述
**保留**：
- 高階商業意圖
- 非直覺的專案特定工具指令
- 特殊風險點

即使是人類精心撰寫的脈絡檔案，也僅能帶來約 4% 的邊際效能提升 —— 證明**簡潔性比完整性重要**。

## 三、AI Code Review 6 層防線（核心架構）

> 真正有價值的不是押注單一神奇 agent，是把多層防線組起來。

### 第 1 層：PR / MR 的 AI Reviewer

**目標**：不是放行，而是先做第一輪高覆蓋檢查（bug、漏測、風格、潛在安全、說明不完整）。

| 工具 | 平台 | 分析深度 | 誤報率 | 月費（USD/user） |
|------|------|---------|-------|----------------|
| **Graphite Agent** | GitHub | 深度（全 codebase + Stacked PRs） | 約 3% | 40 |
| **Greptile** | GitHub, GitLab | 深度（預先索引全 codebase） | 最高（換廣度） | 30 |
| **CodeRabbit** | GitHub, GitLab, Bitbucket, Azure | 表面（diff 分析） | 中等 | 24-30 |
| **GitHub Copilot CR** | GitHub | 表面（diff 分析） | 中等 | 10-39（套件內） |
| **BugBot** | GitHub | 中等（8 次迭代 diff） | 低-中 | 40 + Cursor 費 |
| **Qodo** | 多平台 | 深度（SDLC 自動化 + 人機協作） | 低（受治理約束） | 企業報價 |
| **GitLab Duo** | GitLab | 深度（看 changes / comments / issues / repo / cross-file） | - | GitLab 套件 |

### 第 2 層：確定性安全掃描當 blocking gate

可重現、可治理、可 audit。適合「阻擋 merge」或最低基線。

| 工具 | 特性 |
|------|------|
| **GitHub CodeQL** | 結果變成 GitHub code scanning alerts |
| **Semgrep Code** | 確定性 static analysis + LLM contextual reasoning（混合模式）；可接 CI/CD |
| **Snyk Code** | AI-based engine、低誤報導向；進 IDE / repo / CI |
| **SonarQube** | quality gate 決定過不過 |

### 第 3 層：上下文型安全 agent（2025-2026 真正升級的地方）

抓傳統掃描器難抓的問題（auth logic、跨檔案權限、business logic flaw）。

| 工具 | 特性 |
|------|------|
| **OpenAI Codex Security** | 先建專案 threat model，再做漏洞搜尋、驗證、修補建議；sandboxed validation 環境壓測，降低噪音 |
| **Claude Code Security** | 上下文理解 + 系統信任邊界 |
| **Semgrep AI-powered detection** | 確定性 SAST + LLM 推理；抓 IDOR 和 broken authorization |

### 第 4 層：測試生成與真實執行驗證

「不要只看起來合理，要跑起來」。

| 工具 | 特性 |
|------|------|
| **Diffblue Cover** | 自動產 Java / Kotlin unit tests，sandbox 中執行 |
| **Playwright Test Agents** | 根據 Markdown plan 產測試，即時驗證 selector 與 assertion |
| **QA Wolf** | 三代理（Mapping / Automation / Maintenance）+ 自癒性測試 |

### QA Wolf 的自癒性測試六層
1. **時間自癒**：處理非同步 API 延遲導致的順序錯誤
2. **執行期錯誤自癒**：隔離應用程式崩潰並設定重試
3. **測試資料自癒**：偵測並恢復過期連線階段或無效虛擬資料
4. **視覺斷言自癒**：電腦視覺驗證 Canvas / PDF，過濾像素級別差異
5. **互動變更自癒**：處理被選單遮擋的元素
6. **選擇器自癒**：因應 DOM 結構屬性變更

### 第 5 層：測試經濟學優化

當 AI 讓改動頻率與變更量變大，測試成本也會爆。

| 工具 | 特性 |
|------|------|
| **Launchable** | predictive test selection：不是每次全跑，而是優先挑最可能失敗、最能快速驗證風險的測試 |

特別適合 agent 開發（agent 常做很多小步迭代與多輪修補）。

### 第 6 層：品質與維護性 Gate（最容易少做）

| 工具 | 特性 |
|------|------|
| **SonarQube** | reliability / security / security review / maintainability 做成 gate |
| **GitHub / GitLab / CodeRabbit** | 越來越依賴 custom instructions，把團隊架構規則、檔案路徑規則、code style、風險重點明文化 |

**核心點**：維護性檢查不只是 complexity 指標，而是**把「你們團隊真正介意的維護成本」寫進 review policy**。

## 四、自動化驗測四大類

| 類別 | 機制 | 可攜性 | 代表 |
|------|------|--------|------|
| **代理化自動測試** | 產出決定性 Playwright / Appium 程式碼，可重現、可稽核 | 程式碼儲存於用戶端、無供應商鎖定、跨平台 | QA Wolf |
| **代理化手動測試** | 電腦操作代理 + LLM 視覺動態執行，**非決定性、高 token** | 依賴供應商 runtime、難整合 CI/CD、可能隱藏回歸錯誤 | Mabl、Testim、Functionize |
| **IDE 協同副手** | 編輯器內生成測試框架程式碼 | 需自行維護基礎設施 | GitHub Copilot、Cursor、Claude Code |
| **對話錄製器** | 記錄並重播真實使用者 DOM 變更與網路請求 | 僅瀏覽器端、無法驗證後端、隱私風險 | Meticulous、Replay.io、Checksum |

**選擇關鍵**：系統是生成「團隊可擁有、可審查的決定性程式碼」，還是依賴執行階段動態調整的非決定性行為？前者才是企業級 QA 的黃金標準。

### LLM 評估開源框架
- **DeepEval**：類 Pytest 測試結構，內建 30+ 種正確性 / 一致性 / 相關性 / 幻覺偵測指標
- **Arize Phoenix**：開源 LLM 可觀察性，記錄每次模型呼叫
- **Opik**：端到端測試追蹤 + LLM-judge metrics 自動化
- **RF-MCP（Robot Framework）**：讓 LLM 在生成腳本前先在真實執行階段做關鍵字探勘，根除幻覺指令

## 五、資安檢查與 DevSecOps 代理化

### 從「掃描修補」到「設計即安全」

| 工具 | 防禦領域 | 運作層級 |
|------|---------|---------|
| **Checkmarx One Assist** | 代理化 AppSec（SAST、開源漏洞、IaC、容器） | IDE → CI/CD 全生命週期 |
| **Checkmarx Developer Assist** | 開發者優先 IDE 即時漏洞預防 | IDE 原生即時掃描 |
| **OX Security** | 脈絡感知風險決策、整合可視性 | 生產環境拓樸 + CI/CD 追蹤 |
| **Snyk** | 安全技術債重構、自動化修補 | SDLC 內依賴與弱點修復 |

### AI 供應鏈安全（AI SCS）
2026 年新興概念，從傳統 SBOM 延伸至：
- AI 物料清單（**AI-BOM**）
- 管線物料清單（**PBOM**）
- 偵測 LLM、MCP server、AI agent 框架、prompt 資料集
- 偵測模型下毒（Model Poisoning）、不安全反序列化、Pickle/Torch Gadget

**Snyk AI-BOM**：把 models / datasets / agents / tools / MCP server-client 關係映射成依賴圖。

### 合規自動化
- **Secureframe** —— SOC 2 自動化準備
- **LogicGate** —— 高度可自訂合規工作流
- **OneTrust** —— 隱私管理與資料防護
- **Sprinto** —— 新創公司快速合規

對應法規：歐盟 EU AI Act（2026 年 8 月全面生效）、NIST AI RMF、ISO 42001。

## 七、判斷工具的 5 個準則

### 1) 不要只看「找出幾個問題」，要看「每 10 個 comment 有幾個真的值得修」
CR-Bench 已提醒：resolution rate 不足以衡量 AI reviewer，雜訊會拖垮整體效益。

### 2) 不要把 AI reviewer 當 merge approver
官方文件幾乎都把這些工具定位成 review / triage / remediation assistant，不是替代人類責任。

### 3) 真正高價值的是「有上下文」
GitHub / GitLab / Semgrep 都在強調 custom instructions、linked issues、threat models、design docs、project-specific context。沒有這些，review 很容易只剩 generic 建議。

### 4) 維護性問題正在變大，不只是安全問題
GitClear 資料指出，AI-assisted code 出現 duplicated code 上升、short-term churn 上升、moved lines 下降。沒有 refactor gate 與結構檢查，技術債會比以前更快累積。

### 5) Sandbox 與權限邊界會越來越重要
Diffblue test generation 強調 sandbox；Anthropic Claude Code on the web 強調 isolated environment 與 network/filesystem restrictions；Sonar 已把「AI agent code execution without sandboxing」列為 security-sensitive。

## 八、落地組合建議

### 小到中型團隊（5-20 人）
1. **PR reviewer**：GitHub Copilot / CodeRabbit / GitLab Duo 擇一
2. **Blocking scan**：CodeQL 或 Semgrep / Snyk 擇一
3. **測試**：既有 CI 單元測試 + Playwright E2E
4. **品質 gate**：SonarQube，至少把 lint / coverage / complexity / security scan 做成 merge gate
5. **高風險模組**：再加 contextual security scan

### 較成熟或高風險團隊
- AI PR reviewer 做廣覆蓋
- CodeQL / Snyk / Semgrep 做 deterministic gate
- Codex Security / Claude Code Security / Semgrep AI detection 抓 business logic 與 auth 問題
- Diffblue / Playwright / QA Wolf 做執行驗證
- Sonar 做 maintainability / reliability gate
- Snyk AI-BOM 做 AI 供應鏈盤點

## 九、近期重要趨勢觀察

### Sonar 的指標
2026.1 把「自動偵測 AI code」標為 **deprecated**，理由是高 AI adoption 下要調整做法。意思：未來不再執著「這段是不是 AI 寫的」，而是把新 code 一律放進更嚴格的品質、可維護性、安全門檻。

### AI agent 本身成為新的資安對象
- 國際 AI 安全報告 2026 明講：general-purpose 與 agentic models 的安全與風險治理仍有顯著證據缺口
- Sonar 已加入「AI agent code execution without sandboxing is security-sensitive」規則
- Snyk 開始做 AI-BOM 把 models / datasets / agents / MCP 連線都納入供應鏈盤點

### 從規則型到「上下文 + 規則引擎」混合
Semgrep 把產品描述成「**確定性 static analysis + LLM contextual reasoning**」的組合，抓傳統 SAST 不容易抓的 business logic flaw（IDOR / broken authorization）。

### Review 工具從 diff comment 到 repo-aware
Copilot CR、GitLab Duo、Graphite、CodeRabbit、Qodo 已經不是只看幾行 diff，而是看 changes / comments / linked issues / repo structure / cross-file dependencies。

### 訊號品質 > 找到更多問題
最新研究指出 AI code review agents 若一味追求抓出所有隱藏問題，常會出現 **low signal-to-noise ratio**。OpenAI Codex Security 把「higher-confidence findings」當主賣點。市場從「多抓」轉向「少但準」。

---

## 十、一句話結論

> **不是讓 AI 取代 review，而是讓 AI 把 review、驗測、資安、品管從「人工抽查」變成「高頻、低延遲、可配置、可持續的系統」。**
>
> 真正的瓶頸不在生成 code，而在**訊號品質、上下文注入、真實驗證、與風險分級**。短期內最強的做法不是押注單一神奇 agent，是把多層防線組起來。
