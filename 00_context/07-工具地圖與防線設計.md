# 工具防線設計

## TL;DR

- **核心命題**：AI 已進入 PR review、CI 驗測、資安 triage、品質 gate。真正有價值的不是押注單一工具，是**把多層防線組起來**。
- **最小有效脈絡**：過度詳盡的 AGENTS.md 讓任務成功率降 3%、推理成本升 20%+——簡潔比完整重要。
- **趨勢立場**：不再執著「是不是 AI 寫的」，而是把新 code 一律放進更嚴格 gate；市場從「多抓」轉向「少但準」。
- **具體工具與價格會過期**：本檔只留架構與準則，選型時再查當期市場。

---

## 一、最小有效脈絡（ETH Zurich 研究）

過度詳盡、由 LLM 自動生成的 `AGENTS.md` / `CLAUDE.md` 對 Agent 表現有**負面**影響：任務成功率下降約 3%，推理成本增加 20% 以上。原因是 Agent「過於服從」——冗餘指示會把簡單任務複雜化。

**省略**：自動生成的冗長目錄列表、架構概述。
**保留**：高階商業意圖、非直覺的專案特定指令、特殊風險點。

即使人類精心撰寫的脈絡檔也只帶來約 4% 邊際提升——**簡潔性比完整性重要**。

## 二、六層防線架構

| 層 | 目標 | 代表工具類型 |
|---|------|-------------|
| 1. AI PR Reviewer | 第一輪高覆蓋檢查（bug、漏測、潛在安全），是預選賽不是放行 | GitHub Copilot CR、CodeRabbit、Graphite 等 |
| 2. 確定性掃描 Gate | 可重現、可稽核，適合當 blocking gate | CodeQL、Semgrep、Snyk、SonarQube |
| 3. 上下文型安全 Agent | 抓傳統掃描難抓的 auth logic、跨檔案權限、business logic flaw | Codex Security、Claude Code Security、Semgrep AI |
| 4. 測試生成與真實執行 | 「不要只看起來合理，要跑起來」 | Playwright Test Agents、Diffblue 等 |
| 5. 測試經濟學 | 改動頻率變大後，不是每次全跑，優先挑最可能失敗的測試 | predictive test selection 類 |
| 6. 品質與維護性 Gate | 把「團隊真正介意的維護成本」寫進 review policy，不只 complexity 指標 | SonarQube quality gate + custom instructions |

**自動化驗測的選擇關鍵**：系統是生成「團隊可擁有、可審查的**決定性程式碼**」，還是依賴執行階段動態調整的非決定性行為？前者才是可稽核的黃金標準。

---

## 三、判斷工具的 5 個準則

1. **不看「找出幾個問題」，看「每 10 個 comment 有幾個值得修」**——雜訊會拖垮整體效益。
2. **不把 AI reviewer 當 merge approver**——官方定位都是 assistant，不替代人類責任。
3. **高價值來自「有上下文」**——custom instructions、linked issues、threat model；沒有這些只剩 generic 建議。
4. **維護性問題正在變大**——沒有 refactor gate，技術債比以前累積更快。
5. **Sandbox 與權限邊界越來越重要**——「AI agent code execution without sandboxing」已被列為 security-sensitive。

---

## 四、落地組合建議（5-20 人團隊）

1. **PR reviewer**：Copilot / CodeRabbit / GitLab Duo 擇一
2. **Blocking scan**：CodeQL 或 Semgrep / Snyk 擇一
3. **測試**：既有 CI 單元測試 + Playwright E2E
4. **品質 gate**：SonarQube——lint / coverage / complexity / security 做成 merge gate
5. **高風險模組**：再加 contextual security scan

## 一句話結論

> 不是讓 AI 取代 review，而是讓 AI 把 review、驗測、資安、品管從「人工抽查」變成「高頻、低延遲、可配置、可持續的系統」。瓶頸不在生成 code，在**訊號品質、上下文注入、真實驗證、風險分級**。
