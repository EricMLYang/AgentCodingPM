將扮演約 40 人團隊的 AI 時代工作方式推手

一個處，兩個部，每個部約 20人，我是屬於某一個部，但命令是處長下的，大家都要配合


希望能把 AI 時代的工作方式帶入團隊，

目前團隊性質大略分類：

1. 韌體 Team，開發能驅動面板的 Box 軟體，需要跟各種面板的 CMS 播放器溝通（尤其是 電子紙、電子標籤...等新產品）整合

2. CMS 播放器協助維運：公司是面板製造為主，因此衍伸的解決方案中 CMS (Content Management System) 是重要一環，有 Team 再協助

3. 新應用系統 Team，有 Java 也有 C# ASP.NET 的技術，前端有 Vue.js 和 React

4. 數據價值相關系統：有數據平台、數據分析、數據可視化等相關系統，技術棧目前以 Databricks 為主，例如廣告投放分析

5. 公司內部 Agent 應用優化：我們也要支援公司內部的效率提升，協助開發各種內部 Agent，技術是以 Databricks 和 各種 LLM 應用為主



===
# 1. mabl:25 人工程團隊,把 Agent Coding 做成跨 75+ repos 的平台化工程基礎設施

> **一句話結論(全文核心)**
> mabl 這個案例**不是證明「大家要多用 Copilot」**,而是證明:**團隊級 Agent Coding 需要 cross-repo context、skills/MCP、validation、PR governance,以及人類最後 approve 的紅線**。對我們處級規模(40 人、跨韌體 / CMS / 應用 / 數據 / Agent 五條技術線)要落地「AI 時代工作方式」,這是目前最完整、最務實的可參考工程藍圖。

---

## 一、關於 mabl(背景脈絡)

### 1.1 公司簡介

mabl 是 2017 年由前 Google 工程師 Dan Belcher 與 Izzy Azeri 創辦的 **AI-native / agentic testing platform**。他們做的**不是單純取代 Selenium 或 Cypress 腳本**,而是把 low-code 測試建立、AI 自我修復、視覺驗證、測試執行、失敗分析、agentic 測試 workflow 整合成一個 AI 驅動的測試自動化平台。

客戶案例包含 **Mercedes-Benz、LendingClub Bank、JetBlue、Workday、Vivid Seats** 等企業(以 mabl 官方 2026 年 actively 引用的代表客戶為準)。

### 1.2 兩階段轉型:從「ML 工具」到「AI Agent 平台」

很多人會問:「2017 年就創辦,但 AI Agent 是這 1 年才紅,怎麼能說 mabl 是 agent 領域的老兵?」這是個合理的提問,實際上 mabl 經歷了一段**清楚的兩階段轉型**:

#### 階段一(2017–2022):ML 驅動的測試自動化

mabl 早期的「AI」主要不是今天的 LLM Agent,而是偏**傳統機器學習、電腦視覺、auto-healing(UI 改了測試不會壞)、視覺迴歸測試、low-code 測試**。解的是「Selenium 腳本太難維護」這個老問題,賣的是 SaaS 工具——客戶買單是因為養 SDET 貴,而 mabl 讓 QA / PM 都能建測試。

這階段他們累積了兩個關鍵資產:**測試領域的 ML 知識** 與 **可靠的測試執行引擎**。

#### 轉折(2023–2024):看見 LLM 浪潮但沒立刻跟風

ChatGPT 出來後,測試自動化領域出現一堆「AI-powered testing」新創,大多是把 ChatGPT 包在傳統工具上面、用自然語言生 Selenium 腳本。mabl 觀察到這波但**沒有立刻跟風**——他們判斷單純包 LLM 解不了核心問題(LLM 寫的腳本一樣會壞、一樣不知道 UI 結構)。

#### 階段二(2025 起):Agentic Tester——從「自動化工具」變「AI 同事」

**2025 年上半年,mabl 明確把產品敘事推向 agentic testing**。2025 年 6 月 18 日發布 Test Creation Agent(自然語言自動建構端到端測試)、Auto TFA(自動測試失敗分析)、Visual Assist(視覺輔助元素辨識)等 agentic AI 能力。

到 2025 年 10 月 22 日的年度用戶大會 mabl Experience,他們宣布 agentic testing 採用率成長了 10 倍。

mabl 的「先做後說」風格值得注意:他們在 2025 年出貨第一代 agent 後,以實際 production 資料(來源:mabl 2026-02-25 部落格〈Rebuilding an AI Agent the Right Way〉)重構整個系統——這證明他們是**用資料驅動 agent 設計**,而不是貼牌。

#### 階段三(2026):Active Coverage + 全面 Dogfooding

2026 年 4 月 23 日,mabl 發布「Active Coverage」概念——quality validation 必須跟上 AI coding agent 的速度。同期發布的 2026 State of Quality Engineering Report(mabl 自家委託、996 位美英軟體專業人員調查)指出:41% 認為 AI 改善了程式碼品質,37% 認為 AI 讓程式碼出得更快但品質下降。

> **引用注意:** 這份調查是 mabl 自家發布的,讀者(尤其是決策者)可能會質疑「業者自己做的調查、自然支持自家產品」。引用時應該定位成「**行業趨勢訊號**」而非中立研究結論。真正最強的說服彈藥還是 mabl **自己工程團隊的 dogfooding 數據**(內部實測,可信度更高)。

也是這個時間點,他們的工程主管 Geoff Cooney 寫出我們在看的這篇〈75+ Repos〉文章——**用自家產品開發自家產品的工程治理紀實**。

### 1.3 為什麼這段歷史對我們重要

兩個關鍵訊號:

**訊號一:「AI 工具」與「AI Agent 基礎設施」是兩個不同的世代。** 大多數企業現在卡在第一波(個別開發者用 Copilot / Cursor),mabl 已經走完第一波、進入第二波(團隊級 agent 基礎設施)。我們處長要推的「AI 時代工作方式」如果只停在第一波,半年內就會被同業追上。

**訊號二:轉型路徑是「在既有資產上長出 agent 層」,不是打掉重做。**

但這裡有一個**對我們特別重要的差別必須點出來**:

| | mabl 的既有資產 | 我們的既有資產 |
|---|---|---|
| 形態 | **單一產品的縱向深化**(同一個測試平台越來越強) | **橫向多元並存**(韌體 / CMS / 應用 / 數據 / Agent 五條技術線) |
| Agent 化路徑 | 把單一產品包成 MCP server | 為**每條技術線各自**包 MCP server,再用 Repo Coordination Graph 把它們**串起來** |
| 治理重點 | 同一產品內部的 PR governance | 跨技術線的 ownership / 介面契約 / release order |

換句話說,我們不能直接複製 mabl 的縱向 agent 化路徑——**我們需要做的是「橫向整合層」,治理難度更高,但 Repo Coordination Graph 的價值也更大**。

## 二、〈75+ Repos〉文章核心內容

### 2.1 一句話定位

mabl 25 位工程師、管理 100+ repositories(其中 **75+ repos 納入 agent 系統覆蓋**),建立四層架構:**Cross Repo Base + 每 repo 的 CLAUDE.md + 3 個核心 MCP Servers + 36+ reusable Skills + AI PR Review + Auto-fix workflow**,把 agent 從個人助手升級成團隊級工程基礎設施。

### 2.2 痛點起點(這段最像我們)

2025 年 8 月,mabl 約 10% commits 是 AI-assisted,完全來自個別工程師 ad-hoc 使用工具;到 2026 年 2 月,這個數字達到 39% 整體、60% 在 infrastructure repo。問題不是「能不能讓 agent 寫程式」,而是「**怎麼讓 25 位工程師安全地在 75+ repos 上協作使用 agent**」。

mabl 提出 5 個 scaling 痛點,每一個我們都會遇到:

1. **跨 repo 協調**:當一個 feature 跨三個 repo,agent 怎麼知道誰相依誰?merge 順序怎麼決定?
2. **開發遠不只寫程式**:看 Jira、本地建置、回應 PR feedback,這些對 agent 比對人類更重要
3. **AI 速度下,human review 變瓶頸**:throughput 提高 3-5x,不可能讓人 review 300 PRs/週
4. **Operations 規模化挑戰**:PR 量級提高一個 order of magnitude,build / release pipeline 先撐不住
5. **Quality 必須上下移動**:速度提高 + 高層次規格化 → 自動化必須更可靠

### 2.3 四層架構

#### Layer 1:Cross Repo Base(共用上下文)

一個 pseudo mono-repo,放共同規範、工程指南、設計模式、Java/TS 最佳實踐、Google Cloud 與內部工具規範、可重用 skills。每個 repo 仍維護自己的 `CLAUDE.md`,描述 repo purpose、architecture、dependencies、開發慣例、step-by-step workflows。

**Repo Coordination Graph(這是最值得參考的單一元件)**:850+ 行的 dependency / ownership / release order 註冊表,涵蓋 79 repositories,包含 dependency graph、Pub/Sub topic 對應、資料表 ownership、release ordering。當 agent 跨 repo 改東西時查這張圖。

成果:「context drift(agent 中途忘記專案慣例)從約 40% 的失敗原因,降到 < 5%」。

#### Layer 2:Skill System(MCP Servers + Reusable Skills)

整合三個核心 MCP server:
- **Atlassian MCP**:agent 可查 Jira ticket、改狀態、加註解、搜尋 Confluence
- **mabl Testing MCP**(自家產品):agent 可觸發測試、解析結果、判斷是 flaky test 還是 regression
- **Desktop Automation MCP**:用 Playwright 跑 UI 互動、截圖,解決「Teaching Agents to See」問題

加上 **36+ reusable Skills**(總共近 40 個 unique skills),分五類:Workflow、Cross-repo build、Validation、Analysis & Planning、Operations。Validation skills 特別值得注意——他們為每個技術棧各建一套(Java/Gradle、React/Vitest、TypeScript/Jest、Playwright/Electron),並有 **validation router** 依照變更檔案自動選測試。

#### Layer 3:Operations & Governance

關鍵紅線:**AI 不能 approve PR,只能 `REQUEST_CHANGES` 或 `COMMENT`,merge 永遠由人決定**。

- **AI Code Review**:每個 PR 自動觸發 claude-pr-review workflow,拉 cross-repo-base 規則 + 該 repo 的 CLAUDE.md
- **Auto-Fix Agents**:只處理小事(linter、漏 import、簡單型別錯誤),且有 **circuit breaker**——連續兩個 [auto-fix] commit 就停;PR 作者 revert 過某個 auto-fix 就不再嘗試
- **PR Slash Commands**(ChatOps):/claude-review、/run-integration-tests、/deploy-preview 等

#### Layer 4:把上面三層串成自動化 workflow(留待 Part 2)

四階段 pipeline 處理單一 ticket,有 confidence-based gating 決定 agent 何時自主前進、何時停下問人。

### 2.4 量化成果

2026 年 2 月,mabl 在 application repos 達到 370+ PRs/月(2025/8 為 230/月);AI code review 在人類 reviewer 投入時間之前先攔截問題;auto-fix agent 解決平凡的 CI 失敗(漏分號、未使用 import、型別錯誤)無需人類介入。

## 三、與我們情境的相似度與差異

### 3.1 我們的情境簡述

- **組織**:約 40 人、一個處兩個部、命令來自處長
- **我的位置**:屬於其中一個部,需橫跨另一個部協作
- **5 條技術線**:
  1. **韌體 Team**:驅動面板的 Box 軟體,要跟各種面板 CMS 播放器溝通(電子紙、電子標籤等新產品)
  2. **CMS 播放器維運**:面板製造衍伸的解決方案
  3. **新應用系統**:Java + C# ASP.NET,前端 Vue.js + React
  4. **數據價值系統**:Databricks 為主的數據平台、分析、可視化(如廣告投放分析)
  5. **公司內部 Agent 應用**:Databricks + 各種 LLM 應用

### 3.2 相似度評估:★★★★☆(原本 ★★★★★ 過度樂觀)

**規模高度相似:** 25 人 vs 40 人,都屬於「個人 ad-hoc 用 agent 的天花板已經摸到、必須走向團隊化」的階段。

**架構需求高度相似:** 跨 repo、需要 MCP / Skills / Review / Governance、要把開發流程而非只有寫程式 agent 化——這些痛點我們**比 mabl 更嚴重**。

### 3.3 關鍵差異(對我們是更難而非更簡單)

| 維度 | mabl | 我們 |
|---|---|---|
| 技術棧 | Java/Gradle、TypeScript/React、Electron、Playwright,**單一產品線** | 韌體 Box + CMS + Java + C# ASP.NET + Vue + React + Databricks + LLM Agent,**5 種異質技術棧並存** |
| 既有資產形態 | 單一產品的縱向深化 | 橫向多元並存 |
| 組織 | SaaS 公司,單一工程組織 | 跨「一個處、兩個部」,需要橫向協調 |
| 整合複雜度 | 純軟體 SaaS | 韌體要跟各種面板 CMS 播放器溝通,**軟硬整合 + 多代產品並存** |
| 推動者位置 | 工程主管直接拍板 | 我屬於兩個部之一,要橫跨另一個部協作 |
| 破壞性風險 | 軟體 bug 可快速 hotfix | 韌體 bug 影響面板出貨;Databricks production pipeline 影響業務報表 |

**結論:mabl 的架構藍圖直接適用,但我們的治理難度高一個量級。** 他們的 Repo Coordination Graph 對我們不是 nice-to-have,是**剛需**——因為韌體 ↔ CMS ↔ 應用系統 ↔ 數據平台的 ownership 與 release order,比 mabl 嚴重得多。

## 四、可直接借鑑的 5 件事(從 mabl 的 3 件擴充)

### 借鑑 1:建一個 cross-repo-base repo

放共用規範、Java / C# / TypeScript 各自最佳實踐、設計模式、標準工作流、security constraints、技能入口。每個 repo 仍保留自己的 `CLAUDE.md`。

**對應我們:** 韌體、CMS、應用系統、Databricks、Agent 應用各有自己的工程慣例,但跨 team 的「合作介面規則(資料格式、API 命名、發版流程)」應該抽到共用 base。

### 借鑑 2:建 Repo Coordination Graph(我們的最高優先級)

mabl 的 850+ 行 dependency/ownership/release order registry,涵蓋 79 個 repositories,包含資料表 ownership、Pub/Sub topic 對應、release ordering。

**對應我們:** 這是**對我們價值最高的一塊**。韌體改 Box 軟體 API 會影響 CMS 播放器;CMS 播放器格式變動會影響數據平台 ETL;數據平台 schema 變動會影響 Agent 應用——這些 ownership 與 release order 目前**很可能還停留在大家心知肚明的階層**,沒有顯性化。先把這張圖畫出來,本身就是推動 AI 時代工作方式的「鉤子」,因為連人類協作都會受益。**這也是政治阻力最低的一步,可以最先動手。**

### 借鑑 3:把 validation 做成 reusable skills(分技術棧)

mabl 為不同技術棧各建一套 validation skill,加上 validation router 自動選測試。

**對應我們:** 我們需要的 validation skill 至少要涵蓋 **Java、C# ASP.NET、Vue.js、React、Databricks notebook / pipeline、LLM Agent 應用**這 6 條線。validation router 對我們特別有價值,因為跨技術棧時人類常常不知道該跑哪些測試。

### 借鑑 4:3 個核心 MCP Server 對標(原版漏掉但很關鍵的一塊)

| mabl | 我們的對等物 |
|---|---|
| Atlassian MCP(Jira / Confluence) | **同樣適用**(視我們實際使用工具而定) |
| mabl Testing MCP(自家產品包成 MCP) | **Databricks MCP**:讓 agent 能查 job 狀態、跑 notebook、查 Unity Catalog metadata、觸發 pipeline |
| Desktop Automation MCP(Electron / Playwright) | **CMS 播放器 MCP / 韌體模擬器 MCP**:讓 agent 能驗證 Box 軟體是否真的能驅動面板;這是我們**最有戰略價值**的一塊,因為這是業界沒有現成方案、但我們有領域知識可以做的差異化 |

### 借鑑 5:AI PR Review + Auto-fix workflow(治理面)

mabl 的紅線:**AI 永遠不能 approve PR,只能 REQUEST_CHANGES 或 COMMENT**。Auto-fix 只處理 lint / import / 型別小錯,且有 circuit breaker。

**對應我們:**
- 韌體與 Databricks production pipeline 是**高風險變更區**,auto-fix 範圍要比 mabl 更保守
- 建議:auto-fix 初期只開放在「應用系統」與「內部 Agent 應用」兩條線
- 韌體 / CMS / Databricks production 應該完全禁止 auto-fix,只開放 PR review 與 plan
- 這部分可以接你已經在自己 team 做的 L1/L2/L3 review 系統,直接套用並對外推廣

## 五、可能踩到的坑

### 5.1 mabl 自己提到的坑

- AI 讓 throughput 提高 3-5x 後,**human review 會變成瓶頸**(他們從 230 PR/月 → 370+ PR/月)
- Context drift 在沒有 cross-repo-base 之前佔失敗的 ~40%
- 「passing test 在 agentic workflow 中是給自主系統的決策輸入。AI healer 被優化來讓測試通過,而不是保留商業意圖。當 UI 改變時,agent 可能找到產生綠色結果的新互動路徑,即使原本的使用者旅程已經沒被驗證」——mabl 自己警告的「assumption drift」最危險:不是測試壞掉,而是測試「以為對的方式通過」

### 5.2 我們會遇到、mabl 不會遇到的坑(推論)

> **以下為基於我們情境的推論,非 mabl 原文內容**

**坑 1:跨部協作的政治成本。** 處長下令但兩個部落地節奏不同。建議先在自己的部做出可運作的 MVP 與量化成果,再反向影響另一個部,而不是一開始就強推處級統一框架。

**坑 2:韌體與資料 production 的破壞性風險高。** auto-fix / agent 自主操作必須有比 mabl 更嚴格的「destructive operation governance」。

**坑 3:異質技術棧讓 skill 維護成本高。** 6 條技術線的 validation skill 各自要有人維護。初期不要全做,選 2 條最痛的先試。

**坑 4:多代產品並存。** 電子紙、電子標籤等新產品 vs 既有面板,Box 軟體要相容多代——這個複雜度 mabl 文章完全沒提,我們要自己想。

## 七、下一步建議:三波務實 MVP

**不要**先做全處級 agent 平台。**也不要**直接複製 mabl 那套 36+ skills。建議分三波:

### Wave 1(1–2 個月):在自己的部內驗證

- 建一個 minimal cross-repo-base(只放共用規範 + 3-5 個你已驗證過的 skills)
- 選你部內 2-3 個代表性 repo(建議:1 個 Databricks 數據 repo + 1 個內部 Agent 應用 repo + 1 個應用系統 repo)
- **同步啟動 Repo Coordination Graph 第一版**(這一步可以先於 Wave 1 開始,因為它本身對人類協作就有用,風險低、政治阻力小)
- 跑通 AI PR Review(只 COMMENT 模式,不 REQUEST_CHANGES)
- 量化成果:PR 量、review 時間、context drift 失敗率

### Wave 2(3–4 個月):擴到處內

- Repo Coordination Graph 擴大到處內所有 repo
- Databricks MCP 自建或對接(類比 mabl Testing MCP)
- 引入第 2 個部加入 review workflow
- AI PR Review 升級到可 REQUEST_CHANGES

### Wave 3(5–6 個月):韌體 / CMS 加入

- 韌體 / CMS 因為破壞性風險高,**最後加入**
- 只開放 review 與 plan,不開放 auto-fix
- 建立你版本的 destructive operation governance(直接拿 L1/L2/L3 那套擴大應用)
- 開始投入「CMS 播放器 MCP / 韌體模擬器 MCP」的設計——這是我們的差異化
