# AgentCodingPM 落地改造計劃書

> 一句話賭注：**這個 repo 的瓶頸不是「知識不夠」，是「沒有消費者」。所以接下來 90 天只做一件事——把它從「筆記庫」改造成「一支會交付的內部服務隊」，並用它自己的理論（瓶頸遷移 + 風險分層 + 可驗證）來治理自己。**

---

## 0. TL;DR（給沒空讀完的自己）

- **承認現實**：這不是一個產品管線 repo，是一個「個人知識庫 + 一個真實交付物（資安 Review）」被硬套上 PM 框架的鷹架。
- **大刀闊斧的決定**：殺掉假管線與沒人用的鷹架，把 repo 重新定義為 **「Agent Coding 內部服務隊」**——對外有客戶、有交付物、有回流。
- **唯一楔子**：資安 / Code Review。它是全 repo 唯一被驗證有人要的東西。所有改造繞著它閉環。
- **90 天目標**：完成 **3 次真實交付**（對 3 個真實子產品 codebase/PR），量出 1 個真實 lead time，並讓 `00_context/` 因為撞到現實而被迫更新至少 5 處。
- **成功定義**：90 天後，這個 repo 的 commit 有一半以上是「交付驅動」而非「整理家務」。

## 2. 根因：它違反了自己寫下的原則

這個 repo 的中心論點是 **「瓶頸會遷移，不會消失」**。把這把刀對準它自己：

> AI 沒有讓你「寫筆記」變快就解決問題。瓶頸從來不在筆記產量，而在 **「這些知識有沒有被某個真實決策拉去用」**。

它還定義了量測指標「**需求到驗證通過**的 lead time」——卻從沒在任何真實東西上量過。一個沒有消費者的知識庫，註定：
寫筆記 → 沒人用 → 沒有缺口暴露 → 沒有更新動力 → 停更。**這不是紀律問題，是結構問題。**

更深一層：repo 混了**四種成熟度完全不同**的東西，用同一種「寫筆記」節奏對待，結果全部退化到最低共同節奏。

| 混在一起的 | 它其實是 | 該有的引擎 | 現況 |
|---|---|---|---|
| `00_context/` | 知識庫 | 季度 review（本該慢） | ✅ 但凍結 |
| `05_product/` | 產品管線 | 真實 item 的週節奏 | ❌ 全空 |
| `tool_experiments/` | 評估實驗室 | 每個實驗收斂成裁決 | ⚠️ 囤積 |
| `review_test_qa/` | 真實交付物 | 跟著真實客戶跑 | ⚠️ 熄火 |

## 3. 大刀闊斧的決定：重新定義這個 Repo

### 3.1 身份切換

```
舊身份：AgentCodingPM = 一個 PM 子 repo，管 Outcome/OPP/Backlog（複製 PM_Head 框架）
新身份：AgentCodingPM = 一支「Agent Coding 內部服務隊」
        對子產品線（MI / VMS / SmartSignage / Aeco）提供：
          ① AI 資安 Review   ② AI Code Review   ③ Agent Coding 流程導入陪跑
        知識庫只是這支隊伍的「作戰手冊」，不是產品本身。
```

**判準**：一個 repo 健不健康，不看它有多少筆記，看它**這個月交付了什麼給誰**。

### 3.2 三個取捨（好策略必有明確取捨）

1. **砍掉「假產品管線」**：不再維護 Outcome/OPP/Backlog 三層理論結構。改成單一 **交付登記簿（Engagement Log）**——記真實交付，不記想像中的機會。
2. **降級知識庫為「手冊」**：`00_context/` 90% 凍結成 reference；只把能直接拿去跑的部分（Gate A–E checklist、風險分層判定）抽成**可執行的 checklist/skill**。知識只在交付撞到缺口時更新。
3. **把交付物扶正**：`review_test_qa/` 從一個被埋起來的「測試」資料夾，升格為 repo 的**核心展示櫃**（這才是產品）。

## 5. 90 天落地計劃（三階段）

### Phase 0 — 止血與拍板（Week 1）

| 動作 | 產出 | 為什麼 |
|---|---|---|
| 拍板「服務隊」身份 + 鎖定第一個客戶 | 本計劃書簽核 + E01 客戶名 | 沒有客戶，後面全是空談 |
| 改寫 `AGENTS.md`：核心流程從「Outcome/OPP/Backlog」改為「Engagement 生命週期」 | 新版 AGENTS.md | 指令源頭要先對齊新身份 |
| 重組目錄（第 4 節）| 新結構落地 | 結構即誘因 |
| 砍掉清單執行（第 6 節）| 一批 deprecate/刪除 commit | 移除認知負擔 |

### Phase 1 — 第一個真實楔子閉環（Week 2–4）

**目標：完成 E01——對 MI / VMS 影像平台跑一次完整資安/Code Review，並追到底。**

1. 跟 MI/VMS 子 PM 確認要審的 codebase/PR 範圍（最近有動的分支、或上線前的關鍵服務）
2. 用 `05-風險分層` 的 Gate A–E + L1/L2/L3 跑 Review → 產出 `report_for_human.md` + `report_for_ai.json`
3. **關鍵差異**：把建議事項回送給該團隊，並**追蹤有沒有被修**（這一步是 4 月那次缺的）
4. 量這次的 **lead time**：從接案到交付、從交付到修復
5. 把過程中「手冊講不清楚 / 講錯」的地方，回寫 `10_playbook/`（預期 ≥ 3 處）

**閘門**：E01 沒閉環（建議沒被採納或忽略），不准開 E02。先搞懂為什麼沒人理。

### Phase 2 — 從「做過一次」變「可重複服務」（Month 2）

1. 把 E01 的流程反推成一個 **`review` SKILL**（輸入 codebase/PR → 輸出標準報告），讓下一次半自動
2. 跑 E02、E03（另外兩個子產品），驗證 SKILL 可複用
3. 建立**接案介面**：子 PM 怎麼跟你下單一次 Review（一張表單/一個 issue 模板）
4. `30_tooling/`：8 個工具各下一行裁決，淘汰的 clone 直接刪

### Phase 3 — 制度化與量測（Month 3）

1. 累積 3 次 lead time → 畫出**第一張真實的「需求到驗證通過」趨勢**（兌現你自己的指標論述）
2. 寫 1 份 **對 PM_Head 的彙報**：這支服務隊本季交付了什麼、幫子產品擋掉哪些風險
3. 季度 review `00_context/`：哪些被現實證實、哪些該改、哪些是空談 → 對應更新
4. 決定下一季是否擴編服務類型（從 Review → 流程陪跑 / Skill 庫輸出）
