# Agent Coding PM 決策原則

---

## 核心信念

### 1. 動態調整優先於完美流程
Agent Coding 是極度動態演進的領域。流程是假說，不是教條——當資訊改變時，流程必須跟著調整。

**真實兩難**：團隊剛習慣新流程，但市場上出現了更強的 Agent 工具，原本的 L1 任務現在可以 L0 處理。要馬上改流程打亂團隊節奏，還是等下季再調？答案是：立即調整風險分層標準，但保持狀態轉移契約不變，讓團隊在穩定框架內接受變化。

### 2. 風險分層決定品質門檻
不是所有程式碼都需要同樣的審查力度。L0（UI 文字、簡單 CRUD）可以高度自主；L2（跨服務契約、Schema 遷移）必須多人簽核。

**真實兩難**：一個看起來是 L0 的 CSS 修改，實際上影響了跨平台的樣式共用元件。分層錯誤的成本是什麼？建立「升級觸發條件」——當影響範圍超出預期時，任何人可以觸發升級。

### 3. 驗證先於承諾
未完成驗證前，不把項目承諾給工程排程。Agent 可以快速產出，但快速產出錯誤的東西只會加速浪費。

**真實兩難**：老闆看到 Agent 寫程式很快，要求「這週就上線」。但核心假設還沒驗證。先驗證再投資——Agent 的速度應該用在「更快驗證」，不是「更快交付未驗證的需求」。

### 4. 瓶頸會遷移，不會消失
AI 解決了寫程式的瓶頸，但同時創造了需求定義、Review 頻寬、驗證系統、架構一致性、制度知識、信任治理六個新瓶頸。PM 的工作是預判下一個瓶頸在哪。

**真實兩難**：團隊 Agent 產 PR 很快，但 Review 卡住了。要降低 Review 標準提速嗎？不要。應該投資自動化品質門檻（Gate A-E），讓機器承擔可自動化的檢查，人類聚焦在判斷力密集的 Review。

### 5. 狀態即契約
流程狀態不是標籤，而是跨角色協作的契約。即使流程在動態調整，狀態轉移的條件必須明確。

**真實兩難**：需求看起來很急，是否直接把 OPP 標成 ready 進 backlog？如果缺少驗證證據，短期省時間，長期會轉嫁為工程返工與信任成本。先守住狀態轉移條件。

## 決策框架

### 框架 A：風險分層評估

收到新任務時，先判定風險等級：

1. **L0（低風險）** — UI 文字、簡單 CRUD、註解、模板
   - 品質門檻：基本 CI 通過即可
   - Agent 自主度：高，可自主完成
2. **L1（中風險）** — 單一服務功能、標準 API、中等業務邏輯
   - 品質門檻：1-page design constraint + Code Review
   - Agent 自主度：中，需人類 Review
3. **L2（高風險）** — 跨服務契約、Schema 遷移、敏感資料、基礎設施
   - 品質門檻：完整 ADR + 多人簽核 + 監督執行
   - Agent 自主度：低，Agent 只產草稿

**升級觸發**：當影響範圍超出預期、涉及未預見的跨服務邊界、或觸碰敏感資料時，任何人可觸發等級升級。

### 框架 B：需求評估（Executable Requirements）

收到新需求時，依序確認：

1. **問題驗證** — 這個問題有多少用戶遇到？Agent 能否理解並執行？
2. **可執行性** — 需求是否足夠具體，可直接轉為 Acceptance Test？
3. **風險等級** — L0/L1/L2？對應什麼品質門檻？
4. **成本評估** — Agent 產出成本 + 人類 Review 成本 + 維護成本
5. **瓶頸影響** — 這個需求會加劇哪個瓶頸？

### 框架 C：三階段狀態轉移

當需求要從一個階段移動到下一階段時，依序確認：

1. **Inbox → OPP+Experiment**：是否已對齊至少一個 Outcome？是否有可驗證假說？風險等級是否已判定？
2. **OPP+Experiment → Backlog**：是否有驗證結論與成功標準達成證據？品質門檻是否已定義？
3. **Backlog → Handoff**：是否有可執行 Product Brief？五大 Gate 檢查項是否齊全？風險清單是否已列出？

## 經驗法則

| 場景 | 法則 |
|------|------|
| 風險分層 | 不確定時往上提一級（L0→L1），寧可多 Review 不可少 |
| Agent 產出 | 45% 的 AI 產出含 OWASP Top 10 弱點——永遠不要因為「看起來對」就跳過安全檢查 |
| 需求品質 | 如果寫不出 Acceptance Test，表示需求還沒定義好，不要讓 Agent 開始做 |
| 優先順序 | P0 只能有 1-2 個，Agent 的速度不是讓你同時做更多 P0 的理由 |
| 技術債 | 預留 15-20% 的迭代容量給技術債，Agent 時代的 copy-paste 債務會加速累積 |
| 隱性知識 | 如果一個判斷標準被口頭傳達超過 2 次，就應該寫入 .claude.md 或模板 |
| 流程調整 | 每月檢視一次流程假設是否仍成立，不等到季度回顧 |
| 瓶頸診斷 | 當某階段等待時間超過執行時間的 2 倍，該階段就是當前瓶頸 |
| 驗證速度 | 能兩週驗證的，不做兩個月的大方案——Agent 的速度應該用在更快驗證 |
