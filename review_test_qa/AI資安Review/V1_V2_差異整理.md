## 整體結論

V2 不是單純把 V1 的內容重寫，而是重新整理了風險分類方式與敘事重點。

- 漏洞總數：`12 → 14`
- Critical：`3 → 3`
- High：`4 → 4`
- Medium：`3 → 4`
- Low / Hardening：`2 → 3`

V2 的主要變化：

- 把原本混在一起的「認證繞過」拆得更清楚
- 新增對前提條件、PoC、影響範圍、信心度的描述
- 增加根因分組與攻擊鏈分析
- 將部分原本偏「防禦建議」或「脈絡相依」的項目降級
- 新增幾個 V1 未明確指出的議題，尤其是「只靠帳號即可登入」

## V2 新增的重要議題

以下議題在 V1 沒有明確列出，或在 V2 被提升為更具體的風險：

### 1. 登入只需帳號、不需密碼

- V2：VULN-003
- 嚴重度：Critical
- 說明：
  - V2 明確指出登入流程只需要 `loginId`
  - 無密碼、無 MFA、無鎖定、無頻率限制
  - 這比單純前端假 token 更接近真正的身份驗證失效

### 2. 客戶端角色可竄改

- V2：VULN-005
- 嚴重度：High
- 說明：
  - V2 指出角色資料存在 localStorage，可直接用 DevTools 竄改
  - 焦點從「前端有角色選單」轉成「前端權限模型本身可被修改」

### 3. 動態注入第三方 Script 無 SRI

- V2：VULN-006
- 嚴重度：High
- 說明：
  - V1 提的是外部圖片載入風險
  - V2 改抓到更實際的供應鏈風險：第三方 `embed.js` 動態注入且無 SRI

### 4. API 路徑參數未編碼

- V2：VULN-010
- 嚴重度：Medium
- 說明：
  - 新增輸入處理面的風險
  - 指出 `roleName` 直接拼接到 API path，未經 `encodeURIComponent`

### 5. RedirectView 路徑參數未驗證

- V2：VULN-011
- 嚴重度：Medium
- 說明：
  - 新增內部路由導向驗證不足議題
  - 雖非外部 redirect，但屬於內部導向邏輯缺口

### 6. 正向安全發現

V2 額外補了幾個「未發現問題」的項目，V1 沒有：

- 未發現 `v-html`、`innerHTML`、`document.write`
- 未啟用 sourcemap
- `npm audit` 漏洞限於 devDependencies

這代表 V2 的報告風格比較接近完整審計，而不是單純列洞。

## 被降級或重新定義的議題

### Open Redirect：High → Medium

- V1 將其視為 High
- V2 降為 Medium
- 原因：
  - V2 補充說明 Vue Router 對外部 URL 的處理仍需實測
  - 代表證據強度從「確定可利用」調整為「可能可利用」

### localStorage 敏感資料：High → Low / Hardening

- V1 視為高風險資料儲存問題
- V2 改判為風險放大器
- 原因：
  - 單靠 localStorage 明文儲存，不一定能單獨直接利用
  - 真正利用通常仍要搭配 XSS 或第三方 script 被植入

### CSRF：High → Low / Context-dependent

- V1 認為缺乏 CSRF 防護屬 High
- V2 重新評估後降級
- 原因：
  - 目前使用 `Authorization: Bearer` header
  - 傳統 CSRF 多數依賴瀏覽器自動附帶 cookie
  - 因此在目前架構下不是首要風險

### 安全標頭：Medium → Low / Context-dependent

- V1 從 `index.html` 缺少安全 meta 標籤切入
- V2 改成要求確認部署環境是否已在 proxy/CDN 層設定 headers
- 代表 V2 更重視部署脈絡，而不只看前端原始碼

## V2 報告方法上的提升

相較於 V1，V2 增加了以下資訊結構：

- 信心度（Confirmed / Likely / Context-dependent）
- 前提條件
- PoC 步驟
- 影響敘述
- 根因分組
- 攻擊鏈
- 優先修復順序與工作量

這使 V2 更適合拿來做：

- 修復排程
- 風險溝通
- 向工程或主管說明優先順序

## 關鍵判讀

若只看數量，V2 比 V1 多 2 項；但真正重要的是，V2 更明確指出了兩個核心問題：

1. 認證模型未正式化
2. 授權 enforcement 只停留在前端 UI 層

其中最值得優先確認的是：

1. 系統是否真的只靠 `loginId` 就能登入
2. 後端 API 是否真的驗證 JWT 與角色，而不是只靠前端判斷

如果這兩件事屬實，則 V2 的風險判讀比 V1 更接近真實根因。

---

## 建議的後續處理順序

1. 先驗證 V2 的 Critical 是否可重現，尤其是「無密碼登入」與「任意 token 繞過」
2. 確認後端是否有 JWT 簽章、過期與角色驗證
3. 若後端未驗，優先處理認證與授權模型
4. 再處理供應鏈 script、mock code、redirect 與路徑驗證等防禦縱深項目
