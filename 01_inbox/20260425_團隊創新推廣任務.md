接收到團隊新任務，將扮演約 40 人團隊的 AI 時代工作方式推手

一個處，兩個部，每個部約 20人，我是屬於某一個部，但命令是處長下的，大家都要配合


希望能把 AI 時代的工作方式帶入團隊，

目前團隊性質大略分類：

1. 韌體 Team，開發能驅動面板的 Box 軟體，需要跟各種面板的播放器（尤其是 電子紙、電子標籤...等新產品）整合

2. CMS 播放器協助維運：公司是面板製造為主，因此衍伸的解決方案中 CMS (Content Management System) 是重要一環，有 Team 再協助

3. 新應用系統 Team，有 Java 也有 C# ASP.NET 的技術，前端有 Vue.js 和 React

4. 數據價值相關系統：有數據平台、數據分析、數據可視化等相關系統，技術棧目前以 Databricks 為主，例如廣告投放分析

5. 公司內部 Agent 應用優化：我們也要支援公司內部的效率提升，協助開發各種內部 Agent，技術是以 Databricks 和 各種 LLM 應用為主



===

下面是我把公開案例篩過後的結論：**最貼近你情境的，不是「Copilot 導入案例」，而是已經把 AI coding 從個人工具升級成「平台工程 + Context 治理 + 品質閘 + Agent Workflow」的案例。**

公開資料裡，真正有流程、配置、踩坑、數字的案例不多；最值得優先深讀的是 **mabl、Spotify Honk、Uber FlakyGuard / AI Dev Platform、Slack migration**。

# 1. mabl：25 人工程團隊，把 Agent Coding 做成跨 75+ repos 的平台化流程

## 一句話定位

mabl 25 位工程師、100+ repositories，建立 **Cross Repo Base + CLAUDE.md + MCP Servers + 36+ Skills + AI Review + Auto-fix workflow**，把 agent 從個人助手升級成團隊級工程基礎設施。([Mabl][1])

## 歸屬類型

A 團隊級工具與基礎設施、B Skills / Prompt / Workflow、C Code Review、D 度量與治理、E 知識共享。

## 與你情境的相似度

★★★★★
相似點：團隊規模接近、跨 repo、重視「寫程式以外的開發流程」、有 MCP / Skills / Review / Governance。
差異點：mabl 是 SaaS 軟體公司，技術棧比你的韌體、CMS、Databricks 混合情境更單純一些。

## 可直接借鑑的 3 件事

1. 建一個 **cross-repo-base repo**：放共同規範、工程指南、標準工作流、security constraints、技能入口。mabl 讓每個 repo 仍保留自己的 `CLAUDE.md`，描述 repo purpose、architecture、dependencies、build/test workflow。([Mabl][1])
2. 建 **Repo Coordination Graph**：mabl 維護 850+ lines 的 dependency / ownership / release order registry，讓 agent 知道跨 repo 修改順序、要 tag 誰、哪些資料表或 Pub/Sub topic 歸誰。這非常適合你們跨 CMS、Web、Databricks、Agent 應用的情境。([Mabl][1])
3. 把 validation 做成 reusable skills：mabl 有 Java/Gradle、React/Vitest、TypeScript/Jest、Playwright/Electron、E2E test、validation router，會依照變更檔案自動選測試。這很符合你關心的「需求到驗證通過 lead time」。([Mabl][1])

## 可能踩到的坑

mabl 明確提到：AI 讓 coding throughput 提高後，**human review 會變成瓶頸**；所以他們不讓 AI approve PR，只允許 AI `REQUEST_CHANGES` 或 `COMMENT`，最後 merge 仍由人決定。([Mabl][1])

## 來源

mabl engineering blog，2026-04-08，〈How We Built a System for AI Agents to Ship Real Code Across 75+ Repos〉。([Mabl][1])

## 下一步建議

MVP 不要先做全公司 agent 平台。先做一個 **「Agent Base Repo + 3 個代表性 repo + 5 個 validated skills」**：
`run-tests`、`read-ticket`、`generate-plan`、`ai-pr-review`、`fix-simple-ci-failure`。
這個案例是你最值得深讀的第一名。

# 2. Spotify Honk：背景 coding agent，專攻大規模維護與 migration

## 一句話定位

Spotify 建立內部背景 coding agent「Honk」，用於大規模 codebase maintenance / migration，公開資料顯示曾達到 1,500+ AI-generated PRs，後續 QCon 報導提到速度成長到 1,000 merged PRs / 10 days。([Spotify Engineering][2])

## 歸屬類型

A Cloud / Background Coding Agent、B Workflow、C Review bottleneck、D 規模化度量。

## 與你情境的相似度

★★★★☆
相似點：重點不是 autocomplete，而是 **background agent + codebase maintenance + review bottleneck**。
差異點：Spotify 規模遠大於你們，且它偏 platform team / DevEx 角度，不是 40 人部門級導入。

## 可直接借鑑的 3 件事

1. 把 agent 任務聚焦在 **maintenance / migration / repetitive change**，不要一開始挑新產品核心功能。
2. 把 PR review 視為新瓶頸。InfoQ 報導 Spotify QCon talk 時特別指出，code generation 不是瓶頸後，PR review 會變成下一個瓶頸。([InfoQ][3])
3. 把任務做成 fleet / campaign，而不是單次 prompt。Spotify Honk 後續文章也延伸到 dataset migration / Fleet Management。([Spotify Engineering][4])

## 可能踩到的坑

你們如果直接模仿 Spotify，很容易做太大。Honk 類型的 agent 需要成熟 repo ownership、CI、review queue、release discipline。你的 MVP 應該只做 **一種 L0/L1 任務 campaign**，例如：
「所有 repo 的 deprecated API usage 修正」或「固定格式的 dependency / config migration」。

## 來源

Spotify Engineering，2025-11 起 Honk 系列；InfoQ 2026-03 QCon London 報導。([Spotify Engineering][2])

## 下一步建議

選一個橫跨 5–10 個 repo 的低風險 migration 題目，建立：
`task list → agent branch → PR → AI review → human review → merge queue`。
不要先追求「agent 自動寫很多功能」，先追求「同一類變更可重複、安全地跑」。

# 3. Uber FlakyGuard：把 flaky test 修復做成 autonomous repair pipeline

## 一句話定位

Uber 的 FlakyGuard 針對真實工業 repo 的 flaky tests，自動 reproduce、定位、產生修復，六個月部署中處理 1,115 個 flaky tests，對可重現 flaky tests 達成 47.6% 修復率，產生的修復有 51.8% 被開發者接受。([arXiv][5])

## 歸屬類型

C 品質防線、D 度量與治理、A 自動化 agent pipeline。

## 與你情境的相似度

★★★★☆
相似點：非常符合你關心的「需求到驗證通過」與「瓶頸從 coding 轉到驗證」。
差異點：這是專項研究 / 大型公司案例，不是一般 Copilot team rollout。

## 可直接借鑑的 3 件事

1. 把 agent 任務綁到 **已知痛點：flaky test、CI failure、簡單測試修復**，比開放式寫功能更安全。
2. 用明確指標追蹤：reproduced rate、fix generated rate、developer acceptance rate、merged fix rate。
3. 把人放在 acceptance gate：agent 產生 fix，但最後仍由 developer accept / review。這很適合你的 L0/L1/L2 風險分層。

## 可能踩到的坑

flaky test repair 的成效高度依賴測試基礎建設。如果你們現在測試覆蓋不足，第一步不是寫 FlakyGuard，而是先建立 **CI failure taxonomy**：lint、type、unit test、integration test、環境問題、資料問題、真 regression。

## 來源

Uber / FlakyGuard 論文與 ASE 2025 paper page，2025-11。([arXiv][5])

## 下一步建議

做一個 **CI Failure Auto-Triage MVP**：
先不要自動修 code，只做「分類 + 建議 owner + 建議修復方向 + 是否可交給 agent」。
穩定後再開 L0 auto-fix。

# 4. Uber AI Dev Platform：MCP Gateway、Agent task、Code Inbox、uReview、Autocover

## 一句話定位

Uber 公開與媒體資料顯示，其 AI 開發平台已從個人工具擴展到 agentic engineering，包含 MCP Gateway / Registry、background coding agent、Code Inbox、uReview、Autocover、Shepherd 等內部工具；公開報導稱 95% 工程師每月使用 AI，內部 agent 每週產生約 1,800 個 code changes。([Agentic AI Foundation (AAIF)][6])

## 歸屬類型

A 團隊級基礎設施、C AI Review、D 度量與治理。

## 與你情境的相似度

★★★☆☆
相似點：很符合「已經有 AI tools 後，怎麼建立平台級機制」。
差異點：Uber 規模太大，很多資料來自媒體 / podcast / conference 整理，不是完整工程 blog。

## 可直接借鑑的 3 件事

1. **MCP Gateway / Registry**：不要讓每個 team 自己亂接工具，應該有一個 catalog / gateway 管理哪些 MCP 可用、誰能用、權限多大。
2. **AI review comment quality**：Uber 被報導有 uReview，重點是讓 AI review 提供 high-signal comments，而不是製造噪音。([Pragmatic Engineer][7])
3. **Autocover**：用 AI 補測試比直接寫新功能更適合早期團隊推廣。報導提到 Uber 有每月產生 5,000+ unit tests 的 Autocover。([Pragmatic Engineer][7])

## 可能踩到的坑

Uber 的做法非常平台化。你們 40 人團隊不該直接做大型 MCP gateway。先做「白名單 MCP + 權限矩陣 + 3 個 approved tools」即可。

## 來源

Business Insider，2026-03；Pragmatic Engineer newsletter 摘要，2026-03；MCP Dev Summit 整理，2026-04。([Business Insider][8])

## 下一步建議

先做 **MCP / tool approval board lite**：
列出 agent 可用工具、風險等級、資料權限、允許的 repo、是否可 write。
這會直接對應你的「工具安全」品質門檻。

# 5. Slack：AST + LLM hybrid migration，15,000 Enzyme tests 轉 RTL

## 一句話定位

Slack 為 React 18 升級，把 15,000+ Enzyme tests 遷移到 React Testing Library，採用 **AST codemod + LLM** 的 hybrid approach，QCon 資料提到約 80% conversion success rate。([Slack Engineering][9])

## 歸屬類型

B Workflow、C 系統正確性、D lead time / migration efficiency。

## 與你情境的相似度

★★★★☆
相似點：它不是導入 Copilot，而是把 AI 放進「可驗證的工程流程」。
差異點：偏單一 migration，不是長期 team operating model。

## 可直接借鑑的 3 件事

1. 不要迷信 pure LLM。Slack 的重點是 **AST 處理 deterministic 部分，LLM 處理 edge cases**。
2. 給 agent 足夠 examples / context，而不是只調 prompt。平台工程文章也總結 Slack 的成功關鍵是 context engineering，而不是 prompt refinement。([Platform Engineering][10])
3. 開源工具可參考：Slack 有公開 `enzyme-to-rtl-codemod`，設計成可搭配你自己的 LLM API。([GitHub][11])

## 可能踩到的坑

如果你們沒有測試可驗證，AI migration 很難落地。Slack 的場景可成功，是因為 test migration 本身有明確 pass/fail gate。

## 來源

Slack Engineering，2024-05；QCon SF 2024 / InfoQ 2025 轉載。([Slack Engineering][9])

## 下一步建議

找你們內部一個「可機械化 + 可驗證」的 migration：
例如 Vue component API 調整、C# logging pattern 統一、Databricks notebook import path 改寫、Java dependency upgrade。

# 6. Airbnb：state machine + validation gates 做 test migration

## 一句話定位

Airbnb 針對 3,500 個 test files migration，建立 state machine，讓每個檔案通過 Enzyme refactor、Jest fixes、lint、TypeScript validation 等 gates；公開整理稱 6 週完成原本估 1.5 年的工作，並達到高比例自動化。([Platform Engineering][10])

## 歸屬類型

B Workflow、C 品質門檻、D lead time。

## 與你情境的相似度

★★★☆☆
相似點：非常適合你的「L0/L1/L2 + 品質門檻」思維。
差異點：資料主要來自二手整理，不如 Slack / mabl 直接。

## 可直接借鑑的 3 件事

1. 把 agent workflow 設計成 **state machine**，不要一口氣叫 agent 完成所有事。
2. 每個 gate 都有明確 pass/fail：lint、type check、unit test、snapshot、manual review。
3. 失敗時把 error message 回灌給 LLM retry，而不是只叫人接手。

## 可能踩到的坑

state machine 很容易做得太重。你們第一版只需要 3 階段：
`Plan → Implement → Validate`，每階段都有 human confidence gate。

## 來源

PlatformEngineering.org，2025-12，整理 Slack / Airbnb / Google migration cases。([Platform Engineering][10])

## 下一步建議

把你現有的成熟度模型落成一張表：
L0 可自動修、L1 需人審、L2 禁止 agent 自動改。
然後每個 workflow state 都綁一個風險等級。

# 7. HP + Stack Overflow MCP：把企業知識庫變成 agent 可取用的 context

## 一句話定位

HP 的 Developer Experience / Applied-AI team 使用 Stack Overflow MCP，並規劃內部 MCP broker，把企業知識、security/privacy context、validated Q&A 變成 coding agents 可系統化取用的 source of truth。([Stack Overflow Blog][12])

## 歸屬類型

A MCP / 共享 Context、E 知識共享、D 治理。

## 與你情境的相似度

★★★☆☆
相似點：你們技術異質性高，最缺的通常不是 prompt，而是 tribal knowledge 能不能被 agent 可靠取得。
差異點：HP 是 4,000+ developers，公司規模遠大；案例仍偏 discovery / POC，而不是完整營運數據。([Stack Overflow Blog][12])

## 可直接借鑑的 3 件事

1. 做 **MCP broker / catalog**，避免每個團隊自己接一堆 MCP，造成工具疲勞與權限混亂。([Stack Overflow Blog][12])
2. 把 security、privacy、corporate coding context 放進 agent context，而不是只放技術文件。([Stack Overflow Blog][12])
3. 用 validated Q&A / accepted answer 當 source of truth，比丟一堆文件給 RAG 更容易被工程師信任。

## 可能踩到的坑

MCP 很容易變成「接很多工具，但沒人知道什麼時候用」。你應該先定義 use case：
例如「新同事 / agent 查 repo onboarding、CI 錯誤處理、Databricks table ownership、release checklist」。

## 來源

Stack Overflow Blog，2025-12，HP MCP Server case。([Stack Overflow Blog][12])

## 下一步建議

先做 **Internal Engineering Q&A MCP / Knowledge MCP MVP**：
收 30 條最常問問題：環境建置、CI 失敗、Databricks table owner、CMS release、韌體交付流程。
先不要做大知識庫。

# 8. Stripe Minions：大量 human-reviewed agent PRs

## 一句話定位

公開討論資料提到 Stripe 的 Minions coding agents 每週有 1,000+ 到 1,300+ completely minion-produced、human-reviewed merged PRs。([news.ycombinator.com][13])

## 歸屬類型

A Background Agents、C Human Review、D throughput metric。

## 與你情境的相似度

★★★☆☆
相似點：很值得觀察「AI PR 大量進入 review queue 後，human review 如何承接」。
差異點：目前我能找到的公開資料品質較混合，包含 HN 討論與二手整理；不像 mabl / Spotify 有完整工程文可直接照抄。

## 可直接借鑑的 3 件事

1. 指標不要只看 AI 寫了多少 code，而要看 **merged PR / accepted PR / review rejection**。
2. 「human-reviewed」是底線，不是裝飾。HN 討論也提醒大量 AI PR 會讓 code review 品質變成風險。([news.ycombinator.com][13])
3. 你們若未建立 review taxonomy，AI PR 量增加只會把 reviewer 壓垮。

## 可能踩到的坑

高 PR 數很吸引人，但對 40 人團隊可能是錯誤 KPI。你應該量測：
「需求到驗證通過時間」、「review rework 次數」、「CI failure rate」、「rollback / defect rate」。

## 來源

HN 討論與 2026 AI coding agents roundup。([news.ycombinator.com][13])

## 下一步建議

不要模仿 PR 數量。只借鑑一件事：
建立 AI PR dashboard，分成人寫、AI assisted、agent generated 三類，追蹤 merge rate / reject reason。

# 9. Duolingo feature flag cleanup agent：一週 prototype 到 production 的窄任務 agent

## 一句話定位

公開 LLMOps database 摘要提到 Duolingo 建立 agent，自動 clone repos、找出並移除 obsolete feature flags，跨 Python / Kotlin codebase 建 PR，約一週從 prototype 到 production。([zenml.io][14])

## 歸屬類型

A Self-service coding agent、B 固化 workflow、C 低風險維護任務。

## 與你情境的相似度

★★★☆☆
相似點：非常適合 40 人團隊做第一個 L0/L1 agent workflow。
差異點：目前公開資料較少，較像案例摘要，不是完整工程長文。

## 可直接借鑑的 3 件事

1. 選 **窄任務**：feature flag cleanup、deprecated config、unused import、固定 pattern migration。
2. 產出 PR，不直接 merge。
3. 把任務做成內部自助工具：工程師提出需求，agent 產 PR 給 owner review。

## 可能踩到的坑

窄任務 agent 如果沒有 ownership mapping，PR 會沒人 review。你需要搭配 CODEOWNERS 或 repo owner registry。

## 來源

ZenML LLMOps Database 案例摘要。([zenml.io][14])

## 下一步建議

在你們內部找一個「大家都知道該清，但沒人想清」的東西，例如：
舊 API、舊 config、舊 dashboard 欄位、deprecated Databricks table reference。
