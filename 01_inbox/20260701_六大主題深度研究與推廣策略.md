# 六大主題深度研究與推動小組策略

> 承接 [`20260425_團隊創新推廣任務.md`](./20260425_團隊創新推廣任務.md)（mabl 案例分析）——本篇**刻意不重複研究 mabl**，聚焦另外六個主題找業界案例，並把兩篇合併成一份給推動小組（一處兩部）用的策略。

## 0. 一句話結論

六個題目裡，三個有**極具體、可落地**的業界案例（Loop Engineering、雲端 Agent 開發、資安檢測），一個是**警示而非模範**（Agent Coding Review 治理——業界大多數 AI PR 根本沒人 review），一個是**要自己延伸**（低風險/最小變異開發——韌體與 Databricks pipeline 沒有任何案例覆蓋），一個是**真空**（設計/PM Agent 輔助流程——沒有任何 claim 通過驗證）。**不要把研究覆蓋率的落差誤讀成「這件事不重要」**，而是推動小組自己要補的地方。

---

## 一、Loop Engineering ——採用 Anthropic 自己的 harness 架構

**最適用案例**：Anthropic Engineering Blog〈Effective harnesses for long-running agents〉

**具體做法**：
- 拆成「一次性 Initializer Agent」（建 `init.sh`、git commit、`claude-progress.txt`）+ 「重複執行、無記憶的 Coding Agent session」
- 進度用**結構化 JSON feature list**追蹤（而非 Markdown——模型比較不會亂改 JSON），配合 git history 當第二層真相來源
- 沒有這套鷹架，模型會出現兩種失敗模式：**過度野心**（想一次做完，把 context 燒光）與**假性完工**（只看到部分進度就宣稱做完）

**對兩部的意義**：這正是解決你們「應用系統 / 數據 / 內部 Agent」這三條線長任務（例如一次遷移、一次大型重構）該用的鷹架設計，不需要自己發明。

**延伸（雲端可恢復性）**：Anthropic〈Managed Agents〉把 agent 拆成三個可獨立替換、無狀態的元件（持久 append-only session log、無狀態 harness/loop、隔離 sandbox），harness 掛掉時新實例靠重播 event log 復原，不需要原 process 存活——這是把 agent 從「本機開發者的個人助手」過渡到「雲端/CI 常駐服務」的關鍵模式。

**同一來源給的最小變異保護**：credential/secret **架構上永遠不進入 agent 執行程式碼的 sandbox**——透過 token bundling 或 vault + 專屬 proxy 存取，harness 本身看不到明文憑證。**這條直接可以現在就採用**，不管哪條技術線，只要 agent 會執行程式碼，就不該讓它直接碰到 production 憑證。

## 二、雲端 Agent 開發 —— Spotify「Honk」是目前最貼近的真實案例

**最適用案例**：Spotify Engineering Blog，背景 coding agent「Honk」系列文章（2025-11 至 2026-04）

**具體數字**（已驗證，非行銷用語）：
- **1,500+ 筆 AI 產生的 PR 已 merge 進 production**
- 遷移類任務**節省 60-90% 時間**（相較人工改寫）
- 跑在 Kubernetes pods 裡的自主背景系統，不是本機 IDE 助手

**治理設計（這段對「怎麼推」比數字更重要）**：
- Agent 的可執行動作被刻意限縮到最小集合：**只能看 code、改檔案、呼叫 verifier**——推 code、跟使用者互動、寫 prompt 全部由外圍基礎設施負責，不是 agent 自己做主
- 兩層驗證：(a) 決定性 verifier 依偵測到的 codebase 自動啟用（例如偵測到 `pom.xml` 就跑 Maven verifier），在開 PR 前先跑；(b) **LLM-as-judge** 層在決定性 verifier 之後跑，會否決約 **25% 的 agent session**（多數原因是 scope creep，agent 做超過原本要求的範圍），agent 收到否決後約一半時間會自己修正

**對兩部的意義**：這是「雲端 Agent 開發」該長成的樣子——**不是給 agent 更大權限，而是把它的動作集縮到最小、把驗證拆成兩層**。這比空泛地說「上雲端」更能指導你們決定 Databricks MCP / CMS 播放器 MCP 該開放哪些具體操作。

⚠️ **兩個已被推翻、不要用的說法**（研究過程中有查核到但被否決，來源本身有寫但不成立）：
- ❌「Spotify 約一半 PR 都被自動化」——這個數字被 3 個獨立查核都推翻，真實數字只有上面驗證過的 1,500+ 筆與 60-90% 兩項
- ❌ 某篇論文提出的「三層分級人類監督模型（HITL/HOTL/AWM）」——也被查核推翻，不要拿去當「業界標準框架」引用

## 三、AI 資安檢測 —— Anthropic `/security-review` 定義了目前的基準線，但明確承認做不到的事

**最適用案例**：`anthropics/claude-code-security-review`（官方 GitHub repo）+ Anthropic 產品部落格

**具體做法**：
- Claude Code 內建 `/security-review` 指令，掃 SQL injection、XSS、authN/authZ 缺陷、不安全資料處理、依賴漏洞
- 搭配 GitHub Action，PR 一開就自動觸發、可自訂規則、直接在 PR 留 inline comment 附修復建議
- **明確分工**：「Claude 找漏洞，開發者自己實作修復」——不自動改 code
- 有自動化 false-positive 過濾，刻意排除低影響/雜訊類（DoS、rate limiting、記憶體耗盡、通用未驗證的輸入驗證、open redirect），維持在大量掃描下的訊噪比

**關鍵限制（官方自己寫的，直接影響你們的 gate 設計）**：
> 這個 Action **沒有針對 prompt injection 做強化**，只該跑在信任的 PR 上，建議「外部貢獻者一律要求先核准」——確保 workflow 只在維護者已經看過 PR 之後才執行。

**對兩部的意義**：這條直接支持你們 `05-風險分層與五大品質門檻.md` 裡「AI CR 是預選賽，不是最後一關」的立場——不是 AgentCodingPM 自己保守，**連 Anthropic 官方工具自己都這樣要求**。可以直接引用這句話去說服另一部或處長：AI 資安掃描要接受人工 gate，不是選配。

## 四、安全、變異最小的軟體開發 —— 有可用模式，但韌體/Databricks pipeline 是真空地帶，要自己補

**可採用的模式（來自 Anthropic Managed Agents，見第一節）**：
- Credential 永不進 sandbox
- 「guardrail 是結構性、自動的；quality gate 只是事後檢查、靠人／流程回應」——**guardrail 要做在架構裡，不能只是加一道 review 關卡**

**警示案例（務必拿去溝通用）**：
- Replit/PocketOS 事件：一個有過度授權 API token 的自主 agent，在**9 秒內**執行 DROP TABLE 刪掉 production 資料庫連同備份——根因是「過度授權的 token + 沒有分層攔截」，不是模型不夠聰明
- 這正好對應你們 `05-風險分層` 裡 R3 四重保護（dry-run / 雙人簽核 / 備份還原驗證 / 分段釋出）存在的理由，可以直接拿這個真實案例當「為什麼要有這條規則」的佐證

**真空地帶（研究誠實回報，沒有查到，不是我漏看）**：
1. **沒有任何來源處理韌體/embedded 場景下的 blast-radius containment**——Anthropic/Spotify 的模式都是 SaaS/web context，一次錯誤的 autonomous action 對電子紙/電子標籤面板來說可能是**物理不可逆**（例如一次錯誤的 flash/OTA push），這件事全網沒有現成案例可抄，**要你們自己設計**
2. **沒有任何來源處理 Databricks 資料 pipeline 的 verifier 設計**——Spotify 的 verifier 檢查的是 build/test 通過與否，你們的資料線需要的 verifier 要檢查 schema/data quality/lineage，這也是空白，要自己補
3. 有一份 arXiv 論文（2509.09970）提到 LLM 生成韌體用 fuzzing + static analysis + runtime monitoring 的混合驗證框架，號稱 92.4% 漏洞修復率——**信心度中等**，僅供參考方向，不建議直接引用這個數字對外溝通

**對兩部的意義**：韌體/CMS 這條線的治理，注定要比應用系統/數據線晚、也更嚴——這正好呼應你上次策略裡「Wave 3 最後才讓韌體/CMS 加入、且只開放 review 與 plan、不開放 auto-fix」的判斷，這次研究進一步證實：**不是保守，是業界真的還沒有人解決這個問題，你們沒有捷徑可抄**。

## 五、Agent Coding Review 治理 —— 這題最重要的發現是「不要學業界現狀」

**這不是一個「最佳案例」，是一個警示**：

- 對 33,707 筆 AI 產生的 GitHub PR 的實證研究（EASE 2026，統計檢定 p<0.001）：**61.38% 完全沒有被記錄的 review**；剩下 38.62% 有被 review 的裡面，**多數是被其他 AI agent review，不是人類**——只有 10.14% 是純人類 review
- 對照組：人類寫的 PR 有 25.21% 是純人類 review（AI PR 只有 8.08%），也更常收到人類直接回饋（93.56% vs 65.53%）
- 就算有人類介入 AI PR，互動模式也在從「評估程式碼」轉向「操控 agent」（叫它去 rebase / 修 / 補測試），而不是真正審查邏輯
- 對 1,000 個熱門開源 repo 的調查：只有 11.8% 有正式的 AI 貢獻政策；有政策的裡面 74% 要求人類把關這一步——是目前找到的**最常見控制點**

**對兩部的意義**：這正是「業界目前的預設狀態」，也正是你們**不該**繼承的狀態。這份研究直接支持你先前定的紅線——**AI 只能建議/標記，人類永遠是最終 merge 判斷**——不是你們過度謹慎，是業界的 61% 沒人管的現狀正在製造風險，你們現在立規則是在避開多數團隊正在犯的錯，而不是拖慢自己。

**具體建議**：把 mabl 案例裡「AI 只能 REQUEST_CHANGES / COMMENT，人類才能 approve」的紅線，和這份研究的「74% 靠人類把關」對照著用——一個是正面案例（怎麼做對），一個是反面數據（不做會怎樣），兩個一起說服力更完整。

## 六、設計與 PM 的 Agent 輔助流程 —— 誠實的證據缺口，需要再補一輪研究

**這題沒有任何 claim 通過驗證**——搜尋角度找到 Linear/Ramp 的客戶案例（Ramp 內部 agent「Inspect」串 Linear，號稱能追蹤「客戶需求 → 產品規格 → 程式碼」的完整脈絡），但最終被判定不夠獨立可查證，未進入正式發現清單。

**這代表什麼**：不是這個題目不重要，是**目前公開網路上還沒有你能直接引用的、經過交叉驗證的具體案例**。與其硬套一個查證不足的案例，不如誠實承認：這塊要嘛①另外開一輪更聚焦的研究（鎖定 Figma / Linear / 設計工具廠商的工程部落格，或企業級 UX research + AI 案例），要嘛②**先讓自己的 PM/SA 團隊小範圍試、自己產出案例**，而不是等外部案例。

對照你們自己 `00_context/04-輕量開發流程.md` 已經寫好的 PM/架構師/SA 判斷權劃分——這部分反而是你們自己的方法論已經比外部研究更成熟的地方，不必等別人。

## 七、整合到「兩軌 + 閉環」策略（延續前次討論）

把六個題目對應回你們的兩部、五條技術線：

| 主題 | 屬於哪一軌 | 對應技術線 | 這一季的具體動作 |
|---|---|---|---|
| Loop Engineering | 軌道一（自己部內深挖） | 應用系統 / 數據 / 內部 Agent | 挑一個真實遷移/重構任務，套 Initializer + JSON progress 的 harness 設計 |
| Agent Coding Review | 貫穿兩軌的紅線 | 全部 5 條線 | 把「人類永遠 merge」寫進推動小組憲章第一條，引用 61%/74% 數字對處長溝通 |
| 雲端 Agent 開發 | 軌道一 | 內部 Agent / 數據 | 參考 Honk 的「最小動作集 + 兩層 verifier」設計 Databricks MCP 的權限邊界 |
| 資安檢測 | 軌道一（複用資安 Review pilot）| 應用系統優先 | 引用「Anthropic 自己都要求外部 PR 先人工核准」這句話，把 `/security-review` 式工具的批准閘寫進流程 |
| 低風險/最小變異開發 | 軌道一 + 韌體/CMS 延後 | 韌體/CMS 明確排在 Wave 3 | 用 Replit 9 秒刪庫案例佐證 R3 四重保護的必要性；承認韌體/Databricks verifier 要自己設計，不裝作有現成方案 |
| PM/設計 Agent 輔助 | 軌道二（跨部但先觀察）| PM/SA 角色 | 不急著找外部案例，先讓自己的 PM 用起來，半年後自己就有案例可以輸出 |

**沒有變的判斷**：資安 Review pilot 的閉環追蹤（4 月斷過的地方）仍是第一優先；Repo Coordination Graph 仍是唯一該從第一天就跨部做的事。這次研究補的是「軌道一該怎麼做得更具體」，不是推翻既有策略。

## 附：查核方法與限制（誠實揭露）

- 6 個搜尋角度、25 個來源、111 個候選 claim，抽樣驗證 25 個，**22 個通過（3 票投 2 票以上）、3 個被推翻、0 個無法判定**
- 所有來源集中在 2025-11 至 2026-05，**是個快速變動領域的即時快照**，具體數字（否決率、時間節省、review 缺口比例）應視為方向性參考，定期回頭查核，不要當作永久不變的常數寫進正式政策
- 開源 AI 政策統計（11.8% 有政策、78% 允許、51% 要求揭露、74% 要求人類把關）描述的是**外部開源貢獻者治理**，不是企業內部 code review 政策，引用時要做轉譯，不能直接套用
- 沒有任何一個來源來自韌體或 production 資料 pipeline 為主的團隊——credential isolation / 無狀態 harness / 最小動作集這些模式全部來自 SaaS/web 場景，套用到韌體與 Databricks pipeline 前需要你們自己做一次「這個模式在物理不可逆場景下還成立嗎」的檢查
